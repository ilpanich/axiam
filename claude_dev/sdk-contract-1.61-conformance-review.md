# CONTRACT 1.61 — cross-SDK conformance review (the 1.0.1 fields)

**Date:** 2026-10-13
**Scope:** the eleven `claude/contract-1.61-sync` branches, one commit each on top of
`origin/main`, each opened as a draft PR — the sync of `sdks/CONTRACT.md` 1.61 (axiam
`058d8e0f1`, branch `claude/release-1.0.1`). The rows read are those §34.5 assigns to every SDK:
`Certificate.user_id` and its two request members (§27.11 rule 5, with its one required test),
`SsfStreamInput.expected_updated_at` with the three meanings of `events_requested` on an update
and the rule that an edit sends back what it read (§32.2, §32.3 rule 4, §32.8 test 1, which also
answers ilpanich/axiam#631), and `CibaPendingList.total_pending` / `truncated` (§33.3 rule 16).
The rest of §34.5 is informative and asks nothing of an SDK.

**Outcome:** no wire defect. Every SDK sends `user_id` and `expected_updated_at` exactly as given
and leaves the key out when unset, decodes `null` and an absent `user_id` alike, sends
`events_requested: []` as `[]`, surfaces a `409` once, and states conformance at 1.61 without
moving its version. Two SDK fixes were made, one signed commit each on the same branches
(**R161-java-01 / -02**, `35ed4d7`; **R161-python-01**, `a034e2f`). The contract text raises seven
questions for the axiam PR (§5), none worked around: the largest are that **none of the eleven
SDKs carries `CibaPendingList`** although §34.5 lists it as SDK work (Q1), that Rust and Java
cannot add a model member without breaking a struct literal or a record constructor although the
contract's change-log line says "no SDK-side breaking change" (Q5), and that one request member
can be sent as `null` from TypeScript only (Q3).

## 1. Method

One reviewer read every repository against the same checklist, every cell carrying a `path:line`
on the commit below (the code won wherever a README, a CHANGELOG or a commit message disagreed):

1. Vendored `CONTRACT.md`, `openapi.json`, `management-registry.json` and `proto/` byte-identical
   to axiam `058d8e0f1` (`cmp`; `diff -r` for `proto/`).
2. The §27 surface regenerated by the SDK's own generator and its `--check` clean, with no
   hand edit in a generated file.
3. `Certificate.user_id` on every certificate response model the SDK ships (`Certificate`, which
   is also the `certificates.list` projection, and `GeneratedCertificate`); `null` and absent
   both "no account named"; never coalesced or synthesised; the request member on `generate` and
   `sign_csr` sent as given and left out when unset (never `null`); §27.11 rule 5's required
   test present and asserting what the rule says.
4. `SsfStreamInput.expected_updated_at` optional, passed as the string read, omitted when unset;
   the read-modify-write helper sends back the `events_requested` and `expected_updated_at` it
   read, `[]` as `[]`; an absent `events_requested` stays absent; `409` surfaced and not retried;
   §32.8 test 1's new assertions present.
5. `CibaPendingList.total_pending` / `truncated`: modelled, or the claim "this SDK ships no such
   type" verified by search.
6. Every transport the model crosses (REST; `proto/` and the AMQP contract, §8 and §8b, were
   searched for the three models — none of them is on gRPC or AMQP, so the seven full-surface
   SDKs carry them on REST alone).
7. README conformance statement at 1.61, CHANGELOG `[1.0.1]`, version not bumped.
8. Anything else wrong in the diff.

The suites were run wherever the toolchain was in the sandbox. Disk was shared with another
executor, so the Rust build used `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=0`, and
`cargo clean` ran afterwards. Where a suite was not run, the report says so and the review is by
reading, plus a probe in the review's scratch area where one was cheap (PHP). No probe was
written into a repository.

## 2. What the suites did not catch

All suites that ran were green, and every repository carries §27.11 rule 5's required test and
§32.8 test 1's new assertions by name. What the suites do not see:

- **Nothing builds `examples/` in most repositories.** The Java mTLS-provisioning example passed
  six arguments to a record with eight components and did not compile (R161-java-01); it was
  already one short at 1.0.0 and 1.61 added the second missing one. Of the eleven, only C builds
  its examples with its suite.
- **A helper that reads a date-typed model cannot show a changed spelling by a test that uses
  `Z`.** Kotlin's helper test reads `…00Z` and gets `…00Z` back (`Contract161ModelsTest.kt:161-169`);
  Java's compares the instants, which is the right assertion for what it does and the wrong one
  for what its Javadoc said (R161-java-02). Both re-render (Q4).
- **No test assigns `null` where the request type allows it** except Python's (and Python's was
  written for it). TypeScript sends such a `null` (R161-typescript-01, Q3).
- **`GeneratedCertificate` is tested with a UUID only in Rust, TypeScript, Python and Go.** `null`
  and absent decode there by the same mechanism as on `Certificate` (an `Option` with
  `#[serde(default)]` on the wire twin, `models.rs:2462`; an optional property, `models.ts:2339`;
  a `None` default, `models.py:2540`; a pointer, `management_models.go:1753`), so this is a gap
  in the assertion, not in the code.
- **The 1.61 change to `ManagementModel.to_wire` in Python also changes `ScimTargetInput`** (an
  assigned `None` was sent as `null`; the CHANGELOG says so), and no test said it
  (R161-python-01).
- **`409` "not retried" is vacuous as a test of retry.** A `409` is in no SDK's retry set, so the
  assertion holds for any client; the PHP test even builds its client with retry off
  (`ManagementRouteTestCase.php:34`). The assertion that matters is §32.8 test 5 (`503`, once),
  which every repository already had.
- **The three meanings of `events_requested` are restated at the `update_stream` call site in six
  SDKs** (Java, PHP, Kotlin, C#, C++, Swift) **and only on the member in five** (Rust, TypeScript,
  Python, Go, C), where `openapi.json`'s new description puts them in all eleven. Nothing in §32
  requires the call-site text (Q6).
- **Source compatibility.** The suites compile against the new shape, so no test shows the
  struct-literal, record-constructor and positional-argument breaks the new members cause (Q5).

## 5. Questions for the axiam PR

Each is reported as a question, never worked around; each SDK's behaviour is stated so the answer
can be applied to the right ones.

**Q1 — `CibaPendingList` is listed as SDK work but is reachable by no generator (§34.5 table,
§33.3 rule 16).** §34.5 puts `CibaPendingList.total_pending` / `truncated` under "SDK work: yes,
read-only: a generated model carries the two members; no operation", and §33.3 rule 16 says an SDK
"that generates its models from `openapi.json` carries `CibaPendingList` with the two members and
needs nothing else". None of the eleven generators works from `openapi.json` alone: each takes
`management-registry.json` (§27.8) and emits the schemas its operations reach (Go's
`internal/cmd/genmanagement/main.go:924` `schemaClosure` and Java's `scripts/gen_management.py:753`
say so in as many words), and the registry reaches neither `CibaPendingList` nor `CibaApprovalPage`
(the route's tag `ciba` is excluded and no operation returns the type). A search of all eleven
repositories finds no such type, and each says so in its CHANGELOG.
Is "not modelled" conformant — then the table's SDK-work cell should read "no" — or must the
registry carry the schema (for example a list of schemas no operation reaches) so that the
generators emit it?

**Q2 — does the "cut to the new `events_allowed`" bind a converter that returns a body to edit
(§32.2)?** §32.2 says a composed read-modify-write form, "and any helper that edits a stream a
caller read, MUST therefore send the `events_requested` and the `expected_updated_at` it read, the
former cut to the new `events_allowed` when the ceiling was lowered". Ten SDKs offer a converter
(`From<&SsfStream>`, `ssfStreamInputFrom`, `ssf_stream_input`, `ToInput`, `ReplacementBodies.from`,
`SsfStream.toInput`, `ToInput()`, `axiam_mgmt_ssf_stream_to_input`, `to_input()`,
`SsfStreamInput(copying:)`) that returns the body for the caller to change; it cannot know that the
ceiling will be lowered, so the cut is the caller's and each documents it. Only PHP's
`ReadModifyWrite::ssfStream($stream, $changes)` takes the change and cuts. Is a documented caller
duty enough for a converter, or must ten SDKs add a form that takes the change?

**Q3 — an assigned `null` on a request member (§27.11 rule 5, §32.2).** The rules say the key is
omitted when the caller names no account / sets none, and that `null` is not sent. The spec types
all three members `["string","null"]`. TypeScript is the only SDK whose request type holds `null` apart from unset (`string | null` on
an optional key, spread into the body), and it sends an assigned `null`. Python drops an assigned
`None` (`_NEVER_NULL_MEMBERS`, which the commit also applies to `ScimTargetInput`); in the other
nine `null` and unset are one value (an `Option`, a pointer, a nullable reference or an optional)
and the key is omitted. Is an explicitly assigned `null` "none" (to be dropped) or a value to send
as given? If dropped, TypeScript needs the rule (`user_id` ×2, `expected_updated_at`).

**Q4 — "exactly as the response carried it" for a helper that reads a date-typed model (§32.2).**
The rule says to pass the `updated_at` through "the string, not re-formatted: the comparison is of
the instant, and a timestamp rounded to fewer fractional digits than the server stored does not
match". Eight SDKs hold `updated_at` as a string. C# keeps the server's string next to the parsed
value. Java (`OffsetDateTime`) and Kotlin (`Instant`) parse it, because the generators turn every
`date-time` into a date type, and their converters re-render the same instant to the nanosecond
(`+00:00` → `Z`, fraction digits regrouped). Is an instant-preserving re-rendering by a converter
conformant (then say that "verbatim" binds the caller-set string and that a converter over a typed
model must preserve the instant to the nanosecond), or must Java and Kotlin keep the response's
own spelling as C# does?

**Q5 — "no SDK-side breaking change" (change-log line of 2026-10-13, and the SemVer promise of
each README).** The line says "clarifications and three optional fields; no SDK-side breaking
change". Wire-additive, yes; source-additive not in every language: a member added to a Rust
struct without `#[non_exhaustive]` breaks every struct literal that names all fields (five
structs, `CHANGELOG.md:33-35` of the Rust SDK says so, while its README says a breaking change
waits for 2.0.0); a component added to a Java record breaks the canonical constructor (the Java
README carves records out of its promise); Kotlin and PHP constructors gain a parameter in
alphabetical position, so a positional caller shifts; C, C++, Go (unkeyed literals) and Swift
(an initialiser with defaults) are source-compatible in practice. Should the line say so, so that
the release plan can choose 1.1.0 for the SDKs where it matters, or is 1.0.1 intended for all
eleven?

**Q6 — is the three-meanings text required at the `update_stream` call site (§32.2)?** §32.2 says
the omitted-member defaults are "repeated at the `update_stream` call site". Six SDKs repeat the
three meanings of `events_requested` there (Java, PHP, Kotlin, C#, C++, Swift); Rust, TypeScript,
Python, Go and C state them only on the member, from `openapi.json`'s new description. Is the
call-site text part of the rule?

**Q7 — "MUST NOT judge the value client-side" for a typed UUID (§27.11 rule 5).** The request
`user_id` is a `uuid`. Rust, Go, Java, Kotlin and C# type it, so a string that is not a UUID
cannot be sent from them; Python, PHP, TypeScript, Swift, C and C++ pass any string (the Swift, C and C++
tests send `not-a-uuid` to show it). Is the type a "judgement" the rule forbids, or is a
malformed UUID outside the rule, which concerns the server's semantic `400`s (wrong type, unknown
user, disagreeing `metadata.user_id`)?
