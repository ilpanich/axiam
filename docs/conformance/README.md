# Conformance receipts

OpenID Foundation conformance-suite results for AXIAM, published in full —
green and red alike.

That phrasing is a commitment, not a flourish. The fee-waiver letter in
[`claude_dev/fapi-certification-submission.md`](../../claude_dev/fapi-certification-submission.md)
tells the Foundation that "our OpenID conformance-suite results will be
published in full alongside the certification, green and red alike", and AXIAM
already publishes its benchmark receipts including its own regressions. Reports
are added here **alongside** earlier ones, never over them. Deleting an
inconvenient run would break a promise made in a letter.

`index.md` is generated by `just conformance-report`. This file is not — it is
maintained by hand, and it is where §X5.3 says to record the image digest a
report was produced against.

**Nothing here is a submission**, and the headline numbers should not be read as
a verdict on AXIAM. Most of the FAPI failures and every one of the 31 `WAITING`
modules are properties of the harness and the deployment, described below. The
three findings that *are* about AXIAM are in their own section, and they are the
reason running this was worth it.

Two variants were not run at all: the FAPI `self-signed` plan (no reason beyond
time) and the FAPI `private_key_jwt` plan, which **cannot** run — the registrar
has never provisioned its two clients, though `conformance-run` has always
driven the plan. That is defect 15, still open.

## Reading a report

`report.py` writes failures first and states what each verdict means, because
the most common way a first certification submission comes back rejected is a
wall of unread `REVIEW`s treated as green. Three verdicts matter here:

- **`REVIEW` is not a pass.** The suite could not judge the module mechanically;
  a human must read the log.
- **`WAITING` is not a result at all.** The module is parked waiting for a
  browser to complete an authorization. No assertion has been evaluated, so it
  is neither evidence of conformance nor evidence against it.
- **`SKIPPED` can hide a finding.** Three modules here were skipped because a
  scope was not advertised — see below. A skip that follows from a gap is not
  the same as a skip that follows from an inapplicable variant.

## The first run: what it cost to get one module to execute

The runbook predicted that "the first person to run it should expect to find
harness bugs, and should fix them here rather than working around them
locally." That was right, and understated. Fifteen defects stood between the
committed harness and a working run. They are listed because the *shape* of them
is the useful part: almost none were discoverable by reading, and each produced
a symptom that pointed somewhere other than its cause.

| # | What broke | What it looked like |
|---|---|---|
| 1 | `SUITE_IMAGE` named `ghcr.io/openid/conformance-suite`, which does not exist | `denied` on pull — reads as a credentials problem. The file's own comment said gitlab; the value was wrong |
| 2 | Pinned tag `release-v5.1.34` had been reaped by the registry's retention policy | Tag not found. A *tag* pin is not reproducible; only a digest is |
| 3 | Compose set `MONGODB_URI`, which the image never reads | Inert. Worked only because the image's `MONGODB_HOST` default equalled the service name |
| 4 | The entrypoint turns an unset `OIDC_GITLAB_CLIENTID` into an **empty** property, overriding the jar's defaults | `Client id of registration 'gitlab' must not be empty` — the suite would not boot at all |
| 5 | Compose had trimmed upstream's nginx sidecar as "an httpd fronting a hosted deployment" | It is the TLS terminator. The app serves plain HTTP on 8080 and nothing published it |
| 6 | Healthcheck probed `https://localhost:8443` *inside* the suite container | Nothing has ever listened there; the service could never become healthy |
| 7 | The suite refuses any request that did not arrive over TLS | `A non-https request has been received by the conformance suite` — for every path, including the healthcheck |
| 8 | `localhost.emobix.co.uk` does not resolve on every host | A bare `000` from every script. Needs an `/etc/hosts` entry, and a resolver-cache flush where `nsswitch` puts `resolve` before `files` |
| 9 | `register-clients.sh` required `AXIAM_ADMIN_TOKEN`, a bearer nothing in AXIAM's admin flow issues | Admin auth is a session: an `org_slug` login, a cookie, and an `X-CSRF-Token` echoed on writes |
| 10 | `suite.env` is **tracked**, and the registrars rewrite it in place | Survivable while only client ids were written; the Basic lane writes client **secrets** |
| 11 | Config files overrode the environment | `AXIAM_ADMIN_PASSWORD=` in the committed file *cleared* an exported credential; the registrar exited 1 having printed nothing |
| 12 | `AXIAM_ISSUER` served two vantage points at once | `host.docker.internal` resolves only inside a container; host-side scripts got `Could not resolve host` |
| 13 | `render-plan.sh` demanded FAPI certificates and client ids for *every* template | The Basic plan was unrenderable, and the error advised a step that would not have helped |
| 14 | The three FAPI templates carried variants the suite rejects | `Unknown variant parameter(s) [fapi_client_type]`, then `Variant 'fapi_request_method' has been set by user, but test plan already sets this variant`. **No FAPI plan had ever been creatable** |
| 15 | `register-clients.sh` never provisions the `private_key_jwt` clients, though `conformance-run` drives that plan | Still open. That third variant cannot run |
| 16 | `report.py` wrote `docs/conformance/README.md` | It clobbered this file — the one §X5.3 tells an operator to maintain. It now writes `index.md` |

All but #15 are fixed in the harness rather than worked around, which is what
the runbook asked for. Two things worth being precise about:

- **The FAPI plans had never run.** Not "had not been run recently" — the
  templates could not create a plan, so no module had ever executed from them.
  Any earlier statement resting on the FAPI harness being ready was resting on
  something untested.
- **The environment matters more than expected.** The docker bridge on the
  machine that produced this run is a custom `192.168.10.0/24`, not the
  conventional `172.17.0.1`, and port 8443 was already held by unrelated
  software. Both are now discovered or configurable rather than assumed.

## Findings about AXIAM, not about the harness

Three came out of the first FAPI module that ever executed
(`fapi2-security-profile-final-discovery-end-point-verification`). They are
real, they are in the discovery document, and no unit test had caught them.

1. **`code_challenge_methods_supported` is absent.** RFC 8414 §2 defines it and
   the suite requires `S256`. AXIAM enforces PKCE; it does not advertise that it
   does.
2. **`token_endpoint_auth_signing_alg_values_supported` is absent.** Required by
   FAPI 2.0 for the `private_key_jwt` family.
3. **A tenant-scoped discovery URL cannot be used by a conformance plan.** The
   suite's `CheckOauthDiscEndpointIssuer` refuses it:

   > issuer listed in the discovery document is not consistent with the location
   > the discovery document was retrieved from. These must match to prevent
   > impersonation attacks.

   OIDC Discovery ties the retrieval location to the `issuer` claim, and W7's
   `?tenant_id=` query parameter breaks that correspondence.

### The third finding has a measured consequence

It is tempting to file that last one as cosmetic, on the grounds that the scopes
still work — and they do: the request-time gate and the userinfo release resolve
the tenant from the **client**, not from the discovery document, so a client
registered for `address` and `phone` gets them. This run measured what is
actually lost, and it is not cosmetic:

> `oidcc-scope-address`, `oidcc-scope-phone` and `oidcc-scope-all` were
> **SKIPPED**.

The suite reads `scopes_supported` and declines to test a scope the server does
not advertise. So a Basic OP certification run against the bare well-known URL
leaves AXIAM's sensitive-scope support **entirely unexercised** — three modules
that would otherwise be evidence, silently absent from the result. A reviewer
scanning for red would see none.

Three ways out, none taken here, because the choice is an architectural one
about what an AXIAM issuer *is* and it is larger than one wave:

- give each tenant its own issuer URL, so discovery is path-scoped rather than
  query-scoped and the issuer claim matches;
- let a deployment nominate a default tenant for the bare document;
- accept it, and document that AXIAM advertises the sensitive scopes only to
  callers that already know their tenant.

## The interactive wall

Thirty-one of the Basic plan's 35 modules finished `WAITING`.

The cause is specific, and worth recording because `browser_sso` was expected to
solve exactly this. The W3 login hop redirects to `LOGIN_PATH` — a *same-origin*
`/login`, deliberately, since same-origin is what keeps `return_to` path-only
and stops it becoming an open redirect. But the `axiam-server` binary does not
serve that route; the admin SPA does. So:

> `just conformance-serve` is sufficient for the metadata half of a plan
> (discovery, JWKS, token, userinfo) and cannot complete a single authorization
> module.

A conformance target must serve the SPA and the API **on one origin** — which
the production nginx image already does. Until a run is pointed at such a
deployment, `browser_sso` buys nothing unattended, a `browser` automation block
in the plan would be driving a page that 404s, and the interactive modules must
be finished by hand in the suite UI. This is the top follow-up.

One module produced a genuine verdict rather than waiting:
`oidcc-server-client-secret-post` **FAILED** at `GetStaticClientConfiguration`
("As static client was selected, the test configuration must contain a client
configuration"). The rendered plan does carry a complete `client2` block with a
client id, a 64-character secret and a scope list, so the cause is not a missing
value and is **not yet determined**. It is recorded as open rather than
attributed: nothing here demonstrates an AXIAM defect.

## Reproducing a run

```bash
just conformance-certs             # CA, two client certs, AXIAM's own server cert
just conformance-up                # the pinned suite + mongo + the TLS sidecar
cargo build -p axiam-server --no-default-features
just conformance-serve             # AXIAM with TLS, on a non-loopback bind
just conformance-register          # the FAPI clients
just conformance-register-basic    # the Basic OP clients and the test user
just conformance-run               # the FAPI plans
just conformance-run-basic         # the OIDC Core Basic plan
CONFORMANCE_DATE=$(date +%F) just conformance-report
```

Two things the recipes do not do for you:

- **`sensitive_scopes_enabled` must be on at the ORGANIZATION level.** It is off
  by default and validated disable-only at the tenant level — a tenant may turn
  its organization's decision off, never on — so setting it on the tenant is
  refused, both scopes stay unregistrable, client registration fails, and it
  reads like an AXIAM bug rather than a missing switch.
- **`localhost.emobix.co.uk` must resolve.** Add `127.0.0.1
  localhost.emobix.co.uk` to `/etc/hosts`, and flush the resolver cache if
  `/etc/nsswitch.conf` lists `resolve` before `files`.
