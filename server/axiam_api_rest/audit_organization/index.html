The organization a system-partition request row concerns (SA-02, N1).

The request audit middleware (axiam_audit::AuditMiddleware) writes a row with a nil tenant for every request it cannot attribute to a tenant: no verifiable access token, no handler-proven [axiam_audit::AuditAttribution]. That partition is deployment-wide, and GET /api/v1/audit-logs/system returns an organization only the rows whose recorded organization is its own. This module is where a request row’s organization is decided.

system_audit_organization runs inside the audit middleware (the composition root wraps it there). After the request has been served, and only for a request the middleware will record in the system partition, it starts the lookup of the organization on a task of its own and lets the response go (review SR4-3): the audit worker waits for the answer, through an [axiam_audit::PendingAuditOrganization], before it writes the row. No response waits on the datastore, so a response’s latency says nothing about whether the id its path names exists, whatever the cache below holds. The organization is resolved from something the server has verified, never from a value the client merely sent:

  1. a VerifiedAuditTenant an extractor inserted after verifying a credential that names the tenant — a SCIM provisioning token — gives that tenant’s organization;
  2. otherwise a path /api/v1/organizations/{org_id}/… naming an organization that exists gives that organization;
  3. otherwise a path /saml/v2/{tenant_id}/… or /t/{tenant_id}/… naming a live tenant gives its organization.

Anything else records no organization, and the row is then returned by the system endpoint to nobody: a request that names no organization in its path (/oauth2/token?tenant_id=…, /api/v1/users without a token), or one that names an organization or tenant that does not exist. A datastore failure during the lookup counts as unresolved: the row is still written, without an organization. A path segment says which organization a request was addressed to, not who sent it; that is exactly what the row records (the traffic aimed at that organization’s routes), and it can only ever be shown to that organization.

§What the lookup costs (review QR2-8 / SR2-4)

The resolver runs for every request the middleware writes to the system partition — every token-less request among them, a cheap 401 included — and outside every scope-level rate limiter. A path naming an organization or tenant would therefore cost one datastore point read per request, and a client looping an invented id could turn each 401 into one. SystemAuditOrgCache bounds that: an id that resolved is remembered for RESOLVED_TTL, an id the datastore says does not exist for the shorter UNRESOLVED_TTL, so a repeated id costs one read per TTL, not per request. A datastore failure is not remembered. What it cannot bound is a client sending a different invented id every time: each still costs one indexed record-id read, limited by the deployment’s edge and unauthenticated rate limits and, in how many run at once, by the bound below. Do not add a lookup here that is dearer than that.

§How many lookups run at once (review SR15-1)

Since SR4-3 nothing makes the client wait for its lookup, so the cache alone would leave a client sending a fresh invented id per request free to pile up detached reads, each outliving the audit worker’s wait for it. The datastore reads are therefore bounded process-wide: a lookup that misses the caches takes one of MAX_CONCURRENT_LOOKUPS permits of a semaphore held beside the cache (try_acquire_owned, which never waits) immediately before its read, and keeps it until the read has finished. A lookup the caches answer — this module’s own, or crate::tenant_org_cache — reads nothing and takes no permit (review QR16-2), so a known organization’s rows keep recording it however many invented ids hold the permits. A lookup that must read while every permit is taken reads nothing and answers no organization: its row is written without one — returned by the system endpoint to nobody, the same fail-safe answer as an id that names nothing. Either way its response was served exactly as any other.

The cache is an optimisation of the lookup’s cost, not of any response’s latency (review SR4-3): the lookup, cached or not, runs on its own task after the response has gone, so the two TTLs differing — a known id served from memory where an unknown one is read again — cannot be timed by the client. The response path does the same work for every id: it reads the path and spawns the task. Whether a permit is free is decided inside the task, after the caches, so it cannot change the response either.

Structs§

SystemAuditOrgCache
What a path id resolved to, remembered for RESOLVED_TTL when it named something and for UNRESOLVED_TTL when the datastore said it does not exist. A datastore failure is never remembered.
VerifiedAuditTenant
A tenant an extractor has verified a request concerns, for a request that carries no access token: the SCIM provisioning token’s tenant, once the token resolved.

Constants§

MAX_CONCURRENT_LOOKUPS
How many organization lookups may be in flight at once, process-wide (review SR15-1).
RESOLVED_TTL
How long an organization or tenant the path names, once found, is served from SystemAuditOrgCache before it is read again.
UNRESOLVED_TTL
How long a path id that named no organization or tenant is remembered as unresolved (QR2-8 / SR2-4).
