The CIBA pending list’s in-process limiter (R101W3-04).

GET /api/v1/ciba/requests is limited per signed-in user, not per address (D-4, #599): thirty console tabs behind one egress address must not silence each other’s badges. The principal exists only once the handler’s extractor has authenticated the token, so the bucket cannot be route middleware; the handler spends ciba_approval_list:{tenant}:{user} from the shared counter.

That counter admits everything when it is switched off (AXIAM__RATE_LIMIT__SHARED=off). The route then had no limiter at all, so the handler falls back to this one: a keyed governor limiter held in AppState, one cell per (tenant, user), with the same allowance (ciba_approval_per_min, burst = per-minute rate, as build_governor sizes the neighbouring routes) and the same 429. It is per process, as every in-process limiter is; the shared counter is what makes the limit hold across replicas when it is on.

§Memory

A key reaches this limiter only after the bearer token has authenticated as a console sign-in of that user, so the map is bounded by the number of users who list in a window, never by what a caller can invent. It is still swept: CibaListLimiter::check drops every cell that has fully replenished (retain_recent) and returns the freed capacity (shrink_to_fit) at most once a minute, which is the time a cell takes to replenish.
