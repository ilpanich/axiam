The network-segment and RADIUS reply-profile management routes (RADIUS Live profile, W6.3; claude_dev/radius-reply-profile-design.md §4, §5).

Ten operations under /api/v1/network, in the network OpenAPI tag and the management registry:

segmentsprofiles
listGET /network/segmentsGET /network/profiles
getGET /network/segments/{id}GET /network/profiles/{segment_id}
createPOST /network/segmentsPOST /network/profiles
replacePUT /network/segments/{id}PUT /network/profiles/{segment_id}
deleteDELETE /network/segments/{id}?version=DELETE /network/profiles/{segment_id}?version=

A segment is a node of the reserved /network subtree of the resource tree (§4.1); its reply profile is owned by the segment and keyed by its id (one per segment, at most), which is why the profile routes are addressed by segment_id. The routes are human-only (network:* is a HUMAN_ONLY_FAMILIES family): a network administrator is a person, and a service-account token is 401 at the extractor. The tenant is the token’s; a segment or profile of another tenant is 404, exactly as one that does not exist.

§Permissions

  • a read needs network:read — at the /network root for a list, at the segment for a get (§4.2: “/network or below”);
  • a write needs what the write gate asks for, not a route-level guess: network:segments_write at the parent (create) or the node (replace, delete) and H6 — and for a replace that changes vlan_id, rank or enabled of a segment that has a profile, or a delete of such a segment, network:grant at the segment and, on a quarantine segment, at its quarantine site (R110W6-03 and the decision of 2026-10-16: that write moves or removes every device that may join it); network:profiles_write and network:grant on the segment, the envelope, the quarantine site’s network:grant and H6 for a profile write (§5.2 H1–H6), and the same minus the envelope for a profile delete. axiam_authz::network_gate is the one place that logic lives.

§What every write does, in this order

  1. the body (400; an unknown key is refused naming it — a profile is a typed record, not an attribute list, §3.4);
  2. the gate (crate::network_gate::authorize): 403 or 400, each with an audit row of its own carrying the internal rule (H2, 4.2:segments_write, …) and the values before and after (§5.4). It returns the NetworkWriteClearance the repositories demand, so a write cannot reach the datastore without it;
  3. the reactor’s veto hook (network.pre_segment_write / network.pre_profile_write, X1): a four-eyes rule on network policy. It is asked only about a write the gate cleared;
  4. the write, conditional on the version the caller read — 409 when it is stale. Every 409 of these routes carries a closed reason_code beside error (NetworkConflictReason: stale_version, strands_profile, has_children, …; §36.4), so that no client parses message. A profile write is also conditional on the owning segment’s version (the envelope it was checked against), and an envelope write that would strand the segment’s profile outside its new filter_ids is 409 naming the profile;
  5. one audit row: the write (network_segment.created / .updated / .deleted, reply_profile.created / .replaced / .deleted) with the values before and after and the versions — or, when step 3 or 4 refused, a *.write_refused row with the internal reason. Every write and every refusal leaves exactly one row.

Writes are metered by RateLimitConfig::network_admin_per_min, one bucket per route (network_segment_create … network_profile_delete); reads are not separately limited.

§The tenant’s Session-Timeout cap

Two more operations, beside the ten, on the one row of tenant policy the network surface has (network.session_timeout_max_secs, 300 to 86 400, default 3600; design note §3.4):
readGET /network/policy — network:read at the /network root
writePUT /network/policy — NETWORK_SEGMENTS_WRITE (network:segments_write) at the /network root, through the write gate

The maintainer’s decision of 2026-10-15 (plan §13.6), corrected the same day: the cap is the Session-Timeout envelope every profile is clamped to, so its write is network:segments_write’s (envelopes), not network:admin’s (which is administrative login to a NAS device and is not grantable). A holder of network:profiles_write alone cannot write it (H3), and only a grant at the /network root counts. The write is a replacement conditional on the row’s version (0 = never written, the first write; a stale one is 409), in a bucket of its own (network_policy_replace). Lowering is always allowed; raising is allowed and audited (network_policy.lowered / network_policy.raised, each with the cap before and after and the versions). The gate asks no more of a raise than of a lowering — see NetworkWrite::PolicyWrite for why. No reactor hook: the design note names network.pre_profile_write and network.pre_segment_write and no third.

Lowering the cap below an existing profile’s session_timeout_secs is fine: the stored value is untouched, every read that produces a reply clamps it to the cap, and the profile says so (session_timeout_clamped). Raising the cap again restores the stored value — unless the profile was replaced while clamped: a replace stores what it carries, and the gate refuses one above the current cap (H3), so a read-modify-write of a clamped profile stores the clamped value and cannot restore the old one (§36.3 rule 6).
