POST /api/v1/network/decide — the RADIUS placement decision (RADIUS D4, W6.4; claude_dev/radius-reply-profile-design.md §4.3, §6.3, §7, §8; threat T-468).

FreeRADIUS’s rlm_rest, in post-auth after EAP-TLS succeeded, posts the presented certificate (or its fingerprint) and the site key from its own client configuration; AXIAM answers { "allow": false } with no reason, or { "allow": true, "reply": … } with the attributes of the segment the device is placed on, rendered from its typed reply profile.

§The caller (T-468)

An authenticated oracle on “is this certificate good here”, so its caller is held to more than an ordinary machine route’s:

  • a service account (aud = axiam:m2m, sub_kind = service_account); a user’s token, an OAuth2 client’s and a user token narrowed to the machine audience are 401;
  • its token bound to its own certificate: cnf.x5t#S256 present (a plain bearer token, or one bound only by DPoP, is 401), presented over a connection whose TLS-verified client certificate is that one (the extractor’s sender-constraint check), and that certificate resolves — through DeviceAuthService::authenticate_der, now, so a revoked caller certificate stops at the next request — to this service account in this tenant, which is Active;
  • holding network:decide on every site node the decision reads (§4.2: “a site”), so a FreeRADIUS credential for HQ answers nothing about a branch office: 403, audited;
  • metered per caller (network_decide_per_min, D-6), not per address.

The network permission family stays human-only (HUMAN_ONLY_FAMILIES); this one route is the named exception, CERTIFICATE_BOUND_MACHINE_ROUTES.

§The decision (§4.3), at one cost (T-457)

Every request that gets past the caller’s checks runs the same steps, in the same order, whatever the certificate turns out to be:

  1. the certificate row by fingerprint (global), then authenticate_der; another tenant’s certificate is refused (§7), with the reject every other failure gets;
  2. the subject’s account (the device’s service account, or — when no certificate of this tenant resolved — the caller’s own, as a decoy of the same shape) — Active or no placement;
  3. the site’s segments, their stored profiles and the tenant’s cap, each one query; every profile is re-validated and rendered (§3.4), and a profile that no longer validates makes its segment no candidate and is audited once per window;
  4. one check_access_batch of network:join over every enabled segment of the site, for the subject (the decoy included), through the decision cache, deny-override in force — which is what makes quarantine by deny work (§4.4);
  5. the lowest-ranked access candidate, else a quarantine one, else none;
  6. one audit row (T-463, §8), and the answer.

“No candidate”, “another tenant’s certificate”, “an inactive account” and a placement therefore cost the same reads and the same batch; only the answer differs. What authenticate_der itself does differs by its own early refusals (an unknown or revoked certificate stops before the chain is verified) — a residual recorded for the threat model, not hidden.

§What is never on the wire, and never in the row

The deny carries no reason. The audit row carries the internal reason, the site, the certificate’s SHA-256 fingerprint, and — for a certificate of this tenant — its id and the service account it is bound to; never the certificate’s subject or alternative names, and the request accepts no Calling-Station-Id or User-Name (an unknown key is a 400), so none can reach the trail (§8, T-464). A certificate of another tenant is recorded by its fingerprint alone: the caller’s tenant learns nothing about the other’s.

Structs§

CertificateBoundServiceAccount
A service-account caller whose token is bound to a certificate this connection presented — the synchronous half of T-468’s caller binding, run as an extractor so that it answers before the body is read: a plain bearer token is 401 whatever it posts.
NetworkDecisionRequest
The body of POST /api/v1/network/decide. Closed: an unknown key — a MAC address, a user name — is a 400 naming it, so nothing the design note’s §8 keeps out of the audit trail can be posted into it.
NetworkDecisionResponse
The decision: { "allow": false } with no reason, or { "allow": true, "reply": … }.
