The decision route’s two pieces of per-process state (RADIUS D4, W6.4; claude_dev/radius-reply-profile-design.md §3.4, §6.3).

§The caller’s bucket

POST /api/v1/network/decide is metered per authenticated caller — the token’s sub, a FreeRADIUS server’s service account — at network_decide_per_min (maintainer decision D-6). The caller exists only once the handler has authenticated its certificate-bound token, so the bucket cannot be route middleware: the handler spends network_decide:{tenant}:{sub} from the shared counter, and when that counter is switched off (AXIAM__RATE_LIMIT__SHARED=off, which admits everything) from the in-process keyed limiter held here, exactly as the CIBA pending list does (R101W3-04; crate::ciba_list_limiter, whose limiter is reused: it is a keyed (tenant, subject) limiter, and nothing in it is about CIBA). A key reaches it only after authentication, so the map is bounded by the number of callers, never by what a caller can invent.

§One reply_profile.invalid row per profile per window

A stored profile that no longer validates (one edited in the datastore behind the API) makes its segment no candidate, and the design note asks for one audit row per profile per window (§3.4), not one per decision: a site’s power-restore storm would otherwise write a hundred identical rows a second. The window is INVALID_PROFILE_AUDIT_WINDOW; the key is the tenant, the segment, the profile’s version and the rule it fails, so a profile rewritten (a new version) or failing a different rule is reported again at once. It is per process, as every in-process limiter is: N replicas write at most N rows a window.
