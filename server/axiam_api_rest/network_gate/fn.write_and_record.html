Expand description

Run the repository write of a network-sensitive write that the gate cleared, and record it once it landed (R110W6-06, #703, T-484): one network_role.assigned / .unassigned / .granted / .revoked / .deleted or certificate_binding.bound row (one of the six), with the role, the grantee, the node and the network: permissions the write conferred (or removed); an assignment’s row also carries exemption, the named exemption it cleared under (organization-bootstrap) or null. Without it a cleared write is visible only in the route’s generic request row, which says neither that it touched the network namespace nor where a join landed.

The row cannot be separated from the write (R111W4-02, #726). It is built here, before the write, from what the gate read ([GateClearance::role], [GateClearance::permission]) — not from reads after the write, which a concurrent role delete made fail and a concurrent regrant made lie. Then repository_write and the append run as one spawned task, which this function awaits through its JoinHandle. Actix drops a handler’s future when its client goes away; dropping the handle does not cancel the task, so a write that commits is appended whether or not anyone still waits for the answer. The task is spawned through AppState::network_writes — on the composition root’s runtime, which an orderly stop keeps until the task is done or the stop’s budget is spent (NetworkWriteTasks, R112W4-02) — so the write must be Send and own what it uses ('static).

What follows the commit rides the same task (R112W4-01, #775). The D7 decision-cache flush the write needs (flush: the grantee for a user or service-account assignment, the tenant for a group assignment, a role delete, a grant or a revoke; local and broadcast, through AuthzChecker::invalidate_*) runs after the write and before the row, so a revocation’s row is never readable while the allow it revokes is still served from the cache of the replica that wrote it. A failed flush (the broadcast was not confirmed) does not drop the row of a write that landed: the row is appended and the flush’s error returned (503, the handlers’ convention for an unconfirmed revocation). On a stale claim the network_role.*_refused row is appended in the task too (the caller then answers with refused_in_task). Before this, both ran in the handler’s future, after the task: a client gone after the spawn left a committed revocation whose cached allow outlived it, on every replica, until the TTL.

No success row is written when the clearance is not network-sensitive, when the write fails, or when the write is not one of those named above (a role update, a resource write, a segment or profile write — those keep their own rows).

A failure to describe the write or to append the row is logged and does not undo or fail the write that already landed — the convention of [audit_refusal], and of every other audit append in the handlers. The row carries ids, names and actions only; never a certificate, key or token.

§Errors

Whatever repository_write returns; the flush’s error once the write landed; AxiamError::Internal if the runtime cancels the task (it shuts down). A panic in the task is resumed here.
