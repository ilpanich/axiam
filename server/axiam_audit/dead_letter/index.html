The audit dead-letter file: where an audit row goes when the datastore did not take it (T19.27, T-108).

One file, named by AXIAM__GDPR_AUDIT_DLQ_FILE, append-only, one DeadLetterRecord as JSON per line: {"occurred_at": …, "reason": …, "entry": {…}}. The entry is the replayable [CreateAuditLogEntry]: an operator (or a later replay job) reads each line back with decode_line and appends the entry once the datastore is healthy. The GDPR records’ dead letter (write_audit_with_dead_letter) and the request-audit worker’s both write it, through encode_line, so the two cannot drift apart.

§When, and why (#595)

A bare entry has no timestamp, and the replay creates the row at replay time, so the trail lost when the event happened and its order against the rows written normally. The envelope carries both:

  • occurred_at is when the event happened, captured where the entry is produced and carried with it, never when a writer flushes it. For a request-audit row it is the moment the response finished and the audit entry was built (the middleware, before the row is queued); for a GDPR record it is the moment the record was handed to write_audit_with_dead_letter, which is right after the action it records and before the datastore write that was then refused.
  • reason is a DeadLetterReason: a closed set of short names, never an error’s text (which can carry a query, an identifier, or a secret).

decode_line reads the earlier, bare form too, with neither field.

Two ways in:

  • append_blocking and append_off_thread write the line, and sync it to the device, before they return. For a caller that wants the guarantee: the cleanup sweep’s erasure record and the GDPR request records. The first blocks its thread on file I/O; a request handler uses the second, which runs the same write on the runtime’s blocking pool (#594).
  • DeadLetterWriter queues the row and returns at once; a writer task owns the file. For a caller that must not wait on file I/O — the request-audit middleware, whose only reason to dead-letter is that the system is under pressure. The task syncs the file’s data after each batch it writes.

§Durability and mode (#594)

Each line is one write_all of the line and its newline, so two records never share a line. A write that has returned has also been through sync_data: a host crash does not take it back. (The file’s directory entry is not synced separately, so a crash right after the file was first created can still lose the file itself.) Both openers create the file with mode 0600 on Unix rather than the process umask’s, and tighten an existing file that is readable by group or others to 0600 when they open it (a failure to do so is logged, not fatal: the record is still written). The lines carry user and tenant identifiers and, for a request row, a client address.

§The budget (R1W2-02)

The file is bounded by MAX_BYTES_ENV (DEFAULT_MAX_BYTES, 192 MiB, by default). Request-audit rows may fill the first nine tenths of it (request_row_limit); past that they are refused, counted as not recoverable, and the writer reports itself full. The last tenth is a reserve only append_blocking — the GDPR records — writes into, so an erasure record is not refused because a flood of request rows got there first. Unbounded, the file filled the disk the datastore needs (Compose) or crossed its volume’s sizeLimit, which Kubernetes enforces by evicting the pod and deleting the volume with the file in it.

A request row’s attacker-chosen fields — the path in action, the client-supplied address in ip_address — are cut to MAX_ACTION_BYTES and MAX_ADDRESS_BYTES in every line (encode_line), so a line is about a kilobyte at most whatever the request carried. The budget counts the bytes of the line as written, envelope included (about 100 more than the bare entry).

Constants§

DEAD_LETTER_FILE_ENV
Environment variable naming the dead-letter file. Intended to point at a mounted volume so the file survives a restart. Unset (or empty) means no file is written and a lost row is counted and logged only.
DEFAULT_MAX_BYTES
The budget when MAX_BYTES_ENV is unset: 192 MiB, below the shipped Kubernetes volume’s 256 MiB sizeLimit.
MAX_ACTION_BYTES
The longest action a line carries, in bytes. A request row’s action is "{method} {path}", and the path is the client’s to choose.
MAX_ADDRESS_BYTES
The longest ip_address a line carries, in bytes: an IPv6 literal with a zone and a port fits. The value is the client’s Forwarded / X-Forwarded-For header where a proxy is trusted, and unvalidated.
MAX_BYTES_ENV
Environment variable bounding the dead-letter file, in bytes (R1W2-02). Unset (or empty) means DEFAULT_MAX_BYTES. Keep it below the limit of the volume the file is on.
MIN_MAX_BYTES
The smallest budget MAX_BYTES_ENV may set: 1 MiB, a thousand request rows or so. Below it the file is full before it is useful.

max_bytes_from_env

request_row_limit
