Expand description

Sign a certificate signing request for an end-entity certificate.

The leaf counterpart to SignIntermediateCsr, and the BYOK counterpart to CreateCertificate: the private key is generated by whoever made the CSR — an offline ceremony, an HSM, a device’s secure element, a tenant-side tool — and never reaches AXIAM at all.

There is no key_algorithm field, because the key is the caller’s and the CSR already says what it is; AXIAM reads it from the request’s public key and refuses anything outside its policy rather than recording what it was told. There is no subject field for the same reason: the CSR’s common name is what the certificate says, so the row and the certificate cannot disagree.

The response is a plain Certificate and not GeneratedCertificate: there is no key to return, and a type with a mandatory key field that is always absent is a type that lies.

Fields§

§tenant_id: Uuid

Taken from the authenticated context, never from the body.

§issuer_ca_id: Uuid

The signing CA that issues it. Must be Active, in its validity window, and hold a key AXIAM can sign with.

§csr_pem: String

PEM-encoded PKCS#10 certificate signing request — a BEGIN CERTIFICATE REQUEST block. The legacy OpenSSL BEGIN NEW CERTIFICATE REQUEST header is not accepted.

§cert_type: CertificateType§validity_days: u32

Validity duration in days. Subject to the same tenant cap and the same CA/Browser Forum hard cap as CreateCertificate, and capped to the issuer’s own expiry.

§metadata: Option<Value>§subject_alt_names: Vec<SubjectAltName>

See CreateCertificate::subject_alt_names. Stated here, never in the CSR: a CSR requesting subjectAltName is refused.
