Network segments, their reply profiles and the tenant’s session cap (RADIUS Live profile, claude_dev/radius-reply-profile-design.md §3.5 and §4).

§Segments are resources

A segment is a node of the existing resource tree, in a reserved subtree, so that RBAC, the hierarchy cascade and deny-override apply to it unchanged (§4.1, maintainer decision D-5):

/network                       network_root     (one per tenant, made on first use)
├── /network/zones             network_branch   (kind = access)
│   └── /network/zones/hq      network_site     site_key = "hq"
│       └── …/hq/corp          network_segment  vlan 10, rank 10
└── /network/quarantine        network_branch   (kind = quarantine)
    └── /network/quarantine/hq network_site
        └── …/hq/q             network_segment  vlan 999

Quarantine is a sibling branch, never a descendant of zones: deny-override cannot express “deny the subtree except this leaf”, so a quarantine segment under zones would be denied by the very rule that quarantines. The fixed two-branch shape makes the correct placement the only placement, and NetworkSegmentPath refuses every other.

The segment’s own row (a sidecar of its resource row, sharing its id) holds what the tree cannot: the kind, the VLAN, the Filter-Id names the segment’s profile may choose from (its envelope) and the rank that orders placement.

§Two writers, one version

Segments, profiles and the tenant policy are written conditionally on the version read (plan §10, the two-writer rule). A profile write is also conditional on the owning segment’s version, so a concurrent change to its filter_ids cannot slip a profile past an envelope that no longer holds.

§What this module is not

Who may write any of this (the H1 to H6 rule, §5.2) is the authorization function’s, not the repository’s. The repository refuses only what it can decide from the data: a path outside /network, a value outside the dictionary, a filter_id outside the envelope.
