The RADIUS reply-profile dictionary axiam-radius-reply/1 and the typed profile built from it (RADIUS D4, claude_dev/radius-reply-profile-design.md §3).

§A typed record, not an attribute list

A reply profile is the set of RADIUS attributes AXIAM would put in an Access-Accept for a device placed on one network segment. There is no field in which a writer names an attribute: every attribute a profile can produce is a named, bounded field of ReplyProfileInput, and the dictionary below (DICTIONARY_V1) is the closed set of them. A vendor attribute, an unknown attribute number or a free-form string attribute cannot be expressed, so it cannot be validated wrongly (§3.1).

The VLAN is not a profile field. The three tunnel attributes are derived from the owning segment’s vlan_id (crate::models::network::NetworkSegment::vlan_id); a profile cannot name one, so the only way to put a device on VLAN 99 is to write the profile of the segment that owns VLAN 99 (§3.1).

§The dictionary is code

It is a compile-time table in this layer-0 crate, each entry citing its RFC section. A dictionary change is a code change with review; no API adds an entry. Every stored profile records the version it was validated against and an unknown version is refused, never ignored (§3.4).

§Bounds

The tenant’s Session-Timeout cap is read from crate::models::network::NetworkPolicy. A value above the cap is refused at write time (ReplyProfileInput::validate) and clamped down at read time (clamp_session_timeout): lowering the cap afterwards only narrows (§3.4, §5.2).
