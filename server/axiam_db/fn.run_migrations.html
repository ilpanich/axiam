Run all pending migrations against the given SurrealDB client.

Creates the _migration and _migration_lock tracking tables on first run, takes the startup lease (below), then applies, in ascending version order, every listed migration whose version is not recorded — not merely those above the highest recorded one (#704, R110W6-07). A datastore that recorded v100 without v99 (one that ran a build carrying v100 but not v99) therefore applies v99 on its next start instead of skipping it for ever; such an out-of-order application is logged at warn.

Applying a migration late is safe only when it is additive — every statement a DEFINE … IF NOT EXISTS — and the list holds many that are not: plain DEFINEs (v1 … v14), UPDATE backfills (v43 rewrites every tenant’s mail override), v42’s REMOVE of the SRP schema, and fields OVERWRITEn twice, whose older definition re-narrows the newer ASSERT (#729, R111W4-05). The runner therefore refuses to boot, naming the version, rather than apply a non-additive migration below the highest recorded one; an operator resolves that gap by hand. A released build never leaves such a gap — every migration added since 1.1.0 is additive, which a unit test over [MIGRATIONS] holds — so the refusal is reached only by a datastore that ran a branch build. Each pending migration is applied atomically: the schema DDL and the version-record CREATE are wrapped in a single BEGIN TRANSACTION … COMMIT TRANSACTION so that a mid-step failure leaves the row re-selectable (CQ-B06 / REQ-14 AC-5).

§The startup lease (#755, R111-05)

_migration_lock:startup is a lease on the datastore’s clock (one clock for the shipped single-node SurrealDB; a clustered SurrealDB evaluates time::now() on whichever node runs each statement, so the lease excludes only while the skew between nodes stays under the TTL less one refresh, about four minutes, and past that the tolerance below keeps the outcome correct): a starter CREATEs it with its own random holder and expires = time::now() + ttl, in a transaction that first deletes the row only if it has expired (or carries no expires, as a 1.1.1 binary’s leftover does). A live row makes the CREATE fail, and the starter waits MigrationLease::poll_every and tries again — for as long as the holder keeps the row live. The holder pushes expires forward every MigrationLease::refresh_every while it migrates and runs the organization-tenant backfill, and on the way out, whether it succeeded or failed, deletes the row only if it is still its own. A holder that dies leaves a row that expires after MigrationLease::ttl (five minutes) and is then taken over.

So two replicas starting together do not both migrate: the second waits, then reads the versions the first recorded and has nothing to apply.

§When the lease is not enough

A lease on a clock is not mutual exclusion against a holder that stalls past its TTL without dying. The runner therefore also tolerates the one collision that case can produce: when a migration’s transaction fails and _migration now records that version, another starter applied it — the failure is the unique version index refusing a second record, the transaction rolled back whole, and the runner logs it and continues.
