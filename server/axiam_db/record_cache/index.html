Short-TTL, process-local caches of the records a token endpoint re-reads on every request: a tenant’s liveness, an OAuth2 client, a user account.

§What is cached, and for whom

Only reads that decide nothing they write back use these caches:

  • TenantRepository::get_by_id_cached — the tenant liveness every client authentication checks (R1W1-03);
  • OAuth2ClientRepository::get_by_client_id_with_context — the client a token endpoint authenticates, with its tenant and the token’s account;
  • UserRepository::get_by_id_cached — the account an already authenticated principal’s request is checked against (account_may_act) or describes (UserInfo claims).

The plain get_by_id, which read-modify-write code relies on (lockout counters, TOTP replay steps, settings updates), is never served from here.

A cached user never carries credential material: its password_hash and mfa_secret are blanked before it is stored, so a cached read can never be the input to a credential check, whatever a future caller does with it.

§The staleness bound

Only positive answers are cached, each for at most the TTL (5 s by default, AXIAM__DB__RECORD_CACHE_TTL_SECS; 0 turns the caches off). Every write method of the repository that owns a record drops it from the cache in the same call, so on a single replica a suspension, a deactivation or a secret rotation through the API takes effect on the next request. A write made on another replica, or outside the owning repository, reaches this one within the TTL — the same bound, and the same decision (claude_dev/db-query-optimization.md §8.5), as the session-validation and authorization decision caches.

RecordCaches
The record caches one process shares between its tenant, OAuth2 client and user repositories. Build one at the composition root and attach the same Arc to each (with_record_caches), so a write through any of them drops the entry every reader would have served.
