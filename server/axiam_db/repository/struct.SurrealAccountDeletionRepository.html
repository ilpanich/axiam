pub async fn create_with_pending_flag( &self, tenant_id: Uuid, user_id: Uuid, scheduled_purge_at: DateTime<Utc>, cancel_token_hash: String, ) -> AxiamResult<AccountDeletion>

D-14: atomically mark a user deletion-pending AND create the account_deletion row (holding the cancel_token_hash) in ONE transaction.

Before this method existed, gdpr.rs::request_account_delete issued two fully independent DB round-trips — user_repo.mark_deletion_pending then account_deletion_repo.create — so a failure on the second call (after the first already committed) left the user permanently deletion_pending = true with no account_deletion row to hold a cancel token: an uncancellable purge (CQ-B39 residual). Wrapping both statements in BEGIN/COMMIT guarantees they succeed or fail together.

Also adds a duplicate-pending-request guard (Rule 2: without it, a double-submit race could mint two live account_deletion rows — two outstanding cancel tokens — for the same user). The guard is evaluated inside the same transaction: if a pending deletion already exists for this user, the whole transaction — including the just-issued UPDATE on the user row — rolls back, so deletion_pending is never left true without a matching cancellable row.

Result slots: BEGIN=0, UPDATE user=1, LET $existing=2, IF/THROW=3, CREATE account_deletion=4, COMMIT=5. Every field of the returned AccountDeletion is already known client-side (the id is generated here, everything else is an input or a literal), so we don’t .take() any statement result — .check() alone proves the whole transaction committed.

pub async fn cancel_pending( &self, tenant_id: Uuid, id: Uuid, ) -> AxiamResult<CancelOutcome>

Cancel the pending deletion request id, and re-enable its account, as one transaction — or say why not.

The request must still be pending, unclaimed by the purge sweep (purge_claimed_at = NONE) and inside its grace window when the transaction runs, and the account must still be deletion-pending; the checks and both writes are one transaction. NotFound when there is no such request in the tenant.

pub async fn claim_for_purge( &self, tenant_id: Uuid, user_id: Uuid, now: DateTime<Utc>, lease: TimeDelta, ) -> AxiamResult<PurgeClaimOutcome>

Claim user_id’s erasure for the purge sweep, before its first destructive step, exclusively and for lease (#738).

PurgeClaimOutcome::NotDue when the account is no longer deletion-pending and due at now (its deletion was cancelled since the sweep’s read), and PurgeClaimOutcome::Held when another unit holds a claim on it younger than lease: the sweep skips the account either way. Otherwise the claim is taken, stamped with now, and the answer is PurgeClaimOutcome::Claimed.

The claim lives on the pending request, as purge_claimed_at; an erasure without a request row is claimed by the same stamp on the user row, in erasure_audit_pending — the field the anonymization overwrites with its record marker, and the recovery reads only on an Anonymized row, so a claim on an account not yet erased is never taken for an owed record. A claim is free when its stamp is NONE, released (the Unix epoch, Self::release_purge_claim) or at or before now - lease: two sweeps that read one due account both reach this transaction, the engine serialises their writes to the one row, and the second, retried on a fresh snapshot, finds the first’s claim live.

Once claimed, a request can no longer be cancelled, released or not: the steps before the point of no return revoke what a cancel does not restore.

pub async fn release_purge_claim( &self, tenant_id: Uuid, user_id: Uuid, stamp: DateTime<Utc>, ) -> AxiamResult<()>

Give up the claim stamp on user_id’s erasure without erasing it, so the next sweep takes the account at once rather than after the lease (#738): the request’s purge_claimed_at becomes the Unix epoch — older than any lease, and still not NONE, so the request stays uncancellable — and a user-row stamp is cleared.

Only while the account is still deletion-pending: once the anonymization — the point of no return — has cleared that flag, the user row’s erasure_audit_pending is the erasure’s record marker, not this claim, and is left alone; so is a claim another unit has since taken over, which carries a different stamp.

impl<C: Connection> SurrealAccountDeletionRepository<C>

The erasure-record marker, user.erasure_audit_pending (#689, schema v108).

The anonymization — the erasure’s point of no return — sets it in its own transaction to a stamp the erasure chose and armed its guard from before the write (UserRepository::anonymize_user_marked, #737); the value is the claim’s stamp. The erasure writes its proof and gdpr.user_pseudonymized, and then clears the marker, completing the account’s deletion request in the same transaction (Self::settle_erasure_record). An erasure cut in between leaves it set, and the next GDPR sweep, on any replica, claims it (Self::claim_owed_erasure_records) once it is released (Self::release_erasure_record: the Unix epoch) or older than the lease, writes what the erasure still owed — the proof unless it exists, the record unless it is already there (Self::erasure_recorded) — and settles it. Every write is conditional on the stamp read, so the erasure and a sweep, or two sweeps, never both own the marker.

pub async fn settle_erasure_record( &self, tenant_id: Uuid, user_id: Uuid, stamp: DateTime<Utc>, ) -> AxiamResult<bool>

The erasure’s record is written: clear user_id’s marker and, in the same transaction, complete its pending deletion request — only while the marker still carries stamp, the claim the caller holds. true when this call cleared it; false when the marker was taken over (the replica that took it settles it) or is already clear.

pub async fn claim_owed_erasure_records( &self, now: DateTime<Utc>, lease: TimeDelta, ) -> AxiamResult<Vec<OwedErasureRecord>>

Claim, at now, every erasure whose record is owed and that nobody is recording: an anonymized account whose marker is released or stamped at or before now - lease, and (#689 (i)) an anonymized account with no marker whose deletion request is still pending — an erasure cut before schema v108 between its anonymization and its completion. Each claim stamps the marker with now, conditionally on the value read, so of two sweeps that read one account exactly one takes it. What is returned is this call’s to record, then to settle (Self::settle_erasure_record) or give up (Self::release_erasure_record).

pub async fn erasure_recorded( &self, tenant_id: Uuid, user_id: Uuid, pseudonym: &str, action: &str, ) -> AxiamResult<bool>

Whether tenant_id’s audit trail holds action written for the erasure of user_id — for gdpr.user_pseudonymized, whether the erasure’s record was written before its marker could be cleared (#689). An account is erased once, so the first such row is the one.

The row is written with user_id as its actor and pseudonym in its metadata; it is matched by either. A unit that stalled past its claim’s lease and then ran its audit scrub after another unit had recorded the erasure nils that row’s actor_id (#737): the pseudonym, the keyed HMAC of the tenant and the account and so the account’s alone, still names it.
