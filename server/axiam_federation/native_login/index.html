G-A — verifying a provider-issued ID token presented by a native app as a sign-in. G-A — a provider-issued ID token, presented by a native app, verified as a sign-in.

Design: claude_dev/social-login-gap-plan-2026-10-30.md §3.1. The rule every function here applies:

An ID token is accepted as a sign-in only when it was issued to us.

“Us” is one of the client IDs an operator listed in the provider’s native_login.client_ids for exactly this purpose — not the provider’s web client_id unless it is listed, and never “any audience”. The party a token was issued to is its azp when it carries one, otherwise its single aud (D-N17, see [issued_to]).

This module answers one question: which AXIAM user does this ID token prove signed in, through which provider? The grant that turns the answer into a token set lives in axiam-oauth2 (W2.3).

§The order is the design

[OidcFederationService::verify_native_id_token] runs these steps in this order, each before the next (step 1, client authentication and the grant gate, is the token endpoint’s):

  1. Provider: the request’s provider (UUID or provider_slug) names an effective provider of the requesting tenant — its own, or inherited from its organization, exactly as the browser login’s provider listing resolves it (crate::provider_resolution) — that is enabled, speaks OIDC and has native_login.enabled. A provider of another tenant is not found.
  2. Header: alg=none refused on the raw header, alg within the provider’s allowed_algorithms, kid resolved through the JWKS cache with its rate-limited rollover refetch — no new fetch surface.
  3. Signature and claims, through the browser login’s own verification core: iss exactly the discovered issuer; the token issued to a listed client ID, azp-first (D-N17): a listed azp, with aud (string or array) containing a listed ID or the provider’s web client_id — the shape of Google’s Android tokens — or, with no azp, a single listed aud (several audiences need an azp, OIDC Core §3.1.3.7); exp in the future within the 60 s leeway (D-05); iat neither older than max_token_age_secs nor in the future beyond the leeway.
  4. Shape: an ID token and nothing else — nonce present and equal, in constant time, to the SHA-256 hex of the request’s nonce, the claim’s hex letters compared without regard to case (D-N16, D-N21; the app gives the provider SDK the hash and AXIAM the raw value); an access-token typ (at+jwt) refused. The marker list is [crate::token_shape]’s, the same one X4 refuses by.
  5. Replay: the SHA-256 of the token’s JWS signing input (the bytes before its second .) recorded in the replay store under its issuer, deployment-wide (D-N19), until exp plus twice the leeway; a second presentation through any tenant or configuration is refused, and a store that cannot record refuses too.
  6. Subject: the browser login’s resolution, unchanged — map_identity(provider_kind, attribute_map, claims) and then provision_or_link_identity, provisioning on first sign-in, adopting no email as verified; then account_may_act. A first sign-in whose mapped username or email another account holds is the generic refusal (provisioning_conflict), not a server error (F4-W2-10).

§Why the replay guard sits where it does

The store is keyed on the SHA-256 of the token’s signing input — base64url(header) "." base64url(payload), the exact bytes before the second ., which the signature covers — and a row is written only once steps 2–5 have all passed.

The signature part is left out of the key on purpose (F4-W2-11). An ECDSA signature has a second valid encoding (s → n − s), so an ES256/ES384 token has two compact strings that both verify; hashing the whole string recorded them as two tokens and let one be spent twice. The signing input has one spelling per token: changing a byte of it breaks the signature. That covers any malleable algorithm, not only ECDSA.

  • Not before the signature (step 4). Then anyone could write rows: a stream of garbage tokens would fill the table. A forged token can never take a genuine token’s slot either way — its signed bytes, and so its hash, differ — but only a verified token, one the provider really issued to a listed client ID, is ever recorded.
  • Not before the nonce (step 5). Then someone who obtained a victim’s genuine token without the nonce it is bound to (from a log, a proxy, a crash report) could present it, fail the nonce check after burning its hash, and turn the victim’s own sign-in into a “replay”. Recorded after step 5, only a presenter holding both the token and its raw nonce — the app that started the sign-in — can spend it. That holds because the token carries only the nonce’s SHA-256 (D-N16): the claim a token holder can read from the payload is not the value the request must carry. When the claim itself was accepted too, copying it passed (F4-W2-02).
  • Not after subject resolution (step 7). Then two concurrent presentations would both resolve, and both sign in, before either recorded. The insert is the one atomic decision (a UNIQUE index), placed after everything that proves the presentation genuine and before anything that acts on it.

§What the caller learns

Every refusal past step 2 is one generic answer on the wire (the X4 rule: a wrong token and a wrong configuration are told apart only in the server log); [NativeLoginError] keeps the distinctions for logs, audit and tests. The raw token is never logged, never stored, never returned.
