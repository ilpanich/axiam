Forwarding a re-authentication requirement to the upstream identity provider (#838, D-N26).

When a relying party asks AXIAM for a fresh authentication — prompt=login, a max_age the current session cannot meet, a step-up — the sign-in page may answer it with “Sign in with X”. Until #838 the upstream request said nothing about freshness, so a provider holding an SSO session of its own answered at once, with no credential, and the “re-authentication” proved only that the browser still had a cookie at the provider.

Two halves, kept apart because they fail differently:

  1. Ask (oidc_params, oauth2_params, and ForceAuthn="true" on the SAML AuthnRequest). What a provider accepts is the provider’s business, so the parameters are chosen per [ProviderKind] rather than sent uniformly: Google answers prompt=login with an error page rather than ignoring it, which would turn a re-authentication into a dead end.
  2. Verify (check_fresh). Asking is not proof. Where the provider states when it authenticated the user — OIDC auth_time, SAML AuthnInstant — the callback refuses an instant that predates the start of the sign-in. Where it states nothing (every plain-OAuth2 provider, and an OIDC provider that omits auth_time) there is nothing to compare, and the sign-in is accepted on the strength of the request alone; the session is then dated at AXIAM’s verification moment, as before. That residual is recorded in the threat model (T-493) rather than closed by refusing every such provider, which would make a prompt=login relying party unusable for a GitHub user.
