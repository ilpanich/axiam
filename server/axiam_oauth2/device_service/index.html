Device Authorization Grant service (RFC 8628) — B2.

Deliberately a separate service from crate::token::TokenService rather than a seventh generic parameter on it. The device flow needs one repository nothing else needs, and threading it through a service that already carries six would change every construction site in the codebase to serve one grant. The REST layer dispatches grant_type=urn:ietf:params:oauth:grant-type:device_code here and everything else to TokenService, which keeps the seam at one match arm.

§The polling contract (RFC 8628 §3.5)

The device hits the token endpoint in a loop. Almost every one of those requests is answered with an error, and that is normal:

StateAnswerDevice should
pendingauthorization_pendingkeep polling at interval
pending, polled too fastslow_downraise its interval and keep polling
approvedtokensstop
deniedaccess_deniedstop — the user said no
expiredexpired_tokenrestart the flow
unknown / already redeemedinvalid_grantstop

denied being distinct from pending is what lets a device stop immediately instead of polling out the full ten minutes after a user has already refused — which is both a better experience and less load.
