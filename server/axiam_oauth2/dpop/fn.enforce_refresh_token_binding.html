Expand description

RFC 9449 §5 at the refresh grant (#681): a refresh token of a public DPoP-bound client is redeemed only with a proof by the key it is bound to.

bound is the stored token’s dpop_jkt; cnf is this request’s binding, as for refresh_token_binding. For every other client this is Ok and reads nothing. For such a client:

  • a token bound to the proof’s key is admitted, and its successor is bound to the same key (refresh_token_binding of the same cnf);
  • a token bound to another key is invalid_grant: a stolen token no longer refreshes under the thief’s key;
  • a token bound to no key is invalid_grant too. It was issued before v109, or while the client was confidential (an administrator’s PUT may since have made a device-only client public, #675) or not DPoP-bound. Binding it to whichever key presents it first would bind a stolen token to its thief, and the server cannot tell the two apart; the device signs in again instead, once.

§Errors

OAuth2Error::InvalidGrant in the two refusals above.
