G-C (#818) — what a refused refresh-token replay does besides refusing.

T-254 made every presentation of an already-rotated refresh token visible: marked on the session, audited as oauth2.refresh_token_replayed. It did not revoke anything. This module is where the token endpoint learns, per tenant, whether it now should: the tenant’s effective oauth2.refresh_reuse_response (the organization baseline merged with the tenant override), revoke_session unless somebody chose refuse.

§Why a port

For the reason crate::scope_ceiling::ExternalClientScopePolicy is one: the settings live in a repository TokenService has no type parameter for, and the composition root builds one value over the settings repository.

§Read only on the refusal path

The policy is asked only after a replay has been recognised and refused, so a grant that succeeds — every honest request — pays nothing for it.

§A read that fails, or no port at all, means the default

Unlike the scope ceiling, a failed read here does not refuse anything: the refusal has already been decided. It falls back to [RefreshReuseResponse::default], revoke_session, which is both the system default (D-N2) and the stricter of the two values — a datastore fault can make the endpoint revoke where a tenant asked it only to refuse, never the reverse. A service built without a port (default_policy) behaves the same way.
