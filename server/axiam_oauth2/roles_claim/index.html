SA-18 (N15, D-1) — the roles scope and the access token’s roles claim.

§Why the claim exists

Three SDKs implemented require_role by reading the OAuth2 scope claim, because the server issued nothing else that named a role. A scope is chosen by the client and bounded only by its registration; it says nothing about what the user holds. So a client registered for a scope named admin passed require_role("admin") for every user it signed in (N15).

D-1 settles the fix on both sides: the SDKs read only a dedicated roles claim and fail closed without it, and the server emits that claim — the names of the subject’s global roles in the token’s tenant — when, and only when, the grant carries the roles scope.

§The rules

  1. roles is an ordinary scope. A client obtains it only when it is in the client’s registered scopes (and, for an externally registered client, the tenant’s dcr_allowed_scopes), exactly as for any other scope. Nothing grants it by default. A service account, which registers no scopes, may ask for roles and for nothing else: it is a statement about the account’s own assignments, which is all its authority already is.
  2. Granted, the claim lists the names of the roles assigned to the subject with no resource — directly or through a group — in the token’s tenant, sorted and de-duplicated. An assignment scoped to a resource is not a tenant-wide role and is left out.
  3. Not granted, the claim is absent — never [] — so a consumer can tell “not requested” from “holds no roles”. A subject that holds none (or an OAuth2 client, which cannot hold roles) gets [].
  4. It is computed at mint time, by every grant that mints an access token: a refresh recomputes it, and a token exchange recomputes it only when roles survives the narrowing. ID tokens and UserInfo never carry it.

§A snapshot, not an authority

The claim is stale for at most one access-token lifetime: a role withdrawn after minting stays in the token until it expires. It is a coarse, cacheable hint for UI gating and require_role; the authoritative check is still the server’s require_access decision. docs/api/roles-claim.md says so to integrators.
