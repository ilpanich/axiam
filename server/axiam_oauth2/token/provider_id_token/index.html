G-A (W2.3) — native sign-in with a provider ID token. A child module, as the CIBA grant is, so that it issues through this module’s private machinery; re-exported at the crate root as crate::provider_id_token. G-A — native sign-in with a provider ID token: the grant (W2.3).

Design: claude_dev/social-login-gap-plan-2026-10-30.md §3.1, D-N1, D-N6. The rule the whole feature applies:

An ID token is accepted as a sign-in only when it was issued to us.

axiam-federation’s native_login decides whether a provider ID token proves a sign-in and who signed in (§3.1 steps 2–7). This module turns that answer into the client’s ordinary sign-in token set (step 8) and owns the gate in front of it (step 1). The token endpoint dispatches here and writes the audit record (step 9).

§The wire

POST /oauth2/token with grant_type=[PROVIDER_ID_TOKEN_GRANT_TYPE], provider (the federation provider’s UUID or provider_slug), id_token, nonce (the raw nonce the app generated; the provider’s SDK was given its SHA-256 hex, which is what the token carries — D-N16), optional scope and RFC 8707 resource, and the client’s usual authentication — a public (mobile) client sends client_id only.

§Why a vendor URN, and this one

The grant is AXIAM’s own: no IETF or OIDF registry defines “sign in with a third party’s ID token” as a grant, and RFC 8693 is the wrong shape (X4 refuses ID tokens by design; §3.1). RFC 6749 §4.5 extension grants are named by absolute URI, and the tree already has exactly one vendor grant URN, urn:axiam:params:oauth:grant-type:may-impersonate (crate::token_exchange::MAY_IMPERSONATE_GRANT). This one follows it segment for segment, so the two read as one family and no new namespace is opened. Nothing else in the tree, the SDK contract or the discovery document spells provider-id-token.

§Order, and what each step may write

  1. The client is read and authenticates by its registered method — a public client by presenting nothing, a confidential one by its credential (TokenService::authenticate_provider_id_token_client). The profile’s request-time rules run (fapi::enforce_token_request), the registration must list the grant (unauthorized_client otherwise), and the binding the registration asks for (cnf: DPoP, certificate) is decided — refused, not downgraded, when the request cannot satisfy it. The REST layer then applies the oauth2_provider_id_token bucket. Nothing has been written.
  2. The request: provider, id_token and nonce present; scope within the client’s registered set (after the external-client ceiling); resource one the client may address (TokenService::prepare_provider_id_token_grant). Still nothing written, so a malformed request does not spend the token.
  3. Steps 2–7 run in axiam-federation (the provider, the signature, the claims, the shape, the replay record, the user). Every refusal is one invalid_grant on the wire ([refusal_for]). The token endpoint then fires login.post_auth for the resolved user (CONTRACT §22, F4-W2-01) — the gate every interactive sign-in passes — and a veto is the same invalid_grant.
  4. Consent (D-N6): a scope that would need a consent ceremony is consent_required ([decide_consent]) — there is nobody to ask on this request, so it is answered as prompt=none is at /authorize.
  5. Issue (TokenService::issue_provider_id_token_grant): a session recording the federated authentication, the access token, a refresh token when the client holds refresh_token, and an ID token carrying the request’s nonce when openid was granted.

§The session, and what it records

A federated browser sign-in creates a session whose evidence is AuthenticationEvidence::upstream(auth_time, now, [fed]), and a code issued from it carries that session in sid and that evidence onward. The native sign-in records the same: one session row with the provider’s auth_time (clamped to now) and amr = [fed], no browser cookie, and a console refresh credential nobody is given. The access token names it in sid, so UserInfo and the session-validated API admit the token, ending the session (logout, password reset, an administrator’s revocation) ends the tokens, and the user’s session list shows the device. No claim is new.

“Ends the tokens” includes the refresh token (D-N39, #839): a single-session logout (AuthService::logout, behind /auth/logout, RP-initiated logout and SAML single logout) revokes every refresh token issued under the session, and the user-wide revocations revoke all of the user’s. The token endpoint records the client as a participant of the session it creates ([NativeSignIn::session_id]), so back-channel logout reaches a client that registered a backchannel_logout_uri.
