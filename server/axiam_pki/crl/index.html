Certificate revocation lists — one per issuing CA (RFC 5280 §5; #565, T-102).

Revoking a certificate sets the status on its row. Until this module that status reached exactly the places that read the row — device sign-in, and since the same change OAuth2 tls_client_auth — and nowhere else: a relying party that validates AXIAM-issued certificates itself, a FreeRADIUS server doing EAP-TLS or a VPN gateway, had no channel through which to learn of a revocation, although every AXIAM CA carries the cRLSign bit.

§What is published

A complete, version 2 CRL per issuing CA, DER-encoded, at GET /pki/v1/{org_id}/ca/{ca_id}/crl (crl_path), unauthenticated:

  • signed with the CA’s own key, fetched from the CA’s own custodian — the custodian the CA row names, through the same load the leaf path uses, so an RSA-4096 CA and an Ed25519 CA sign their lists exactly as they sign certificates;
  • thisUpdate the start of the refresh epoch it was signed in, or the newest revocation on it if later (#608, below); nextUpdate a configurable interval later (DEFAULT_CRL_NEXT_UPDATE_SECS) and never past the CA’s own notAfter;
  • a CRL number and an authority key identifier equal to the CA’s subject key identifier — the two extensions RFC 5280 §5.2 requires of every CRL;
  • an entry for every certificate the CA signed and revoked that has not expired, or expired during the previous refresh epoch or this one (so it appears on a list issued after its expiry, as RFC 5280 §3.3 asks): its leaves in every tenant, and the subordinate CAs it signed, so an organization CA’s list names a revoked tenant signing CA. Each entry carries the serial read out of the certificate and the date AXIAM recorded the revocation. No reason code: AXIAM does not record one, and RFC 5280 §5.3.1 prefers an absent reason to unspecified.

§Which CAs publish one

A CA AXIAM can sign with, while it is active and in date. Three kinds answer 404 instead, the same 404 as a CA that does not exist:

  • a revoked or expired CA. AXIAM signs nothing with one; its own status is on its parent’s list;
  • an imported trust anchor with no key (external custody): it cannot sign anything, a list included;
  • a CA whose key Vault’s PKI engine holds (vault_pki). Vault signs on AXIAM’s behalf only certificate requests; it has no operation that signs a list AXIAM composed, and AXIAM never holds the key. Vault publishes that CA’s list itself, and AXIAM revokes each leaf there too (crate::CertService::revoke, T-470), so Vault’s list names it. Leaves of such a CA carry no AXIAM distribution point — Vault issues them with its own profile, naming whatever the operator configured on the mount (config/urls) — so nothing points at a route that cannot answer, and relying parties read Vault’s list (/v1/<mount>/issuer/<issuer>/crl/der).

§Signing on request, and the cache in front of it

A list is signed when it is first asked for and kept, per CA, until either the set of revoked certificates changes or its refresh epoch ends; every request still reads the set, so a revocation is in the next response. Two things follow. A relying party revalidating with If-None-Match gets a 304 until the list really changes, because an unchanged list is the same bytes. And a flood of requests costs one database read each and no signature, which matters on an unauthenticated route whose custodian may be a Vault round trip away.

That read is light (#607): each revoked certificate’s fingerprint and the date its entry states, never the certificate. The PEMs — what an entry’s serial is read from — are read only when the list is actually signed.

Each CA is re-signed on its own (#607). One flight at a time re-signs a given CA’s list, through the custodian load, the crypto permit and the signature; requests for the same CA’s changed list wait for it, and nothing else does. A cached list is answered without waiting on any re-sign, this CA’s or another’s. The permit comes from the semaphore issuance and password hashing share, and a flight waits for one at most DEFAULT_CRL_PERMIT_WAIT; past that it fails with 503.

The flight’s outcome is shared (#616). A request that finds one in flight waits for it at most the same permit wait, then answers 503, and is handed what the flight ended with — its 503 included — instead of starting a re-sign of its own behind it. So callers queued on a saturated gate all answer within about one permit wait, not one wait each in turn, and an unauthenticated caller is never queued without bound. A waiter that read a later state than the flight signed (a revocation committed meanwhile) starts the next flight rather than take a list without it. A flight runs as a task of its own, so a caller hanging up does not abandon it: its list is cached for the next request.

§The same list from every replica (#608)

Time is cut into refresh epochs, half the nextUpdate interval long and aligned to the Unix epoch, so every replica cuts at the same instants. What a list says is a function of the revocations in the store and of the epoch alone — thisUpdate is the epoch’s start or the newest revocation date on the list, whichever is later, but never past the epoch’s last second, and the CRL number is that thisUpdate, in seconds, above the entry count. Both CA key types sign deterministically (Ed25519, and RSA PKCS#1 v1.5), so two replicas signing the same state in the same epoch produce the same bytes and the same ETag, and a relying party behind a load balancer revalidates to 304s wherever its request lands. A list served at the end of its epoch still has half its interval left.

§When the number only grows (#615)

RFC 5280 §5.2.3 asks for a CRL number that increases. The derivation gives one — list_identity argues each step — on two conditions, and the datastore’s clock is not among them:

  • The interval is unchanged. Epochs are cut from it, so another AXIAM__PKI__CRL_NEXT_UPDATE_SECS cuts other epochs: raising it moves the current epoch’s start back, and lowering it ends an expired entry’s stay sooner, while thisUpdate may stay put. Either can step the number back once. A relying party that keeps its list until nextUpdate and refuses a lower number is offered a greater one when it fetches again at nextUpdate as long as the new interval is at most twice every interval its list may have been signed under: lowering is safe once every replica runs the new value, and raising goes in steps of at most a doubling, an old interval apart. The PKI guide (docs/pki/README.md) gives the operator the procedure.
  • The replicas’ clocks agree within half an epoch. A replica whose clock has passed a boundary serves the new epoch’s list and one that has not still serves the old, so a relying party alternating between the two can see the previous epoch’s number again for as long as the clocks disagree — never an older epoch’s, and never at its own nextUpdate, by which time every such replica is past the boundary.

A revocation date is written by the datastore’s clock, which can be ahead of the signing replica’s and so lie past the end of the epoch. thisUpdate is clamped to the epoch’s last second and every entry’s stated date to thisUpdate, so no list states a time outside its epoch and the next epoch’s list, starting after every second of this one, has a greater number whatever left it (#615). What remains is that thisUpdate can be ahead of the replica’s clock — and a strict relying party’s — by as much as the datastore’s clock leads, never past the epoch’s end.

The route’s Cache-Control: max-age runs to the end of the epoch — at most half the interval — not to nextUpdate, so a shared cache revalidates with the ETag at least that often instead of serving a list from before a revocation until nextUpdate.

§The distribution point

CrlDistribution is the absolute URL of the route, built from the deployment’s public base URL. CertService and CaService write it into every certificate they sign in-process from then on — leaves on both paths, and subordinate CAs — so a relying party that follows distribution points finds the list without being told. With no public base URL there is no absolute URL to write, and the extension is omitted; the composition root says so at boot.

Constants§

CRL_MEDIA_TYPE
The media type a DER CRL is served as (RFC 5280 §4.2.1.13).
DEFAULT_CRL_NEXT_UPDATE_SECS
Default interval between a list’s thisUpdate and its nextUpdate: one day. Env: AXIAM__PKI__CRL_NEXT_UPDATE_SECS.
DEFAULT_CRL_PERMIT_WAIT
How long a re-sign waits for a permit of the shared crypto semaphore before the route answers 503 (#607): five seconds, the default wait of the password-hash gate the semaphore also serves. It also bounds how long a request waits on a re-sign of the same CA’s list already in flight (#616).
MAX_CRL_NEXT_UPDATE_SECS
Longest accepted interval: seven days. Past it the list stops being a revocation channel anybody should rely on.
MIN_CRL_NEXT_UPDATE_SECS
Shortest accepted interval: five minutes. Below it a relying party would spend more time fetching the list than trusting it.
