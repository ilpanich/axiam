Certificate serial numbers: how AXIAM mints one, and how it spells one it stores (#653).

§Why AXIAM sets the serial itself

Left unset, rcgen 0.14 writes the first 20 bytes of SHA-256 over the subject public key (rcgen-0.14.10/src/certificate.rs:458-472). The serial is then a function of the key alone, so two certificates one CA issues on the same key — a CSR signed twice, a re-issue on a retained key — carry the same serial. RFC 5280 §4.1.2.2 requires the serial to be unique per certificate the CA issues, and a CRL entry names a serial, so revoking one of the two revoked both on every relying party’s list.

[random_serial] is the one place a serial is minted. Every issuance that signs locally (a generated leaf, a CSR-signed leaf, a root CA, an intermediate CA) reads it. Certificates signed by Vault’s PKI engine carry the serial Vault chose, which is random in the same way.

§The stored spelling

certificate_serial_hex is lower-case hex of the serial’s big-endian magnitude, no separators, no sign byte — the bytes crl::list_identity puts in a CRL entry (cert.serial.to_bytes_be()), so a value in the database and an entry on the list for the same certificate are the same string once the list’s bytes are hex-encoded. (Vault’s own spelling, aa:bb:…, is crate::cert’s serial_hex; it is for Vault’s API and is not stored.)
