How long after its last write a rate_limit_bucket row is kept: twice RATE_LIMIT_BUCKET_LONGEST_WINDOW_SECS, plus RATE_LIMIT_BUCKET_CLOCK_MARGIN.

§Why no live limiter reads a row this old

A bucket row holds the count of one fixed window [s, s + W), W its writer’s window. A write lands at some u >= s: it is made while the window is open, and a write-behind flush of the window comes later still. A limiter reads a stored count in two places only:

  1. the window it belongs to, at a time t < s + W (the shared counters’ flush returns it, and the hint cap adds to it);
  2. the hint cap’s previous window, at t < s + 2W (the one later window that adds it to its own count).

From t >= s + 2W on, nothing reads the stored count as a count: an upsert for any later window finds window_start older than its own and starts from its delta, and a peek finds the same and answers 0 — both exactly what an absent row gives. So a row is dead once s + 2W has passed, and s <= u.

The sweep deletes a row only when updated_at (the datastore’s clock at the last write, u) is more than 2L + margin in the past of the datastore’s clock (time::now(), evaluated in the selection and in the DELETE, #676), L >= W being the longest window in use. The sweeping replica’s own clock takes no part in the comparison, so its offset from the datastore is not an input. A reader at t (its own clock) after the sweep has t >= u + 2L + margin - offset >= s + 2W as long as the offset between the reader’s clock and the datastore’s is under the margin. No row a limiter still reads is ever deleted.

If a reader’s clock were off by more than the margin, the cost is a count read as 0 for the rest of one window — the same thing a window boundary does. For the hint cap that is a stretch that may admit up to twice the allowance, so its “exactly” holds under the assumption that readers and the datastore agree to within the margin (T-424).

The table is bounded by what was written in the last RETENTION; the sweep makes the growth of a table that gained a row per hint, per client IP and per endpoint, forever, a steady state.
