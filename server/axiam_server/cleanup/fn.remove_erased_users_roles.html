Expand description

Step (b3)’s role pass (#758 (e)): unassign every direct role assignment of the erased account, and write one network_role.unassigned row (the axiam_authz::network_gate::AUDIT_ROLE_UNASSIGNED action) for each network role it removes.

A network role here is what the gate calls a network-sensitive role: one carrying at least one network: grant, allow or deny (axiam_core::models::network::is_network_action over the role’s permission grants, read before the unassignment). The row has the shape the REST gate writes for an administrator’s unassignment (role_id, role, grantee {kind, id}, node, permissions), tenant of the account, resource the node, actor the platform (System, nil id) — the erasure is the platform’s act, and the row says so. The grantee’s id is cleared again by pseudonymize_actor when the account is anonymized, so no row names the erased subject.

Each row is written after its unassignment landed, like the gate’s, and only when that unassignment is the one that removed the edge (#792): a re-entered erasure finds no assignment left and writes none, and of two units that both read one assignment (a stalled unit and its successor) one writes the row. A public free function, for the reason run_erasure_pipeline is.

Last, flush (when the deployment caches decisions) drops the account’s cached decisions, so a decision evaluated before the unassignments is not served, nor inserted behind them, until the TTL (#802, R112-09 (b)). It runs after the group memberships of step (b3), removed just before this pass, are gone too, and on a re-entered erasure as well: it is idempotent.

§Errors

The datastore error of a read or an unassignment (fail-closed: the purge retries). A failed audit append is dead-lettered, not returned.
