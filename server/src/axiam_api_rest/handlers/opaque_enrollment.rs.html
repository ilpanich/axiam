1//! Recording an OPAQUE registration record at the moments a plaintext password
2//! legitimately exists.
3//!
4//! There are exactly four such moments — user creation, an authenticated
5//! password change, password-reset completion, and first-run bootstrap — and
6//! this module is the one place that handles all of them, so the validation
7//! and the policy checks cannot drift between them.
8//!
9//! # Why enrolment has to be client-driven
10//!
11//! The server cannot compute a record. The envelope is sealed under a key
12//! derived from the password by way of the OPRF, and the whole point of OPAQUE
13//! is that the server never sees the password. So the client builds the record
14//! and posts it; the server's job is to check that what arrived is well-formed,
15//! meets the tenant's policy, and is attributed to the right account — never to
16//! trust the client about *whose* account it is. That is why [`OpaqueEnrollment`]
17//! carries no user id: the tenant and the user are taken from the authenticated
18//! server-side context, and the credential identifier from the sealed session
19//! the server itself minted.
20//!
21//! # Why a missing record is sometimes an error
22//!
23//! Under [`OpaqueMode::Required`] a password set without a record produces an
24//! account that cannot authenticate at all: password login is refused
25//! tenant-wide, and there is nothing for `/auth/opaque/login/start` to answer
26//! with. Accepting it silently would mean an admin creating a user, seeing
27//! `201`, and discovering only later that the account was born unusable. So it
28//! is rejected at the point of creation, where the message can say what to do
29//! about it.
30//!
31//! # What is *not* here any more
32//!
33//! The SRP version of this module had an `invalidate_on_rename` that
34//! `PUT /api/v1/users/{id}` called on every username change. SRP derived its
35//! private key over `username ":" password`, so a rename silently produced a
36//! verifier no client could satisfy — an entirely correct password reported as
37//! "invalid credentials", discovered at the worst possible moment. OPAQUE binds
38//! to a random server-chosen credential identifier that has no relationship to
39//! any name, so there is nothing to invalidate and the function is gone rather
40//! than ported.

56/// Validate a client-built registration record against tenant policy, without
57/// writing anything.
58///
59/// Split from [`store_credential`] on purpose. Every call site has to validate
60/// *before* it moves the password and store *after*, because doing both
61/// afterwards leaves a window in which the Argon2id hash has advanced while
62/// the OPAQUE record still answers to the old password — a user mid-migration
63/// could then log in with two different passwords depending on which endpoint
64/// they used. Making that ordering expressible is what the split is for.
65///
66/// A `None` enrolment is accepted under `disabled` and `optional`, and refused
67/// under `required`.
68pub(crate) fn validate_enrollment<C: Connection + Clone>(
69    state: &AppState<C>,
70    policy: &OpaquePolicy,
71    tenant_id: Uuid,
72    enrollment: Option<&OpaqueEnrollment>,
73) -> AxiamResult<Option<OpaqueEnrolled>> {
74    match (policy.opaque_mode, enrollment) {
75        // Nothing offered, nothing expected.
76        (OpaqueMode::Disabled, None) => Ok(None),
77
78        // A record for a tenant that does not do OPAQUE is refused rather than
79        // dropped on the floor: storing it would be dead weight, and silently
80        // discarding it would let a client believe OPAQUE is active when the
81        // very next login will be a password login.
82        (OpaqueMode::Disabled, Some(_)) => Err(AxiamError::Validation {
83            message: "OPAQUE is not enabled for this tenant".into(),
84        }),
85
86        // The migration state: clients that can do OPAQUE enrol, clients that
87        // cannot keep working.
88        (OpaqueMode::Optional, None) => Ok(None),
89
90        (OpaqueMode::Required, None) => Err(AxiamError::Validation {
91            message: "this tenant requires OPAQUE: the request must include an \
92                      `opaque` registration record, or the account will be unable \
93                      to authenticate"
94                .into(),
95        }),
96
97        (OpaqueMode::Optional | OpaqueMode::Required, Some(enrollment)) => {
98            let opaque = opaque_server(state).map_err(|e| e.0)?;
99
100            // Opening the sealed session is what binds the record to a
101            // credential identifier the *server* chose, and to the suite and
102            // KSF parameters it dictated. A client cannot substitute any of
103            // them, because it never held them in the clear.
104            let enrolled = opaque
105                .register_finish(&enrollment.opaque_session, &enrollment.registration_record)
106                .map_err(AxiamError::from)?;
107
108            // The session is tenant-scoped, and the caller's tenant comes from
109            // its own authenticated context. A mismatch means a session minted
110            // for one tenant is being redeemed against another.
111            if enrolled.tenant_id != tenant_id {
112                return Err(AxiamError::Validation {
113                    message: "the OPAQUE session was issued for a different tenant".into(),
114                });
115            }
116
117            // Policy is a floor, not an exact match. A client that enrols with
118            // a *stronger* suite or KSF than the tenant asks for is doing
119            // nothing wrong, and refusing it would block a client that had
120            // already moved ahead of a tenant's configuration.
121            //
122            // In practice both values came from the server's own
123            // register/start response, so this can only fire if the tenant's
124            // policy was tightened in the seconds between the two calls. It is
125            // kept because "the server told the client what to use" is an
126            // invariant worth enforcing rather than assuming.
127            if !opaque_suite_is_at_least(enrolled.suite, policy.opaque_suite) {
128                return Err(AxiamError::Validation {
129                    message: format!(
130                        "opaque suite {} is weaker than the tenant minimum {}",
131                        enrolled.suite, policy.opaque_suite
132                    ),
133                });
134            }
135            if !opaque_ksf_is_at_least(enrolled.ksf_params.ksf(), policy.opaque_ksf) {
136                return Err(AxiamError::Validation {
137                    message: format!(
138                        "opaque ksf {} is weaker than the tenant minimum {}",
139                        enrolled.ksf_params.ksf(),
140                        policy.opaque_ksf
141                    ),
142                });
143            }
144
145            Ok(Some(enrolled))
146        }
147    }
148}

150/// Persist a validated record against `user_id`.
151///
152/// `None` is a no-op, which is what the `disabled` and `optional`-without-a-
153/// record cases resolve to.
154pub(crate) async fn store_credential<C: Connection + Clone>(
155    state: &AppState<C>,
156    tenant_id: Uuid,
157    user_id: Uuid,
158    enrolled: Option<OpaqueEnrolled>,
159) -> AxiamResult<()> {
160    let Some(enrolled) = enrolled else {
161        return Ok(());
162    };
163    state
164        .opaque_credential_repo
165        .upsert(CreateOpaqueCredential {
166            tenant_id,
167            user_id,
168            credential_identifier: enrolled.credential_identifier,
169            suite: enrolled.suite,
170            ksf_params: enrolled.ksf_params,
171            record: enrolled.record,
172        })
173        .await?;
174    Ok(())
175}
