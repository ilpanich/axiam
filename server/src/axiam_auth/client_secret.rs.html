1//! Client-secret hashing (OBS-1).
2//!
3//! # What this replaces
4//!
5//! Until OBS-1 was remediated, OAuth2 client secrets and service-account
6//! secrets were stored as an **unsalted, single-round SHA-256** digest. That
7//! was safe *only* because every secret is 32 CSPRNG bytes produced by the
8//! repository itself, with no operator-supplied path — an assumption held by
9//! nothing stronger than a code comment. This module removes the dependence on
10//! secret entropy: a stored hash is now a **keyed** HMAC-SHA256 tag, so an
11//! attacker holding a dump of the `oauth2_client` / `service_account` tables
12//! cannot mount an offline guessing attack at all without also holding the
13//! server pepper.
14//!
15//! HMAC-SHA256 (rather than Argon2id) is deliberate. The client-credentials
16//! grant is a machine-to-machine hot path measured at 2 727 req/s precisely
17//! because it is *not* KDF-bound; the threat a KDF defends against — offline
18//! brute force of a low-entropy secret — is already excluded by the 256-bit
19//! CSPRNG secrets, and is now additionally excluded by the key. If a
20//! caller-chosen client secret is ever accepted, revisit this: that is the
21//! trigger condition OBS-1 recorded, and it would call for a salted KDF.
22//!
23//! # On-disk representation
24//!
25//! Two schemes coexist during migration. The scheme is identified by the
26//! stored string itself, so no schema change and no backfill are required:
27//!
28//! | Scheme | Stored form | Length |
29//! |---|---|---|
30//! | v1 (legacy) | `<64 lowercase hex>` — bare `SHA-256(secret)` | 64 |
31//! | v2 (current) | `v2.hs256$<64 lowercase hex>` — `HMAC-SHA256(k, secret)` | 73 |
32//!
33//! v1 hashes **cannot be re-derived** offline — only the digest was ever
34//! stored, never the secret — so migration is necessarily lazy:
35//! [`ClientSecretHasher::verify`] returns
36//! [`ClientSecretVerdict::MatchNeedsUpgrade`] carrying the v2 replacement, and
37//! the caller persists it with a compare-and-swap. The upgrade is produced
38//! **only on a successful verification**; a failed verification never rehashes
39//! and never writes.
40//!
41//! # Keying
42//!
43//! The HMAC key is derived once, at construction, from the configured server
44//! pepper (`AXIAM__AUTH__PEPPER`) with a domain-separation label:
45//!
46//! ```text
47//! k = HMAC-SHA256(pepper, "axiam.client-secret.v2")
48//! ```
49//!
50//! The label keeps this key independent of the pepper's other use (Argon2id
51//! password peppering), so the two never share key material directly.
52//!
53//! ## Pepper rotation (§13.4 observation 3)
54//!
55//! The `v2.hs256$` tag versions the **algorithm**, not the **key**. Rotating
56//! `AXIAM__AUTH__PEPPER` therefore used to be an unversioned hard break: every
57//! stored hash became unverifiable at once, so every service account and OAuth2
58//! client had to be re-issued in lockstep with the restart. The AMQP path
59//! carries a `key_version` on the wire for exactly this reason.
60//!
61//! Set `AXIAM__AUTH__PEPPER_PREVIOUS` to the outgoing value for the duration of
62//! a rotation. Verification then tries the current key and, failing that, the
63//! previous one; a match under the previous key returns
64//! [`ClientSecretVerdict::MatchNeedsUpgrade`] carrying the hash under the
65//! *current* key, so each secret is rewritten the first time its owner
66//! authenticates and the rotation drains itself. Nothing is ever *written*
67//! under the previous key. Unset it once the fleet has drained.
68//!
69//! **Why not a stored key id.** The obvious alternative — derive a kid from the
70//! pepper and store it beside the hash — would hand anyone holding a table dump
71//! an offline oracle for testing pepper guesses directly, which does not exist
72//! today (testing a guess currently requires a known secret/hash pair). Trying
73//! both keys costs one extra HMAC on rotation-era rows and adds no new verifier
74//! for an attacker. Both candidates are computed unconditionally while a
75//! rotation is configured, so the response time does not reveal which pepper era
76//! a row is in.
77//!
78//! # Fail-closed posture
79//!
80//! The pepper is **mandatory** for client-secret hashing. There is no
81//! bare-SHA-256 fallback: a missing pepper is a hard error, exactly like the
82//! mandatory AMQP master signing key (SECHRD-08 / D-05c). Matching that
83//! precedent, a *debug* build falls back to a documented dev-only pepper so
84//! local runs and tests work without extra setup; a *release* build — the
85//! production container image — fails closed with
86//! [`AxiamError::ServiceUnavailable`].

101/// Domain-separation label mixed into the pepper to derive the v2 HMAC key.
102/// Changing this string invalidates every stored v2 hash — treat it as part
103/// of the on-disk format.
104const KEY_DERIVATION_LABEL: &[u8] = b"axiam.client-secret.v2";
105
106/// Scheme marker for the current (v2) client-secret hash format.
107///
108/// Present verbatim at the start of every v2 hash and included in the
109/// constant-time comparison, so the version tag itself is never compared with
110/// an early-exiting `==`.
111pub const V2_PREFIX: &str = "v2.hs256$";
112
113/// Length of a legacy (v1) stored hash: 64 lowercase hex chars of SHA-256.
114pub const V1_HASH_LEN: usize = 64;
115
116/// Length of a v2 stored hash: [`V2_PREFIX`] plus 64 lowercase hex chars.
117pub const V2_HASH_LEN: usize = V2_PREFIX.len() + 64;
118
119/// Documented dev/test-only pepper, used **only** in debug builds
120/// (`cfg!(debug_assertions)` — i.e. never in the `cargo build --release`
121/// binary that ships in the production container image, see
122/// `docker/Dockerfile.server`) when `AXIAM__AUTH__PEPPER` is unset, so local
123/// dev/test runs work without extra setup. This value MUST NOT be used in
124/// production — [`ClientSecretHasher::from_auth_config`] fails closed rather
125/// than falling back to it in a release build.
126const DEV_DEFAULT_PEPPER: &[u8] = b"axiam-dev-only-client-secret-pepper-DO-NOT-USE-IN-PROD";
127
128/// A pepper shorter than this is accepted but warned about at construction.
129const WEAK_PEPPER_LEN: usize = 16;
130
131/// Outcome of verifying a presented client secret against a stored hash.
132///
133/// Deliberately not a `bool`: the migration obligation is part of the result,
134/// so a caller cannot verify a legacy row without being handed — and having to
135/// look at — the replacement hash.
136#[derive(Debug, Clone, PartialEq, Eq)]
137pub enum ClientSecretVerdict {
138    /// The secret matched and the stored hash is already in the current
139    /// scheme. Nothing to persist.
140    Match,
141    /// The secret matched a **legacy (v1)** stored hash. The caller SHOULD
142    /// persist `upgraded_hash` (compare-and-swap against the hash it read) to
143    /// migrate the row. Authentication has already succeeded — a failure to
144    /// persist must be logged, not turned into an auth failure.
145    MatchNeedsUpgrade { upgraded_hash: String },
146    /// The secret did not match. Never rehash, never write.
147    Mismatch,
148}
149
150impl ClientSecretVerdict {
151    /// `true` for both matching variants.
152    #[inline]
153    pub fn is_match(&self) -> bool {
154        !matches!(self, ClientSecretVerdict::Mismatch)
155    }
156}

158/// Keyed hasher for client secrets. Construct once per process (see
159/// [`install_from_config`]) — construction derives the HMAC key, hashing does
160/// not.
161#[derive(Clone)]
162pub struct ClientSecretHasher {
163    key: [u8; 32],
164    /// Key derived from the **previous** pepper, for verify only (§13.4
165    /// observation 3). `None` when no rotation is in progress.
166    ///
167    /// Never used to *produce* a hash — [`ClientSecretHasher::hash`] always
168    /// writes under the current key — so a row that verifies under the previous
169    /// pepper is handed back as
170    /// [`ClientSecretVerdict::MatchNeedsUpgrade`] and migrates forward through
171    /// the same compare-and-swap the v1→v2 migration already uses.
172    previous_key: Option<[u8; 32]>,
173}
174
175impl std::fmt::Debug for ClientSecretHasher {
176    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
177        f.write_str("ClientSecretHasher(<redacted>)")
178    }
179}

181impl Drop for ClientSecretHasher {
182    fn drop(&mut self) {
183        self.key.zeroize();
184        if let Some(previous) = &mut self.previous_key {
185            previous.zeroize();
186        }
187    }
188}

190impl ClientSecretHasher {
191    /// Derive a hasher from raw pepper bytes.
192    ///
193    /// Prefer [`ClientSecretHasher::from_auth_config`]; this exists for tests
194    /// and for callers that hold the pepper outside `AuthConfig`.
195    pub fn from_pepper(pepper: &[u8]) -> Result<Self, AxiamError> {
196        if pepper.is_empty() {
197            return Err(AxiamError::ServiceUnavailable(
198                "client-secret pepper is empty (AXIAM__AUTH__PEPPER) — client-secret hashing is \
199                 keyed and has no unkeyed fallback (OBS-1)"
200                    .to_string(),
201            ));
202        }
203        if pepper.len() < WEAK_PEPPER_LEN {
204            tracing::warn!(
205                pepper_len = pepper.len(),
206                "AXIAM__AUTH__PEPPER is shorter than {WEAK_PEPPER_LEN} bytes — use at least 32 \
207                 bytes of CSPRNG output"
208            );
209        }
210        Ok(Self {
211            key: Self::derive_key(pepper),
212            previous_key: None,
213        })
214    }
215
216    /// Attach a **previous** pepper, so hashes written before a rotation still
217    /// verify (§13.4 observation 3).
218    ///
219    /// Rotating `AXIAM__AUTH__PEPPER` used to be an unversioned hard break: the
220    /// `v2.hs256$` tag versions the *algorithm*, not the *key*, so there was no
221    /// dual read and a rotation permanently invalidated **every** client secret
222    /// — every service account and OAuth2 client had to be re-issued in
223    /// lockstep with the restart. The AMQP path carries a `key_version` on the
224    /// wire for exactly this reason.
225    ///
226    /// A stored kid was deliberately **not** added instead. Deriving a key id
227    /// from the pepper and writing it beside the hash would let anyone holding a
228    /// table dump test pepper guesses directly against that tag — an offline
229    /// oracle that does not exist today, because testing a pepper guess
230    /// currently requires a known (secret, hash) pair. Trying both keys costs
231    /// one extra HMAC on the rare rotation-era row and introduces no new
232    /// verifier for an attacker.
233    pub fn with_previous_pepper(mut self, pepper: &[u8]) -> Result<Self, AxiamError> {
234        if pepper.is_empty() {
235            return Err(AxiamError::ServiceUnavailable(
236                "previous client-secret pepper is empty (AXIAM__AUTH__PEPPER_PREVIOUS) — unset it \
237                 entirely to disable dual-read rather than setting it to an empty value"
238                    .to_string(),
239            ));
240        }
241        if pepper.len() < WEAK_PEPPER_LEN {
242            // §15.3.7: `from_pepper` warns on a weak pepper and this path did
243            // not. The impact is genuinely lower — a previous key can only
244            // verify hashes that already exist, never produce one — but an
245            // operator rotating *away* from a weak pepper is exactly who should
246            // be told it was weak, and silence here reads as approval.
247            tracing::warn!(
248                pepper_len = pepper.len(),
249                "AXIAM__AUTH__PEPPER_PREVIOUS is shorter than {WEAK_PEPPER_LEN} bytes. Secrets                  still hashed under it are weakly keyed until they are rewritten under the                  current pepper; complete the rotation promptly."
250            );
251        }
252        self.previous_key = Some(Self::derive_key(pepper));
253        Ok(self)
254    }
255
256    fn derive_key(pepper: &[u8]) -> [u8; 32] {
257        let mut mac = <HmacSha256 as hmac::KeyInit>::new_from_slice(pepper)
258            .expect("HMAC-SHA256 accepts a key of any length");
259        mac.update(KEY_DERIVATION_LABEL);
260        let mut key = [0u8; 32];
261        key.copy_from_slice(&mac.finalize().into_bytes());
262        key
263    }
264
265    /// Resolve a hasher from the authentication configuration, failing closed
266    /// when no pepper is configured.
267    ///
268    /// - pepper set → derive the key from it;
269    /// - pepper unset in a **debug** build → the documented
270    ///   [`DEV_DEFAULT_PEPPER`], with a `warn!`;
271    /// - pepper unset in a **release** build → `ServiceUnavailable`.
272    ///
273    /// There is deliberately no "degrade to unkeyed SHA-256" branch: silently
274    /// weakening the control when unconfigured is the exact failure mode OBS-1
275    /// objected to.
276    pub fn from_auth_config(config: &AuthConfig) -> Result<Self, AxiamError> {
277        let hasher = Self::resolve(
278            config.pepper.as_ref().map(|p| p.expose_secret()),
279            cfg!(debug_assertions),
280        )?;
281
282        // §13.4 observation 3: attach the outgoing pepper, if a rotation is in
283        // progress, so pre-rotation hashes still verify and migrate forward.
284        match config.pepper_previous.as_ref().map(|p| p.expose_secret()) {
285            Some(previous) if !previous.is_empty() => {
286                tracing::info!(
287                    "AXIAM__AUTH__PEPPER_PREVIOUS is set — client-secret verification will \
288                     dual-read during the rotation, rewriting each secret under the current \
289                     pepper as its owner authenticates. Unset it once the fleet has drained."
290                );
291                hasher.with_previous_pepper(previous.as_bytes())
292            }
293            _ => Ok(hasher),
294        }
295    }
296
297    /// Core resolution, with the debug-build fallback lifted into a parameter
298    /// so both branches are testable from a single (debug) test binary.
299    fn resolve(pepper: Option<&str>, allow_dev_default: bool) -> Result<Self, AxiamError> {
300        match pepper {
301            Some(p) if !p.is_empty() => Self::from_pepper(p.as_bytes()),
302            _ if allow_dev_default => {
303                tracing::warn!(
304                    "AXIAM__AUTH__PEPPER not set — using the dev-only default client-secret \
305                     pepper (NOT valid in a release/production build, OBS-1)"
306                );
307                Self::from_pepper(DEV_DEFAULT_PEPPER)
308            }
309            _ => Err(AxiamError::ServiceUnavailable(
310                "client-secret pepper not configured (AXIAM__AUTH__PEPPER) — mandatory in \
311                 production; client-secret hashing is keyed HMAC-SHA256 with no unkeyed \
312                 fallback (OBS-1)"
313                    .to_string(),
314            )),
315        }
316    }

318    /// Hash `secret` in the current (v2) scheme. The returned string is what
319    /// goes in `client_secret_hash`.
320    pub fn hash(&self, secret: &str) -> String {
321        let mut buf = [0u8; V2_HASH_LEN];
322        self.hash_into(secret, &mut buf);
323        // `hash_into` writes only ASCII (the prefix plus lowercase hex).
324        String::from_utf8(buf.to_vec()).expect("v2 hash encoding is ASCII by construction")
325    }
326
327    /// Write the v2 encoding of `secret` into a caller-owned stack buffer.
328    ///
329    /// Allocation-free: `Hmac<Sha256>` keeps its state inline and
330    /// `hex::encode_to_slice` writes in place. This is what keeps the
331    /// client-credentials hot path free of the per-request `String` the old
332    /// `hash_client_secret` allocated.
333    fn hash_into(&self, secret: &str, out: &mut [u8; V2_HASH_LEN]) {
334        self.hash_into_with(&self.key, secret, out);
335    }
336
337    /// [`Self::hash_into`] under an explicit key, so the rotation dual-read can
338    /// reuse the exact same encoding rather than reimplementing it.
339    fn hash_into_with(&self, key: &[u8; 32], secret: &str, out: &mut [u8; V2_HASH_LEN]) {
340        let mut mac = <HmacSha256 as hmac::KeyInit>::new_from_slice(key)
341            .expect("HMAC-SHA256 accepts a 32-byte key");
342        mac.update(secret.as_bytes());
343        let tag = mac.finalize().into_bytes();
344        out[..V2_PREFIX.len()].copy_from_slice(V2_PREFIX.as_bytes());
345        hex::encode_to_slice(tag, &mut out[V2_PREFIX.len()..])
346            .expect("64-byte tail holds exactly one hex-encoded 32-byte tag");
347    }
348
349    /// Verify `presented` against a `stored` hash in either scheme.
350    ///
351    /// Constant-time throughout: in both branches the candidate is fully
352    /// computed and compared with [`ConstantTimeEq`] over the **entire** stored
353    /// string, scheme marker included — there is no early `==` on the version
354    /// tag and no short-circuit on a prefix mismatch. A `stored` value that is
355    /// neither scheme (including the empty string used for public clients)
356    /// falls through to a length-mismatched comparison and yields
357    /// [`ClientSecretVerdict::Mismatch`] — fail closed.
358    ///
359    /// Which *branch* is taken is a function of the stored row only, never of
360    /// the presented secret, so the (sub-microsecond) cost difference between
361    /// SHA-256 and HMAC-SHA256 cannot be used as a secret oracle. It reveals
362    /// at most which scheme a row is already stored in — not secret material,
363    /// and observable from the migration itself.
364    pub fn verify(&self, presented: &str, stored: &str) -> ClientSecretVerdict {
365        if stored.len() == V1_HASH_LEN {
366            // Legacy (v1): unsalted single-round SHA-256 (OBS-1).
367            let mut candidate = [0u8; V1_HASH_LEN];
368            legacy_v1_into(presented, &mut candidate);
369            let matched = bool::from(candidate[..].ct_eq(stored.as_bytes()));
370            candidate.zeroize();
371            if matched {
372                // Rehash ONLY after a successful verification.
373                ClientSecretVerdict::MatchNeedsUpgrade {
374                    upgraded_hash: self.hash(presented),
375                }
376            } else {
377                ClientSecretVerdict::Mismatch
378            }
379        } else {
380            let mut candidate = [0u8; V2_HASH_LEN];
381            self.hash_into_with(&self.key, presented, &mut candidate);
382            let matched = candidate[..].ct_eq(stored.as_bytes());
383            candidate.zeroize();
384
385            // §13.4 observation 3 — rotation dual-read. Both candidates are
386            // computed and compared unconditionally whenever a previous pepper
387            // is configured: branching on the current key's result would make
388            // the response time reveal which pepper era a row is in.
389            let matched_previous = match &self.previous_key {
390                Some(previous) => {
391                    let mut candidate = [0u8; V2_HASH_LEN];
392                    self.hash_into_with(previous, presented, &mut candidate);
393                    let m = candidate[..].ct_eq(stored.as_bytes());
394                    candidate.zeroize();
395                    m
396                }
397                None => subtle::Choice::from(0u8),
398            };
399
400            if bool::from(matched) {
401                ClientSecretVerdict::Match
402            } else if bool::from(matched_previous) {
403                // Verified under the OLD pepper. Authentication succeeds and the
404                // row is handed back for migration under the current one — the
405                // same lazy compare-and-swap the v1→v2 path uses, so a rotation
406                // drains itself as clients authenticate instead of invalidating
407                // every secret at once.
408                ClientSecretVerdict::MatchNeedsUpgrade {
409                    upgraded_hash: self.hash(presented),
410                }
411            } else {
412                ClientSecretVerdict::Mismatch
413            }
414        }
415    }
416}

418/// Legacy (v1) hash: unsalted, single-round SHA-256, hex-encoded.
419///
420/// Retained **only** so pre-OBS-1 rows still authenticate while they migrate.
421/// It is never produced for new or rotated secrets. Once an operator can show
422/// no v1 rows remain (`client_secret_hash` of length 64), this and the v1 arm
423/// of [`ClientSecretHasher::verify`] can be deleted.
424fn legacy_v1_into(secret: &str, out: &mut [u8; V1_HASH_LEN]) {
425    use sha2::Digest;
426    let digest = Sha256::digest(secret.as_bytes());
427    hex::encode_to_slice(digest, out).expect("64-byte buffer holds one hex-encoded 32-byte digest");
428}

436/// Install the process-wide client-secret hasher from configuration.
437///
438/// Call once during startup, **before** the server begins accepting requests,
439/// so a missing pepper is a startup failure rather than a first-request
440/// failure. Returns the installed hasher.
441///
442/// Repositories (`create`, `rotate_secret`) and the OAuth2 token service all
443/// read this single instance, which is what guarantees that creation, rotation
444/// and verification cannot disagree about the key.
445///
446/// If a hasher is already installed the existing one is returned unchanged —
447/// installation is first-write-wins, never a silent re-key.
448pub fn install_from_config(config: &AuthConfig) -> Result<&'static ClientSecretHasher, AxiamError> {
449    let hasher = ClientSecretHasher::from_auth_config(config)?;
450    Ok(GLOBAL_HASHER.get_or_init(|| hasher))
451}
452
453/// Resolve the process-wide client-secret hasher.
454///
455/// Lock-free and allocation-free (`OnceLock::get` is a single acquire load),
456/// so this is safe to call on the client-credentials hot path.
457///
458/// If nothing was installed: a **debug** build lazily installs the documented
459/// dev-only pepper (so unit and integration tests need no wiring); a
460/// **release** build fails closed.
461pub fn global() -> Result<&'static ClientSecretHasher, AxiamError> {
462    if let Some(h) = GLOBAL_HASHER.get() {
463        return Ok(h);
464    }
465    let hasher = ClientSecretHasher::resolve(None, cfg!(debug_assertions))?;
466    Ok(GLOBAL_HASHER.get_or_init(|| hasher))
467}

645    // -----------------------------------------------------------------
646    // Pepper rotation dual-read (§13.4 observation 3)
647    // -----------------------------------------------------------------
648
649    const OLD_PEPPER: &[u8] = b"outgoing-pepper-0123456789abcdef";
650    const NEW_PEPPER: &[u8] = b"incoming-pepper-fedcba9876543210";
651
652    /// The defect: rotating the pepper permanently invalidated every stored
653    /// client secret, because the `v2.hs256$` tag versions the algorithm, not
654    /// the key. Without a dual read there is no path back.
655    #[test]
656    fn rotating_the_pepper_without_a_dual_read_invalidates_every_secret() {
657        let old = ClientSecretHasher::from_pepper(OLD_PEPPER).unwrap();
658        let stored = old.hash("s3cret");
659
660        let new_only = ClientSecretHasher::from_pepper(NEW_PEPPER).unwrap();
661        assert_eq!(
662            new_only.verify("s3cret", &stored),
663            ClientSecretVerdict::Mismatch,
664            "this is the hard break the observation describes — pinned so the \
665             dual-read test below cannot pass vacuously"
666        );
667    }
668
669    /// With the outgoing pepper attached, a pre-rotation secret still verifies
670    /// and is handed back for rewriting under the current pepper.
671    #[test]
672    fn a_pre_rotation_secret_verifies_and_migrates_forward() {
673        let old = ClientSecretHasher::from_pepper(OLD_PEPPER).unwrap();
674        let stored = old.hash("s3cret");
675
676        let rotating = ClientSecretHasher::from_pepper(NEW_PEPPER)
677            .unwrap()
678            .with_previous_pepper(OLD_PEPPER)
679            .unwrap();
680
681        match rotating.verify("s3cret", &stored) {
682            ClientSecretVerdict::MatchNeedsUpgrade { upgraded_hash } => {
683                let new_only = ClientSecretHasher::from_pepper(NEW_PEPPER).unwrap();
684                assert_eq!(
685                    new_only.verify("s3cret", &upgraded_hash),
686                    ClientSecretVerdict::Match,
687                    "the replacement must be written under the CURRENT pepper, so \
688                     the row stops depending on the outgoing one"
689                );
690                assert_ne!(upgraded_hash, stored);
691            }
692            other => panic!("expected MatchNeedsUpgrade, got {other:?}"),
693        }
694    }
