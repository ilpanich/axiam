1//! Where an organization's CA signing keys are kept.
2//!
3//! A **port**, like [`crate::secrets`], and for a related reason — but a
4//! different shape, and the difference is the point of having two.
5//!
6//! [`crate::secrets::SecretProvider`] serves a fixed set of process-wide keys,
7//! resolved once during composition and answered from memory thereafter. That
8//! works because those keys are known at startup and never change.
9//!
10//! CA signing keys are neither. There is one per CA certificate, they are
11//! created while the process is running, and there is no bound on how many an
12//! organization has. So this port is asynchronous, addressed by key reference,
13//! and read on the path that issues a certificate.
14//!
15//! # Why this exists at all
16//!
17//! Until this port, a CA private key was AES-256-GCM ciphertext in a
18//! `ca_certificate` row, sealed under one process-wide `pki_encryption_key`.
19//! That is a real control and it stays available, but it puts the key and the
20//! thing that unlocks it inside the same blast radius: whoever reads the
21//! database and the environment of one process holds every CA in the
22//! deployment, and nothing anywhere records that they used it.
23//!
24//! A key held in Vault (and later a KMS) is a different proposition. Access is
25//! a policy that can be scoped and revoked, every read is audited by something
26//! that is not AXIAM, and a database dump on its own is inert.
27//!
28//! # Custody, and the stronger thing beyond it
29//!
30//! Most implementations hand back a private key PEM, which means the key does
31//! reach AXIAM's memory to sign with. That is *custody*: the key is somewhere
32//! better than a database column, and reading it is an audited, revocable act
33//! — but AXIAM still reads it.
34//!
35//! One implementation does not. Vault's PKI secrets engine generates the key
36//! inside itself and exposes no API that exports it, so a
37//! [`CaKeyCustody::VaultPki`] CA answers [`CaKeyStore::load`] with a refusal
38//! and answers [`CaKeyStore::sign_csr`] instead. Designing the port around a
39//! key *reference* rather than a key is what left room for that, and the three
40//! capability questions below — [`CaKeyStore::generates_cas`],
41//! [`CaKeyStore::signs_remotely`] — are how a caller finds out which kind of
42//! custodian it is holding without knowing the concrete type.
43//!
44//! The default bodies are the whole point of those methods being on this trait
45//! rather than a second one: a custodian that holds keys the ordinary way
46//! implements none of them and behaves exactly as it did before.
47//!
48//! Nothing here decides *which* custodian a deployment uses. The composition
49//! root picks one and the CA row records which answered, so a deployment that
50//! adopts Vault does not strand the CAs it created before.

62/// Which custodian holds a CA's private key.
63///
64/// Recorded per CA rather than inferred from configuration, because the two
65/// diverge the moment an operator changes custodian: CAs created before the
66/// change are still where they were, and a lookup that consulted only the
67/// current setting would fail to find them — or, worse, look in the right place
68/// and get a different key.
69#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize, utoipa::ToSchema)]
70#[serde(rename_all = "snake_case")]
71pub enum CaKeyCustody {
72    /// AES-256-GCM ciphertext in the `ca_certificate` row itself, sealed under
73    /// the process-wide `pki_encryption_key`. The original arrangement, and
74    /// still the default for a deployment that has configured no custodian.
75    Database,
76    /// A HashiCorp Vault KV v2 secret. The row holds the path and no key
77    /// material at all.
78    Vault,
79    /// A HashiCorp Vault **PKI secrets engine** issuer. The key is generated
80    /// inside Vault by `root/generate/internal` and
81    /// `intermediate/generate/internal`, and there is no API that exports it —
82    /// so unlike every other variant here, AXIAM never holds this key at all.
83    ///
84    /// Signing therefore moves to Vault too: the leaf key is generated here, a
85    /// CSR goes to `sign-verbatim`, and a certificate comes back. That is the
86    /// difference between *custody* and the stronger property this module's
87    /// header describes, and it is the reason the port is addressed by key
88    /// reference rather than by key.
89    VaultPki,
90    /// No private key is held by AXIAM. An imported CA whose key stays with
91    /// whoever generated it: the certificate is a trust anchor here and
92    /// AXIAM cannot issue against it.
93    External,
94}
95
96impl std::fmt::Display for CaKeyCustody {
97    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
98        match self {
99            Self::Database => write!(f, "database"),
100            Self::Vault => write!(f, "vault"),
101            Self::VaultPki => write!(f, "vault_pki"),
102            Self::External => write!(f, "external"),
103        }
104    }
105}

107impl std::str::FromStr for CaKeyCustody {
108    type Err = String;
109
110    fn from_str(s: &str) -> Result<Self, Self::Err> {
111        match s {
112            "database" => Ok(Self::Database),
113            "vault" => Ok(Self::Vault),
114            "vault_pki" => Ok(Self::VaultPki),
115            "external" => Ok(Self::External),
116            other => Err(format!("unknown CA key custody: {other}")),
117        }
118    }
119}

121/// Everything needed to find one CA's private key again.
122///
123/// Carries the custodian as well as the locator, so a caller holding one of
124/// these does not have to consult configuration to know how to read it — which
125/// is what makes a mixed deployment work.
126#[derive(Debug, Clone, PartialEq, Eq)]
127pub struct CaKeyRef {
128    pub organization_id: Uuid,
129    pub ca_id: Uuid,
130    pub custody: CaKeyCustody,
131    /// Where the custodian put it. A Vault path; empty for `Database`, whose
132    /// locator is the row itself.
133    pub locator: String,
134}
135
136/// What a [`CaKeyStore::store`] call produced.
137///
138/// Two variants because the database custodian's "locator" *is* the material:
139/// it hands back ciphertext for the caller to write into the CA row, where
140/// every other custodian hands back a path and keeps the material itself.
141#[derive(Debug, Clone)]
142pub enum StoredCaKey {
143    /// Ciphertext the caller must persist in the CA row.
144    Inline(Vec<u8>),
145    /// The key is with the custodian; this is where.
146    Referenced(String),
147}
148
149/// What a caller asks a key-generating custodian to create.
150///
151/// Only [`CaKeyCustody::VaultPki`] answers this today. Every field is a
152/// *request*: the row that ends up describing the CA is parsed back out of the
153/// certificate the custodian returns, because Vault caps a TTL to the mount's
154/// `max_lease_ttl` and to the signing root's own expiry without failing the
155/// call. A row built from the request would then claim a validity window the
156/// certificate does not have.
157#[derive(Debug, Clone)]
158pub struct CaGenerationRequest {
159    pub organization_id: Uuid,
160    /// The id the CA row will have. Chosen before the call so the custodian can
161    /// name what it creates after the CA that owns it.
162    pub ca_id: Uuid,
163    /// Common name for the root.
164    pub subject: String,
165    pub key_algorithm: KeyAlgorithm,
166    /// Requested root validity.
167    pub validity_days: u32,
168    /// The signing intermediate to create beneath the root, if any.
169    ///
170    /// `Some` is the ordinary case and what HashiCorp's own PKI walkthrough
171    /// does: the root signs one intermediate and then issues nothing else, so
172    /// a compromised issuer is replaced without redistributing the trust
173    /// anchor. `None` issues straight from the root, which is a smaller thing
174    /// to operate and a worse thing to lose.
175    pub intermediate: Option<IntermediateSpec>,
176}
177
178/// The signing intermediate created beneath a generated root.
179#[derive(Debug, Clone)]
180pub struct IntermediateSpec {
181    pub subject: String,
182    pub validity_days: u32,
183}

185/// A CA the custodian generated and still holds the key for.
186#[derive(Debug, Clone)]
187pub struct GeneratedCa {
188    /// The certificate that will sign leaves — the intermediate when one was
189    /// asked for, the root otherwise. PEM.
190    pub certificate_pem: String,
191    /// Everything above it, nearest issuer first, root last. Empty when the
192    /// issuing certificate *is* the root.
193    ///
194    /// Kept because a relying party validating an AXIAM-issued leaf needs it
195    /// and cannot get it from anywhere else: the root's certificate exists only
196    /// inside Vault.
197    pub chain_pem: Vec<String>,
198    /// What to put in the CA row's `key_locator`.
199    pub locator: String,
200}
201
202/// A leaf certificate to be signed by a custodian that holds the CA key.
203#[derive(Debug, Clone)]
204pub struct LeafSigningRequest {
205    /// PEM-encoded PKCS#10 request. The end-entity key is generated by AXIAM
206    /// and never sent — only its public half, inside this.
207    pub csr_pem: String,
208    /// How long the certificate should be valid for, in seconds. Already capped
209    /// to the CA's own remaining validity by the caller; the custodian may cap
210    /// it further, which is why the answer is parsed rather than assumed.
211    pub ttl_seconds: i64,
212}

214/// What a remote signer returned.
215#[derive(Debug, Clone)]
216pub struct SignedLeaf {
217    /// The signed certificate, PEM.
218    pub certificate_pem: String,
219    /// The issuing chain, nearest issuer first.
220    pub chain_pem: Vec<String>,
221}

223/// A custodian for CA signing keys.
224///
225/// Object-safe on purpose — the composition root chooses an implementation at
226/// runtime from configuration, so this is held as `Arc<dyn CaKeyStore>` and
227/// cannot use RPITIT the way the repository traits do. Hence the boxed futures
228/// rather than `impl Future`, matching [`crate::models::email`]'s provider
229/// trait, which is object-safe for the same reason.
230pub trait CaKeyStore: Send + Sync {
231    /// Take custody of `private_key_pem` for a CA that is about to be created.
232    ///
233    /// Called before the CA row is written, so a custodian that refuses stops
234    /// the CA existing at all rather than leaving a certificate whose key is
235    /// nowhere.
236    fn store<'a>(
237        &'a self,
238        organization_id: Uuid,
239        ca_id: Uuid,
240        private_key_pem: &'a str,
241    ) -> Pin<Box<dyn Future<Output = AxiamResult<StoredCaKey>> + Send + 'a>>;
242
243    /// Retrieve a key previously stored under `key_ref`.
244    ///
245    /// `inline` carries the row's own ciphertext, which only the database
246    /// custodian reads; every other implementation ignores it. Passing it
247    /// unconditionally is what lets the caller stay ignorant of which custodian
248    /// it is talking to.
249    fn load<'a>(
250        &'a self,
251        key_ref: &'a CaKeyRef,
252        inline: Option<&'a [u8]>,
253    ) -> Pin<Box<dyn Future<Output = AxiamResult<Zeroizing<String>>> + Send + 'a>>;
254
255    /// Release custody. A no-op for the database custodian, whose material goes
256    /// away with the row.
257    ///
258    /// Best-effort by contract: a CA row is the record of what exists, and a
259    /// custodian that could not be reached must not stop a revocation. What is
260    /// left behind is an orphaned secret, which is a cleanup task, not a
261    /// security failure — it signs nothing that AXIAM will honour.
262    fn delete<'a>(
263        &'a self,
264        key_ref: &'a CaKeyRef,
265    ) -> Pin<Box<dyn Future<Output = AxiamResult<()>> + Send + 'a>>;
266
267    /// Whether this custodian creates CA keys itself, rather than being handed
268    /// one AXIAM generated.
269    ///
270    /// A capability question rather than a match on [`Self::custody`], so that
271    /// adding a KMS does not mean revisiting every caller that wanted to know.
272    fn generates_cas(&self) -> bool {
273        false
274    }
275
276    /// Create a CA whose private key is born inside the custodian.
277    ///
278    /// Only called when [`Self::generates_cas`] is true. The default refuses
279    /// rather than silently generating a key here, which would produce exactly
280    /// the property — a CA key that passed through AXIAM — that a caller
281    /// reaching for this method was trying to avoid.
282    fn generate_ca<'a>(
283        &'a self,
284        request: &'a CaGenerationRequest,
285    ) -> Pin<Box<dyn Future<Output = AxiamResult<GeneratedCa>> + Send + 'a>> {
286        let _ = request;
287        Box::pin(async {
288            Err(AxiamError::Internal(
289                "this CA key custodian cannot generate a CA: it takes custody of a key \
290                 AXIAM generated"
291                    .into(),
292            ))
293        })
294    }
295
296    /// Take custody of a CA an organization already has — BYOK.
297    ///
298    /// Separate from [`Self::store`] only because the certificate matters to a
299    /// custodian that is a PKI rather than a safe: Vault's PKI engine imports a
300    /// key and the certificate it belongs to as one bundle, and has nowhere to
301    /// put a key on its own. Every other custodian ignores the certificate,
302    /// which is what the default body does.
303    fn import_ca<'a>(
304        &'a self,
305        organization_id: Uuid,
306        ca_id: Uuid,
307        certificate_pem: &'a str,
308        private_key_pem: &'a str,
309    ) -> Pin<Box<dyn Future<Output = AxiamResult<StoredCaKey>> + Send + 'a>> {
310        let _ = certificate_pem;
311        self.store(organization_id, ca_id, private_key_pem)
312    }
313
314    /// Whether signing happens inside the custodian.
315    ///
316    /// True means [`Self::load`] will refuse and [`Self::sign_csr`] is the only
317    /// way to issue against this CA — not a degraded mode but the stronger one,
318    /// where the signing key has never existed in this process.
319    fn signs_remotely(&self) -> bool {
320        false
321    }
322
323    /// Sign a CSR with a CA key the custodian holds and will not hand over.
324    ///
325    /// Only called when [`Self::signs_remotely`] is true.
326    fn sign_csr<'a>(
327        &'a self,
328        key_ref: &'a CaKeyRef,
329        request: &'a LeafSigningRequest,
330    ) -> Pin<Box<dyn Future<Output = AxiamResult<SignedLeaf>> + Send + 'a>> {
331        let _ = (key_ref, request);
332        Box::pin(async {
333            Err(AxiamError::Internal(
334                "this CA key custodian does not sign: load the key and sign here".into(),
335            ))
336        })
337    }
338
339    /// Which custodian this is. Recorded on the CA row at creation.
340    fn custody(&self) -> CaKeyCustody;
341
342    /// A short label for logs and startup diagnostics, e.g. `"vault"`.
343    fn describe(&self) -> &'static str;
344}

346#[cfg(test)]
347mod tests {
348    use super::*;
349
350    #[test]
351    fn custody_round_trips_through_its_string_form() {
352        for custody in [
353            CaKeyCustody::Database,
354            CaKeyCustody::Vault,
355            CaKeyCustody::VaultPki,
356            CaKeyCustody::External,
357        ] {
358            let s = custody.to_string();
359            assert_eq!(s.parse::<CaKeyCustody>().unwrap(), custody);
360        }
361    }
362
363    #[test]
364    fn an_unknown_custody_is_refused_rather_than_defaulted() {
365        // Defaulting would silently move a CA's key to a different custodian in
366        // the reader's mind, and the lookup would then miss or hit the wrong
367        // secret.
368        let err = "kms".parse::<CaKeyCustody>().unwrap_err();
369        assert!(err.contains("kms"));
370    }
371
372    #[test]
373    fn custody_serializes_snake_case_for_the_wire() {
374        assert_eq!(
375            serde_json::to_string(&CaKeyCustody::Vault).unwrap(),
376            "\"vault\""
377        );
378        assert_eq!(
379            serde_json::from_str::<CaKeyCustody>("\"external\"").unwrap(),
380            CaKeyCustody::External
381        );
382        // `snake_case` on a two-word variant: the wire form, the `Display`
383        // form, the `FromStr` form and the value the schema's ASSERT allows all
384        // have to be the same string, and `vaultPki` would break three of them.
385        assert_eq!(
386            serde_json::to_string(&CaKeyCustody::VaultPki).unwrap(),
387            "\"vault_pki\""
388        );
389    }
