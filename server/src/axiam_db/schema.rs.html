1625// -----------------------------------------------------------------------
1626// Schema v31 — redemption nonce, so single-use stops depending on the engine
1627// -----------------------------------------------------------------------
1628//
1629// READ THE TWO ADDENDA AT THE END OF THIS COMMENT FIRST — the 2026-08
1630// re-measurement, then the X6 note, which is the current state. The premise
1631// below — "SurrealDB does not detect the write-write conflict" — was measured
1632// on `kv-mem`, which is the TEST engine and not one AXIAM deploys. On the two
1633// persistent engines the conflict IS detected, and this mechanism is now
1634// layered ON TOP of an explicit transaction rather than instead of one.
1635//
1636// v30 relied on SurrealDB detecting the write-write conflict between two
1637// concurrent redemptions. Measured, it does not: 8 rounds in 1200 (8 racers
1638// each) saw two transactions both commit, with zero errors, both returning the
1639// pre-transition row — two RPTs from one authorization decision.
1640//
1641// Three repairs were measured before this one, and the two obvious ones are
1642// worse than the bug they fix:
1643//
1644//   mechanism                                    wrong (this consume path)
1645//   ------------------------------------------   -------------------------
1646//   v30: transaction + WHERE consumed = false     1 / 320
1647//   claim keyed on a record ID                   30 / 1200  (isolated probe)
1648//   claim on a UNIQUE INDEX, in a transaction     3 / 320
1649//   this: per-attempt nonce, write then read      1 / 640
1650//
1651// Read that table honestly: only the UNIQUE-index result is clearly bad. One
1652// failure in 640 against one in 320 is a single event either way, and does
1653// **not** establish that the nonce is less likely to double-redeem than what it
1654// replaces. What it does establish is that the nonce is not *worse*, and the
1655// reason to prefer it is mechanical rather than statistical.
1656//
1657// The nonce does not ask the engine to arbitrate. Every racer writes its own;
1658// the last write persists; each racer reads the row back and only the one whose
1659// nonce survived reports a redemption. Nothing depends on conflict detection or
1660// constraint enforcement — the two guarantees this engine was measured not to
1661// provide — and the one remaining window is at least nameable: a racer's write
1662// can land after another racer's read-back. An opaque failure to detect a
1663// conflict is not analysable in that way.
1664//
1665// No mechanism tested at this layer reaches zero, and closing the window needs
1666// a guarantee from below it — a storage engine that serialises, or
1667// single-writer serialisation in front of it. (X6 took the first of those; see
1668// the second addendum.)
1669//
1670// The read-back is deliberately NOT inside a transaction. Under snapshot
1671// isolation a racer would see its own write and every racer would believe it
1672// won — the failure would be total rather than occasional.
1673//
1674// -----------------------------------------------------------------------
1675// ADDENDUM, 2026-08 — everything above was measured on the wrong engine
1676// -----------------------------------------------------------------------
1677//
1678// The measurements above, and the ones in #302, were taken against `kv-mem`.
1679// Every integration test in this crate opened `Surreal::new::<Mem>(())`, so
1680// `kv-mem` is what "measured" meant. AXIAM does not deploy it: dev and prod
1681// compose run `surrealkv:`, and so does the k8s StatefulSet.
1682//
1683// Re-measured with `tools/surreal-race-probe` on SurrealDB 3.2.3, running the
1684// v30 shape (one guarded UPDATE inside BEGIN/COMMIT) with 8 racers released
1685// through a barrier:
1686//
1687//   engine          rounds x racers   admitted two winners   attempts aborted
1688//   -------------   ---------------   --------------------   ----------------
1689//   kv-mem          1200 x 8          23  (10 on a re-run)   5229 / 9600
1690//   kv-surrealkv    5000 x 8           0                     21613 / 40000
1691//   kv-rocksdb      1200 x 8           0                     8154 / 9600
1692//
1693// The abort column matters more than the winners column. `kv-mem` is not
1694// failing to arbitrate — it aborts contended attempts at 54%, the same rate
1695// `surrealkv` does. It arbitrates and then occasionally misses, silently, both
1696// callers receiving the pre-transition row. The persistent engines did not miss
1697// once, so on the engine AXIAM ships, v30 was already correct.
1698//
1699// What that means for this mechanism, and what it does not:
1700//
1701//   * The nonce is KEPT. It costs one extra write and one extra read on a rare
1702//     operation, it measured no worse than v30 on every engine, and conflict
1703//     detection is not a documented SurrealDB guarantee — so a version bump
1704//     could take it away silently. Removing working defence to reclaim two
1705//     statements is a bad trade.
1706//   * The nonce is NOT the thing standing between AXIAM and a double
1707//     redemption on a deployed system. The engine is. Do not read the presence
1708//     of this field as licence to run `memory` anywhere real; `kv-mem` leaks
1709//     with the nonce in place too (6 rounds in 1200).
1710//   * "Single-use is not guaranteed" above is still the correct posture, but
1711//     for a narrower reason than it says: 0 in 40 000 is strong evidence, not
1712//     proof, and no probe run reproduces the coverage-instrumented, saturated
1713//     conditions #302 describes.
1714//
1715// `WHERE consumed = false` is still required: it is what makes a later,
1716// non-concurrent redemption match nothing and leave the first winner's nonce
1717// undisturbed.
1718//
1719// -----------------------------------------------------------------------
1720// ADDENDUM 2, X6 (#302 closed) — the current state of this mechanism
1721// -----------------------------------------------------------------------
1722//
1723// Everything above describes a choice between the transaction and the nonce.
1724// X6 stopped choosing. All three consume paths now run BOTH:
1725//
1726//   1. the guarded `UPDATE` inside an explicit `BEGIN`/`COMMIT`, so the
1727//      deployed engine arbitrates and aborts the loser (54% of contended
1728//      attempts on `surrealkv`, 0 double winners in 40 000); and
1729//   2. the per-attempt nonce, read back in a SEPARATE QUERY AFTER THE COMMIT,
1730//      which asks the engine for nothing and therefore still catches a
1731//      conflict the engine silently missed.
1732//
1733// The read-back's position is the load-bearing detail and the reason this is
1734// two queries rather than one transaction: inside the transaction, snapshot
1735// isolation shows every racer its own write, so every racer reads back its own
1736// nonce and believes it won. Folding the read-back inside would convert an
1737// occasional double redemption into a certain one. Do not "simplify" it.
1738//
1739// So the posture changes, and this is the wording #302 was holding open until
1740// the fix landed: **single-use is guaranteed, conditional on an attested
1741// persistent storage engine** — the transaction arbitrating, the nonce
1742// auditing. A double redemption now requires two independent failures rather
1743// than one. On `kv-mem` it remains explicitly NOT guaranteed (the nonce leaks
1744// there too, 6 rounds in 1200), which is why `axiam-server` attests the engine
1745// at startup and refuses a positively-identified `memory` datastore unless
1746// `AXIAM__DB__ALLOW_MEMORY_ENGINE=true` — see
1747// `crate::engine_attestation`, including its finding that SurrealDB 3.2.4
1748// exposes no engine identity over the wire, so today that attestation is a
1749// WARN plus a MUST-level operator requirement in `docs/deployment/README.md`.
1750//
1751// The escalation path if a future engine bump breaks this, recorded and
1752// deliberately NOT built: single-writer serialisation in front of the
1753// datastore via a RabbitMQ single-active-consumer redemption queue. It is
1754// disproportionate against 0/40 000 plus a layered mechanism; build it when
1755// the measurement says to.
1756//
1757// Re-run the probe on any SurrealDB bump — README.md in that directory says
1758// why and how, `RESULTS.md` records what each pinned version measured, and
1759// `.github/workflows/surreal-race-probe.yml` makes it a required check
1760// whenever `Cargo.lock` moves `surrealdb`, `surrealdb-core` or `surrealkv`, so
1761// a bump can no longer change this silently.

1828// -----------------------------------------------------------------------
1829// Schema v34 — a key for resource-delete and child-create to collide on (#308)
1830// -----------------------------------------------------------------------
1831//
1832// `resource.delete` refuses to delete a resource that has children, and folds
1833// the check into its own transaction:
1834//
1835//     BEGIN;
1836//     LET $children = (SELECT VALUE id FROM child_of WHERE out = resource:<id>);
1837//     IF array::len($children) > 0 { THROW ... };
1838//     DELETE ...; DELETE type::record('resource', $id) ...;
1839//     COMMIT;
1840//
1841// D-13/CQ-B46 introduced that shape to close a TOCTOU window and described it
1842// as making the read-then-decide-then-delete atomic. It does make the
1843// statements atomic. That is not the property the guard needs, and #308 is the
1844// proof: on `surrealkv` a concurrent child-create beats it on trial 0 of every
1845// run, leaving a deleted parent with a live `child_of` edge pointing at it.
1846//
1847// The guard is a RANGE READ — every edge whose `out` is this parent — and the
1848// racing create INSERTS INTO THAT RANGE. Excluding that is the definition of a
1849// phantom, and preventing phantoms takes serialisable isolation. These engines
1850// give snapshot isolation: they detect write-write conflicts on the same key
1851// (measured doing exactly that, 21613 aborts in 40000 contended attempts — see
1852// `tools/surreal-race-probe`), and they let this through because the two
1853// transactions have no key in common. The delete writes the parent row and the
1854// edges it could see; the create writes a NEW edge the delete never saw.
1855//
1856// No query can fix that, because the guard cannot read a row that does not
1857// exist yet. What fixes it is giving the two transactions a shared key, so the
1858// conflict the engine already detects reliably is the one that decides the
1859// race. That is what this field is for:
1860//
1861//   * `resource.delete` already writes the parent row — it deletes it.
1862//   * Every path that adds a child edge now also writes the parent row, by
1863//     bumping `child_epoch`, inside the same transaction as the RELATE.
1864//
1865// One of the two must now lose. If the create commits first, the delete's write
1866// to the parent conflicts and it aborts, leaving parent and child intact. If
1867// the delete commits first, the create's bump matches no row, its guard throws,
1868// and no edge is written. Neither order produces an orphan.
1869//
1870// The counter's VALUE is not used for anything and deliberately so — reading it
1871// would be a second way to get this wrong. Its only job is to be a write to the
1872// parent's key. It is `option<int>` rather than `int DEFAULT 0` so that rows
1873// predating this migration need no backfill: `child_epoch ?? 0` treats absent
1874// and zero alike, and nothing distinguishes "never had a child" from "has had
1875// exactly zero".
1876const SCHEMA_V34: &str = "\
1877DEFINE FIELD IF NOT EXISTS child_epoch ON TABLE resource TYPE option<int>;
1878";

2204/// Run all pending migrations against the given SurrealDB client.
2205///
2206/// Creates `_migration` and `_migration_lock` tracking tables on first run,
2207/// then applies each pending migration atomically: the schema DDL and the
2208/// version-record INSERT are wrapped in a single `BEGIN TRANSACTION …
2209/// COMMIT TRANSACTION` so that a mid-step failure leaves the row
2210/// re-selectable (CQ-B06 / REQ-14 AC-5).
2211///
2212/// The `_migration_lock` record (`CREATE IF NOT EXISTS`) guards concurrent
2213/// startup — only one process may hold the lock at a time.  The record is
2214/// removed once migrations complete.
2215pub async fn run_migrations<C: Connection>(db: &Surreal<C>) -> Result<(), DbError> {
2216    // Ensure migration-tracking tables exist (all DDL is IF NOT EXISTS).
2217    db.query(MIGRATION_TABLE_DDL)
2218        .await?
2219        .check()
2220        .map_err(|e| DbError::Migration(e.to_string()))?;
2221
2222    // Acquire a startup lock so that concurrent instances do not race on
2223    // schema application.  UPSERT with a deterministic record ID is
2224    // idempotent — if a lock record already exists this is a no-op.
2225    db.query(
2226        "BEGIN TRANSACTION; \
2227         UPSERT _migration_lock:`startup` SET locked_at = time::now(); \
2228         COMMIT TRANSACTION",
2229    )
2230    .await?
2231    .check()
2232    .map_err(|e| DbError::Migration(format!("failed to acquire _migration_lock: {e}")))?;
2233
2234    // Determine current schema version.
2235    let mut result = db
2236        .query("SELECT * FROM _migration ORDER BY version DESC LIMIT 1")
2237        .await?;
2238    let records: Vec<MigrationRecord> = result.take(0)?;
2239    let current_version = records.first().map(|m| m.version).unwrap_or(0);
2240
2241    for migration in MIGRATIONS {
2242        if migration.version > current_version {
2243            info!(
2244                version = migration.version,
2245                name = migration.name,
2246                "Applying migration"
2247            );
2248
2249            // Wrap the schema DDL and the version-record INSERT in a single
2250            // transaction (CQ-B06).  If the DDL succeeds but the INSERT
2251            // fails, the whole block is rolled back and the migration will
2252            // be retried on the next startup.
2253            //
2254            // SurrealDB v3 transaction slot offset: BEGIN = slot 0, first
2255            // statement = slot 1, … (MEMORY.md).  We don't take() from the
2256            // result; we only call .check() to surface errors.
2257            let txn = format!(
2258                "BEGIN TRANSACTION;\n\
2259                 {};\n\
2260                 CREATE _migration SET version = {v}, name = '{n}';\n\
2261                 COMMIT TRANSACTION",
2262                migration.sql,
2263                v = migration.version,
2264                n = migration.name,
2265            );
2266            db.query(&txn).await?.check().map_err(|e| {
2267                DbError::Migration(format!(
2268                    "Migration v{} '{}' failed (transaction rolled back): {}",
2269                    migration.version, migration.name, e,
2270                ))
2271            })?;
2272
2273            info!(
2274                version = migration.version,
2275                "Migration applied successfully"
2276            );
2277        }
2278    }
2279
2280    // Release the startup lock now that migrations are complete.
2281    db.query("DELETE _migration_lock:`startup`")
2282        .await?
2283        .check()
2284        .map_err(|e| DbError::Migration(format!("failed to release migration lock: {e}")))?;
2285
2286    Ok(())
2287}
