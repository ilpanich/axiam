1//! AXIAM directory identity source: LDAP and Active Directory.
2//!
3//! This crate is the home of competitor-gap item **G-3**: a tenant can
4//! federate an existing LDAP or Active Directory directory, so its users sign
5//! in with their directory password, are provisioned just in time, and have
6//! their directory groups mapped onto AXIAM groups (roles and permissions keep
7//! working through group inheritance).
8//!
9//! # What exists today
10//!
11//! * [`config`] validates a directory configuration before it is stored
12//!   (T23.3.1).
13//! * [`escape`] is RFC 4515 filter-value escaping and the only function that
14//!   puts a login name into a filter; [`tls`] builds the verified rustls client
15//!   configuration from a tenant's anchors (T23.3.2).
16//! * [`client`] is the LDAP client — `ldap3` over rustls, mandatory TLS, a
17//!   bounded per-tenant pool, no referrals — and the bind-as-user flow;
18//!   [`authenticator`] is the
19//!   [`DirectoryAuthenticator`](axiam_core::models::directory::DirectoryAuthenticator)
20//!   the composition root injects into the login path (T23.3.2).
21//! * [`dn`], [`groups`], [`group_lookup`] and [`mapper`] are group mapping
22//!   (T23.3.4, D-30): an explicit table of directory group DNs to AXIAM groups,
23//!   nested resolution to a configured depth under a hard cap, and the
24//!   application that owns only the memberships it wrote.
25//!
26//! * [`sync_lookup`] and [`sync`] are the sync job (T23.3.5, D-31): the
27//!   read-only questions it asks the directory, and the full and incremental
28//!   runs that turn the answers into `Inactive` accounts, refreshed attributes
29//!   and group mappings — and never into a re-enabled, created or linked one.
30//!
31//! * [`address`] and [`frame`] guard the connector itself (T23.3.7, D-19):
32//!   the address guard resolves a directory host once, refuses loopback,
33//!   link-local, metadata, multicast and AXIAM's own listeners — and private
34//!   ranges outside the operator's allow-list — and the connection is pinned
35//!   to the vetted address (T-300); the frame guard measures and checks every
36//!   message a directory sends before `ldap3` sees it (P23W2-10, T-295,
37//!   T-331), through a relay beneath `ldap3`.
38//!
39//! The management routes are a later task of the same item (T23.3.8); they
40//! call `config::validate` and [`DirectoryClient::guard`] on every write.
41//!
42//! # Boundaries that bind every later task
43//!
44//! * **Read-only.** AXIAM never writes to a directory. The bind account it is
45//!   given should hold read-only rights, and the documentation says so; nothing
46//!   here may add an LDAP add, modify, delete or password-change operation.
47//! * **No Kerberos.** SPNEGO / Kerberos single sign-on is out of scope for this
48//!   phase (decision D-1), so nothing Kerberos-shaped appears in the model.
49//! * **Encrypted transport only.** A plaintext `ldap://` URL is refused at
50//!   configuration time; the only accepted shapes are `ldaps://` and `ldap://`
51//!   with StartTLS.
52//! * **The bind secret is write-only.** It is encrypted at rest under a key
53//!   held by the secret provider, never returned by any API and never logged.
54//!
55//! # Placement
56//!
57//! Layer 3 of the workspace, beside `axiam-federation`: a federation protocol
58//! with the same dependency shape (domain types below it, protocol code in it,
59//! nothing above allowed to be reached back into). See
60//! `claude_dev/crate-layering.md` for why, and
61//! `scripts/check-crate-layering.py` for the gate that holds it.
62
