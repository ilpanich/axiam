1//! Authentication context class references (W4, plan §4.4 — G3/G4).
2//!
3//! An `acr` claim is a statement about **how** the end user authenticated. A
4//! relying party that requires a second factor reads it and decides whether to
5//! release money, or medical records, or the ability to change a password. It
6//! is therefore one of the few claims whose falsehood is directly exploitable,
7//! and it has one famous way of becoming false.
8//!
9//! # The echo bug, and why it cannot be written here
10//!
11//! The classic implementation of `acr` is: read `acr_values` from the
12//! authorization request, copy the first entry into the ID token, ship it.
13//! Every conformance suite passes, every relying party is satisfied, and the
14//! claim means nothing at all — the RP asked for MFA and was told "MFA"
15//! because it asked, not because anything happened.
16//!
17//! [`acr_for`] is the whole defence, and it is a defence of shape rather than
18//! of discipline: **it takes the session's evidence and nothing else.** There
19//! is no parameter it could be handed the request through, so there is no
20//! review that has to notice the request being handed to it. A future edit
21//! that reintroduced the bug would have to widen the signature first, which is
22//! a change a reader can see without knowing this story.
23//!
24//! The request is not ignored — it decides two things — but neither of them is
25//! what the claim *says*:
26//!
27//! | The request's `acr_values` decide | The session's `amr` decides |
28//! |---|---|
29//! | whether a step-up is offered ([`Acr::satisfies`]) | which class was achieved ([`acr_for`]) |
30//! | which *satisfied* value is reported ([`report_acr`]) | which values are satisfiable at all |
31//!
32//! [`report_acr`] is the second half of the same argument. It can only return
33//! a requested value that the achieved class already satisfies; anything else
34//! falls back to the achieved class itself. So the strongest thing an RP can
35//! do by asking is change *which true statement* it is told.
36//!
37//! # The vocabulary is closed (plan §11, D6)
38//!
39//! Two values, defined by AXIAM, published in `acr_values_supported`
40//! ([`crate::oidc::ACR_SINGLE_FACTOR`], [`crate::oidc::ACR_MULTI_FACTOR`]).
41//! Not operator-configurable strings: an operator who can configure the string
42//! can configure it to say `mfa` for a password login, which is the echo bug
43//! arriving through the configuration file instead of through the code.
44//!
45//! # Federated sessions
46//!
47//! A federated login records `amr = ["fed"]` and nothing else
48//! (`handlers/federation.rs`), because what the upstream provider did to
49//! produce its assertion is the provider's claim and not AXIAM's evidence.
50//! `fed` alone maps to [`Acr::SingleFactor`] here — the plan's "unmapped
51//! upstream evidence yields `1fa`, strict by default". Mapping an upstream
52//! `acr`/`amr` into the local vocabulary would need an operator-configured
53//! attribute mapping, which does not exist (`federation_claims.rs` has no such
54//! field) and which W4 deliberately does not add: it is exactly the
55//! configuration surface D6 refuses.
56
57use axiam_core::models::session::Amr;
58
59use crate::oidc::{ACR_MULTI_FACTOR, ACR_SINGLE_FACTOR};

61/// An authentication context class AXIAM can assert.
62///
63/// Ordered so that a stronger class compares greater than a weaker one, which
64/// is what makes [`Acr::satisfies`] one comparison rather than a table that
65/// could disagree with itself.
66#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
67pub enum Acr {
68    /// [`ACR_SINGLE_FACTOR`] — the floor. Any authentication AXIAM performed
69    /// satisfies it, including one whose evidence a newer binary recorded and
70    /// this one cannot read.
71    SingleFactor,
72    /// [`ACR_MULTI_FACTOR`] — two distinct factors, or one factor that is
73    /// itself a possession proof with user verification.
74    MultiFactor,
75}
76
77impl Acr {
78    /// The published URN.
79    pub const fn as_str(self) -> &'static str {
80        match self {
81            Self::SingleFactor => ACR_SINGLE_FACTOR,
82            Self::MultiFactor => ACR_MULTI_FACTOR,
83        }
84    }
85
86    /// Parse a requested value. `None` for anything outside the vocabulary.
87    ///
88    /// An unrecognised `acr_values` entry is **not** an error: OIDC Core
89    /// §3.1.2.1 makes `acr_values` a voluntary preference, and a relying party
90    /// that lists three registries' worth of URNs is asking AXIAM to pick the
91    /// one it knows. What an unknown value can never do is be *satisfied* —
92    /// [`report_acr`] can only return what parses here — so a client that asks
93    /// exclusively for values AXIAM does not implement is answered with the
94    /// class its session actually achieved, never with its own string.
95    pub fn from_wire(raw: &str) -> Option<Self> {
96        match raw.trim() {
97            ACR_SINGLE_FACTOR => Some(Self::SingleFactor),
98            ACR_MULTI_FACTOR => Some(Self::MultiFactor),
99            _ => None,
100        }
101    }
102
103    /// Does an authentication of *this* class satisfy a request for `required`?
104    ///
105    /// Monotone: a session that completed MFA satisfies a request for the
106    /// single-factor class too. OIDC Core §3.1.2.1 is explicit that what an ID
107    /// token reports is the class the authentication *satisfied*, and refusing
108    /// to let a stronger authentication satisfy a weaker request would force
109    /// relying parties to enumerate every class they would accept.
110    pub const fn satisfies(self, required: Self) -> bool {
111        (self as u8) >= (required as u8)
112    }
113}
114
115/// The class an authentication achieved, from its evidence and nothing else.
116///
117/// **This function must never be able to see the authorization request.** See
118/// the module docs for why that is a property of the signature rather than of
119/// a comment. If a future change needs the request here, the change that is
120/// actually wanted is somewhere else.
121///
122/// [`Acr::MultiFactor`] is answered for evidence that proves two distinct
123/// factors, or one possession factor the authenticator itself verified a human
124/// for:
125///
126/// | Evidence | Why it is multi-factor |
127/// |---|---|
128/// | `mfa` | RFC 8176 §2's own marker, recorded by AXIAM's TOTP and MFA paths |
129/// | `hwk` + `user` | a hardware authenticator that performed user verification — possession *and* a PIN or biometric |
130/// | `swk` + `user` | the same for a platform (software-secured) passkey |
131/// | `x509` | a client certificate: possession of a key the user cannot type, bound to a certificate AXIAM issued |
132///
133/// Everything else — a password, an unverified presence-only passkey, a
134/// federated assertion, no evidence at all — is [`Acr::SingleFactor`]. That
135/// includes the empty list a pre-v55 session row decodes to, and it includes a
136/// value written by a newer binary that [`Amr::from_wire`] dropped: less
137/// evidence lowers assurance, which is the only direction an unreadable row
138/// may move the answer.
139pub fn acr_for(amr: &[Amr]) -> Acr {
140    let has = |needle: Amr| amr.contains(&needle);
141    let verified_key = (has(Amr::Hwk) || has(Amr::Swk)) && has(Amr::User);
142    if has(Amr::Mfa) || verified_key || has(Amr::X509) {
143        Acr::MultiFactor
144    } else {
145        Acr::SingleFactor
146    }
147}
148
149/// Which value to put in the `acr` claim, given what was achieved and what the
150/// relying party asked for.
151///
152/// The rule is **most-preferred satisfied, in the relying party's order**, and
153/// it is deliberately not "the highest class achieved": OIDC Core §3.1.2.1
154/// says an ID token reports the class the authentication satisfied, and when
155/// an RP lists `[1fa, mfa]` it has said which satisfied class it would rather
156/// hear about. An RP that only wants the strongest lists only the strongest.
157///
158/// `requested` may contain anything, including values from other registries
159/// and outright nonsense. Nothing that fails [`Acr::from_wire`] can be
160/// returned, and nothing `achieved` does not [`satisfy`](Acr::satisfies) can
161/// be returned — so the worst an RP achieves by asking is to select among true
162/// statements. When nothing it asked for is satisfied (or it asked for
163/// nothing), the achieved class is reported: truthfully, and knowing it will
164/// disappoint.
165pub fn report_acr(achieved: Acr, requested: &[String]) -> &'static str {
166    requested
167        .iter()
168        .filter_map(|value| Acr::from_wire(value))
169        .find(|wanted| achieved.satisfies(*wanted))
170        .unwrap_or(achieved)
171        .as_str()
172}

174#[cfg(test)]
175mod tests {
176    use super::*;
177
178    /// **T3.1, the type-level half.** `acr_for` is called with evidence and
179    /// nothing else, and the strongest request in the vocabulary does not move
180    /// the answer — because there is no parameter to move it with.
181    #[test]
182    fn the_claim_is_derived_from_evidence_the_request_cannot_reach() {
183        // A password-only session. The RP may ask for whatever it likes; this
184        // call site is the only producer of the claim, and it has nowhere to
185        // put the request.
186        assert_eq!(acr_for(&[Amr::Pwd]), Acr::SingleFactor);
187        assert_eq!(
188            report_acr(acr_for(&[Amr::Pwd]), &[ACR_MULTI_FACTOR.to_owned()]),
189            ACR_SINGLE_FACTOR,
190            "asking for mfa over a password session must be answered 1fa"
191        );
192    }
193
194    #[test]
195    fn multi_factor_is_answered_only_for_evidence_that_proves_two_factors() {
196        for evidence in [
197            vec![Amr::Pwd, Amr::Otp, Amr::Mfa],
198            vec![Amr::Mfa],
199            vec![Amr::Hwk, Amr::User],
200            vec![Amr::Swk, Amr::User],
201            vec![Amr::X509],
202            vec![Amr::Pwd, Amr::Hwk, Amr::User],
203        ] {
204            assert_eq!(
205                acr_for(&evidence),
206                Acr::MultiFactor,
207                "{evidence:?} proves two factors"
208            );
209        }
210    }
211
212    #[test]
213    fn single_factor_is_the_answer_for_everything_else() {
214        for evidence in [
215            vec![],
216            vec![Amr::Pwd],
217            vec![Amr::Otp],
218            // Presence without verification: the authenticator proved
219            // possession and did not prove a human was asked for anything.
220            vec![Amr::Hwk],
221            vec![Amr::Swk],
222            // A bare `user` with no key is not a factor AXIAM can name.
223            vec![Amr::User],
224            // The federated floor: `fed` alone is one upstream assertion.
225            vec![Amr::Fed],
226        ] {
227            assert_eq!(
228                acr_for(&evidence),
229                Acr::SingleFactor,
230                "{evidence:?} does not prove two factors"
231            );
232        }
233    }
234
235    /// The empty list a pre-v55 session row decodes to satisfies the floor and
236    /// nothing above it — the strict direction, and no backfill.
237    #[test]
238    fn a_session_with_no_recorded_evidence_satisfies_only_the_floor() {
239        let achieved = acr_for(&[]);
240        assert!(achieved.satisfies(Acr::SingleFactor));
241        assert!(!achieved.satisfies(Acr::MultiFactor));
242    }
243
244    #[test]
245    fn a_stronger_authentication_satisfies_a_weaker_request() {
246        assert!(Acr::MultiFactor.satisfies(Acr::SingleFactor));
247        assert!(Acr::MultiFactor.satisfies(Acr::MultiFactor));
248        assert!(Acr::SingleFactor.satisfies(Acr::SingleFactor));
249        assert!(!Acr::SingleFactor.satisfies(Acr::MultiFactor));
250    }
251
252    /// **T3.4.** Most-preferred *satisfied* in the RP's order, not highest
253    /// achieved. Pinned so the rule stays explicit rather than incidental.
254    #[test]
255    fn the_reported_value_is_the_most_preferred_one_the_session_satisfies() {
256        let mfa_session = acr_for(&[Amr::Pwd, Amr::Otp, Amr::Mfa]);
257        assert_eq!(
258            report_acr(
259                mfa_session,
260                &[ACR_SINGLE_FACTOR.to_owned(), ACR_MULTI_FACTOR.to_owned()]
261            ),
262            ACR_SINGLE_FACTOR,
263            "the RP put 1fa first and the session satisfies it"
264        );
265        assert_eq!(
266            report_acr(
267                mfa_session,
268                &[ACR_MULTI_FACTOR.to_owned(), ACR_SINGLE_FACTOR.to_owned()]
269            ),
270            ACR_MULTI_FACTOR,
271            "…and the other order selects the other satisfied value"
272        );
273    }
274
275    #[test]
276    fn nothing_requested_reports_what_was_achieved() {
277        assert_eq!(report_acr(Acr::SingleFactor, &[]), ACR_SINGLE_FACTOR);
278        assert_eq!(report_acr(Acr::MultiFactor, &[]), ACR_MULTI_FACTOR);
279    }
280
281    /// A value outside the vocabulary can never be returned — not even one an
282    /// RP invented that looks like AXIAM's own.
283    #[test]
284    fn an_unknown_requested_value_is_never_echoed() {
285        for invented in [
286            "urn:axiam:acr:god-mode",
287            "urn:axiam:acr:MFA",
288            " urn:axiam:acr:mfa ",
289            "http://schemas.openid.net/pape/policies/2007/06/multi-factor",
290            "1",
291            "",
292        ] {
293            let reported = report_acr(Acr::MultiFactor, &[invented.to_owned()]);
294            assert!(
295                reported == ACR_SINGLE_FACTOR || reported == ACR_MULTI_FACTOR,
296                "{invented:?} was echoed as {reported:?}"
297            );
298            assert_ne!(reported, invented, "{invented:?} was echoed verbatim");
299        }
300    }
301
302    /// Whitespace is not trimmed by the parser used for *reporting*, but is by
303    /// [`Acr::from_wire`] — the two must not disagree about what a value is.
304    #[test]
305    fn from_wire_trims_and_is_exact_otherwise() {
306        assert_eq!(
307            Acr::from_wire("  urn:axiam:acr:mfa "),
308            Some(Acr::MultiFactor)
309        );
310        assert_eq!(Acr::from_wire("urn:axiam:acr:1fa"), Some(Acr::SingleFactor));
311        assert_eq!(Acr::from_wire("urn:axiam:acr:1FA"), None);
312    }

314    /// The published vocabulary and the type must be the same two values: a
315    /// class the discovery document does not advertise is one no RP can ask
316    /// for, and a value it advertises that nothing satisfies is a lie.
317    #[test]
318    fn the_type_and_the_discovery_vocabulary_agree() {
319        for value in [ACR_SINGLE_FACTOR, ACR_MULTI_FACTOR] {
320            let parsed = Acr::from_wire(value).expect("advertised values must parse");
321            assert_eq!(parsed.as_str(), value);
322        }
323    }
