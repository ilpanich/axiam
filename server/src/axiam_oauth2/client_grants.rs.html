1//! What removing an OAuth2 client revokes (#517).
2//!
3//! Three paths remove a client row: an administrator's
4//! `DELETE /api/v1/oauth2-clients/{id}`, RFC 7592's
5//! `DELETE /oauth2/register/{client_id}` and the unused-client sweep. Each
6//! calls [`ClientGrantStores::revoke`], so they cannot disagree about what a
7//! removed client leaves behind.
8//!
9//! # Why anything needs revoking
10//!
11//! With the row gone every grant fails at client authentication — but only
12//! while the `client_id` names nothing. A `managed_by: cimd` client's
13//! `client_id` is its metadata document's URL, and `materialise_if_cimd`
14//! writes the row back on the client's next request. Whatever the old row's
15//! client still held would then work again. Before #517 nothing was revoked,
16//! and every refresh token issued before an administrator's delete refreshed
17//! against the re-materialised row.
18//!
19//! # What is revoked, and what is not
20//!
21//! * **Refresh tokens** — marked revoked (`revoke_all_for_client`).
22//! * **Authorization codes** — deleted, redeemed or not. Deleted rather than
23//!   marked used, because a used code presented again is answered as a replay
24//!   (the session it came from is revoked), and a voided code is not evidence
25//!   of theft.
26//! * **Pushed authorization requests** — deleted, spent or not.
27//! * **Access tokens** — self-contained JWTs, revoked by nothing in AXIAM;
28//!   they expire within the access-token lifetime.
29//! * **The end user's AXIAM sessions** — not the client's to end: they are
30//!   shared with every other relying party, and ending them because one client
31//!   went away would be a forced logout a stranger could trigger through
32//!   RFC 7592.
33//! * **D4 consent records** — left to the users who gave them. A `dcr` or
34//!   `admin` identifier is never reissued, and a re-materialised CIMD client is
35//!   the same document at the same URL the user consented to.
36
37use axiam_core::error::AxiamResult;
38use axiam_core::repository::{
39    AuthorizationCodeRepository, PushedAuthRequestRepository, RefreshTokenRepository,
40};
41use uuid::Uuid;
42
43/// The stores holding what a client was granted, revoked together when the
44/// client is removed. See the [module documentation](self).
45#[derive(Debug, Clone)]
46pub struct ClientGrantStores<RT, AC, PR> {
47    refresh_tokens: RT,
48    codes: AC,
49    pushed_requests: PR,
50}
51
52impl<RT, AC, PR> ClientGrantStores<RT, AC, PR>
53where
54    RT: RefreshTokenRepository,
55    AC: AuthorizationCodeRepository,
56    PR: PushedAuthRequestRepository,
57{
58    /// Group the three stores.
59    pub fn new(refresh_tokens: RT, codes: AC, pushed_requests: PR) -> Self {
60        Self {
61            refresh_tokens,
62            codes,
63            pushed_requests,
64        }
65    }
66
67    /// Revoke every refresh token, and delete every authorization code and
68    /// pushed request, issued to `client_id` in `tenant_id`.
69    ///
70    /// Idempotent, so a caller may run it before and again after removing the
71    /// row. The first failure is returned; a caller that has not yet removed
72    /// the row should then keep it, so the removal can be retried rather than
73    /// leave a row-less client whose grants are still live.
74    pub async fn revoke(&self, tenant_id: Uuid, client_id: &str) -> AxiamResult<()> {
75        self.refresh_tokens
76            .revoke_all_for_client(tenant_id, client_id)
77            .await?;
78        self.codes
79            .delete_all_for_client(tenant_id, client_id)
80            .await?;
81        self.pushed_requests
82            .delete_all_for_client(tenant_id, client_id)
83            .await?;
84        Ok(())
85    }
86}
