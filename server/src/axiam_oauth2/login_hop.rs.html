1//! The browser login hop (W3, plan §4.0 "Gap 0").
2//!
3//! Until this wave `/oauth2/authorize` had no way to answer an anonymous
4//! browser. It required an already-authenticated principal — the `axiam_access`
5//! cookie or a `Bearer`/`DPoP` header — and answered anything else with a 401
6//! JSON body. That is a dead end for a real relying party, because
7//! `axiam_access` is `SameSite=Strict` and a cross-site top-level navigation
8//! (which is precisely what an RP redirect is) never carries a Strict cookie.
9//! Even a signed-in user arrived anonymous.
10//!
11//! The hop closes that: an anonymous request from a client registered
12//! `browser_sso` is redirected to the admin SPA's `/login`, carrying a
13//! `return_to` that names where to come back to. This module owns the two
14//! decisions in that sentence which must be right — **what a `return_to` is
15//! allowed to be**, and **why the hop terminates** — as pure functions, so they
16//! are tested without an HTTP server and cannot be re-derived slightly
17//! differently by a second caller.
18//!
19//! # What a `return_to` may be
20//!
21//! Exactly one shape: `/oauth2/authorize?` followed by a query string. Not a
22//! URL, not a path the caller chose, not a prefix — the authorization endpoint,
23//! with parameters, and nothing else. [`validate_return_to`] is where that is
24//! decided, and it is applied **twice on the server** (once when the value is
25//! built, once when the browser comes back with it) as well as in the SPA
26//! before it navigates. The plan calls for validation "on both sides"; the
27//! third check is free and closes the case where a `return_to` is stored,
28//! logged or replayed between the two.
29//!
30//! Since T23.2.3 there is a second caller with a second exact path: the SAML
31//! 2.0 IdP's SSO endpoint, whose hop comes back to
32//! `/saml/v2/{tenant_id}/sso/continue?handle=…` ([`build_saml_return_to`]).
33//! It is the same validator ([`validate_return_to_at`]) told to expect that one
34//! path, so it is still one exact shape per call and the audit list is refused
35//! against it row for row.
36//!
37//! Anything else is an open redirect. The interesting members of that family
38//! are foreign origins (`https://evil.example/…`), scheme-relative values
39//! (`//evil.example/…`, which a browser resolves to a *different host* while
40//! looking like a path), backslash variants (`/\evil.example`, which several
41//! browsers normalise to `//`), and traversal (`/oauth2/authorize/../../admin`).
42//! All four are refused here, and the REST layer additionally resolves the
43//! result against the deployment's own origin and re-checks it through
44//! `require_deployment_spa_origin` — the same rule that already guards the
45//! federation SSO handoff. That second check is redundant while this function
46//! demands an exact path, and it is kept precisely because a future edit to
47//! this function is the way that stops being true.
48//!
49//! # Why the hop terminates
50//!
51//! `authorize → /login → authorize` is a loop if the second `authorize` can
52//! produce a third. It cannot, because of one rule with two halves:
53//!
54//! 1. every login redirect this server builds carries [`LOGIN_HOP_MARKER`] in
55//!    its `return_to`; and
56//! 2. an authorization request that **arrives** carrying that marker is never
57//!    answered with a login redirect — if it still has no principal, it is
58//!    answered with a terminal error.
59//!
60//! So along any chain of authorization requests generated by this server's own
61//! redirects, at most one redirect is emitted: the first request has no marker
62//! and may hop; the request that hop produces has one and may not. The chain is
63//! two authorization requests and one login page, whatever goes wrong in
64//! between — a cookie the browser refused to store, a login into the wrong
65//! tenant, a session that expired between the two legs.
66//!
67//! The marker is in a URL and the user agent could strip it. That costs the
68//! guard nothing: the loop it prevents is a loop in *that same browser*, so
69//! removing the guard only harms whoever removed it, and no security decision
70//! anywhere reads the marker. It selects an error message and the shape of a
71//! response; it never selects a principal.
72//!
73//! # What W4 added to the marker, and why it is still not a security decision
74//!
75//! W3 read the marker in one place: an anonymous return leg is answered rather
76//! than redirected again. W4's honour lane reads it in two more (see
77//! [`crate::honour`]) — a requirement that survives one interaction is
78//! answered rather than retried, and `prompt=none` on a request that has been
79//! through the sign-in page is refused because the interaction it forbade has
80//! happened.
81//!
82//! Both are still, exactly, "which of two truthful answers to give". A relying
83//! party can forge the marker on its own authorization request, and the
84//! strongest thing forging it achieves is that the server skips an interaction
85//! *the forger asked for*: no principal changes, no claim is added, and
86//! `auth_time`, `acr` and `amr` still describe the authentication that really
87//! happened rather than the one the request wanted. A third party cannot forge
88//! it into somebody else's request without already being able to write that
89//! request, at which point it is the relying party.
90//!
91//! # What W5 adds, and why it is all allow-listed types
92//!
93//! W5 lets the sign-in page be *presented* the way the relying party asked:
94//! a pre-filled username (`login_hint`), a compact layout (`display`) and a
95//! language (`ui_locales`). All three arrive as relying-party-controlled
96//! strings and all three end up on a page a human types a password into, so
97//! the rule for this module is the one W4 set for `acr`: **what crosses into
98//! the URL is a type, not a string**, wherever a closed set exists.
99//!
100//! Two of the three have one — [`crate::locale::Locale`] and
101//! [`crate::locale::Display`] — and are matched on the server, so the raw
102//! `ui_locales` and `display` values never reach the SPA at all. The third,
103//! `login_hint`, has no closed set by definition: it is whatever identifier
104//! the relying party believes the user types. It is carried verbatim, and the
105//! two things that make that safe are stated where they are decided rather
106//! than here — the parser bounds it to
107//! [`crate::authn_params::MAX_HINT_LEN`] bytes and drops it if it fails to
108//! parse as UTF-8, and [`Cosmetic::login_hint`] documents the property that
109//! actually matters: **no server-side lookup is ever performed on it.**

113/// The query parameter that marks an authorization request as the return leg
114/// of a login hop.
115///
116/// `axiam_`-prefixed so it cannot collide with an OAuth2 or OpenID Connect
117/// parameter now or later: the registries do not issue names in a vendor
118/// namespace, and a relying party that sends this one is sending a parameter
119/// AXIAM defines.
120pub const LOGIN_HOP_MARKER: &str = "axiam_login_hop";

122/// The only path a `return_to` may name.
123pub const AUTHORIZE_PATH: &str = "/oauth2/authorize";

125/// The SPA route the hop sends the browser to.
126pub const LOGIN_PATH: &str = "/login";

128/// Largest `return_to` this server will build or accept, in bytes.
129///
130/// An authorization request is a query string, and a `request_uri` one is
131/// short; 4 KiB is generous for the inline form (nine OIDC parameters, a
132/// `state`, a `nonce`, a PKCE challenge) and small enough that the redirect
133/// stays inside every deployment's URL limits, since the value is carried
134/// *inside* another URL and is therefore percent-encoded on the way.
135pub const MAX_RETURN_TO_LEN: usize = 4096;

137/// Why a candidate `return_to` was refused.
138///
139/// A typed reason rather than a bool because these are the open-redirect
140/// family and each member has a distinct test; a caller that logs the variant
141/// can tell "a client sent us something long" from "someone tried to send a
142/// browser to another host".
143#[derive(Debug, Clone, Copy, PartialEq, Eq)]
144pub enum ReturnToError {
145    /// Longer than [`MAX_RETURN_TO_LEN`].
146    TooLong,
147    /// Contains a control character, whitespace, or a fragment.
148    ///
149    /// Whitespace and control characters are header-injection material; a
150    /// fragment is not something a server builds and is invisible to the
151    /// server that would have to validate what follows it.
152    IllegalCharacter,
153    /// Not a path at all: it does not begin with a single `/`.
154    ///
155    /// This is the arm that refuses `https://evil.example/…` and every other
156    /// absolute form.
157    NotAPath,
158    /// Begins `//` or `/\` — a scheme-relative reference.
159    ///
160    /// It reads as a path and resolves to a different **host**. This is the
161    /// member of the family that gets missed, which is why it has its own
162    /// variant and its own test.
163    SchemeRelative,
164    /// A path other than exactly [`AUTHORIZE_PATH`], or one with no query.
165    ///
166    /// Traversal (`/oauth2/authorize/../../admin`) lands here rather than in a
167    /// variant of its own: there is no normalisation step to defeat, because
168    /// nothing but the exact path is accepted in the first place.
169    NotTheAuthorizeEndpoint,
170}
171
172impl fmt::Display for ReturnToError {
173    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
174        let msg = match self {
175            Self::TooLong => "return_to is too long",
176            Self::IllegalCharacter => "return_to contains an illegal character",
177            Self::NotAPath => "return_to must be a path on this deployment",
178            Self::SchemeRelative => "return_to must not be scheme-relative",
179            Self::NotTheAuthorizeEndpoint => {
180                "return_to must name the authorization endpoint with a query"
181            }
182        };
183        f.write_str(msg)
184    }
185}

187/// Is this a `return_to` the server built and will honour?
188///
189/// See the module docs for the shape and for why it is checked more than once.
190/// The check is *total and syntactic*: it reads the candidate and nothing else,
191/// so it gives the same answer on the way out (when the server builds the
192/// value) as on the way back (when a browser presents one), which is the whole
193/// property "validated on both sides" is worth having.
194///
195/// # Errors
196///
197/// [`ReturnToError`], naming which member of the open-redirect family the
198/// candidate belongs to.
199pub fn validate_return_to(candidate: &str) -> Result<(), ReturnToError> {
200    validate_return_to_at(candidate, AUTHORIZE_PATH)
201}
202
203/// [`validate_return_to`], for a deployment that serves the authorization
204/// endpoint at a per-tenant path as well (T21.6).
205///
206/// `authorize_path` is the **one** path this candidate may name — the caller
207/// supplies it from the request it is answering (`/oauth2/authorize`, or
208/// `/t/{tenant_id}/oauth2/authorize`), never from the candidate itself. That is
209/// what keeps this exactly as strict as the single-path version it generalises:
210/// the set of accepted paths for any one call is still a set of one, so there
211/// is still nothing to normalise and nothing traversal can reach.
212///
213/// Every other rule — the length bound, the character class, the leading
214/// single `/`, the required query — is applied to the candidate before the
215/// path is looked at, and is the same rule in the same order.
216///
217/// # Errors
218///
219/// [`ReturnToError`], as [`validate_return_to`].
220pub fn validate_return_to_at(candidate: &str, authorize_path: &str) -> Result<(), ReturnToError> {
221    if candidate.len() > MAX_RETURN_TO_LEN {
222        return Err(ReturnToError::TooLong);
223    }
224    // A fragment is refused with the control characters: everything after `#`
225    // never reaches the server that would have to validate it, so a value
226    // carrying one is a value only half of which was checked.
227    if candidate
228        .chars()
229        .any(|c| c.is_control() || c.is_whitespace() || c == '#' || c == '\\')
230    {
231        return Err(ReturnToError::IllegalCharacter);
232    }
233    let mut chars = candidate.chars();
234    if chars.next() != Some('/') {
235        return Err(ReturnToError::NotAPath);
236    }
237    // `/\` is already gone with the backslashes above; `//` is checked here so
238    // the two scheme-relative spellings answer with the same variant.
239    if chars.next() == Some('/') {
240        return Err(ReturnToError::SchemeRelative);
241    }
242
243    let Some((path, query)) = candidate.split_once('?') else {
244        return Err(ReturnToError::NotTheAuthorizeEndpoint);
245    };
246    if path != authorize_path || query.is_empty() {
247        return Err(ReturnToError::NotTheAuthorizeEndpoint);
248    }
249    Ok(())
250}

279/// The SAML SSO endpoint's return leg, `/saml/v2/{tenant_id}/sso/continue`
280/// (T23.2.3): the **only** path a SAML login hop's `return_to` may name.
281///
282/// A SAML `AuthnRequest` is not replayable by redirect (the HTTP-POST binding
283/// arrives as a cross-site form post), so the SSO endpoint parses and checks it,
284/// stores it server-side under an opaque handle, and the browser comes back here
285/// carrying only that handle. [`validate_return_to_at`] with this path is the
286/// whole of the SAML arm: the same five rules, one exact path per call.
287#[must_use]
288pub fn saml_sso_continue_path(tenant_id: uuid::Uuid) -> String {
289    format!("{}/continue", saml_sso_path(tenant_id))
290}

292/// The `return_to` of a SAML login hop: the tenant's
293/// [`saml_sso_continue_path`] with the pending request's opaque `handle` and
294/// [`LOGIN_HOP_MARKER`].
295///
296/// `handle` must be the unpadded base64url string the SSO endpoint minted; a
297/// value outside that alphabet is refused (`None`) rather than encoded, because
298/// nothing but such a handle is ever put here. The result is validated before
299/// it is returned, exactly as [`build_return_to_at`]'s is.
300#[must_use]
301pub fn build_saml_return_to(tenant_id: uuid::Uuid, handle: &str) -> Option<String> {
302    if handle.is_empty()
303        || !handle
304            .bytes()
305            .all(|b| b.is_ascii_alphanumeric() || b == b'-' || b == b'_')
306    {
307        return None;
308    }
309    let path = saml_sso_continue_path(tenant_id);
310    let candidate = format!("{path}?handle={handle}&{LOGIN_HOP_MARKER}=1");
311    validate_return_to_at(&candidate, &path).ok()?;
312    Some(candidate)
313}

315/// Build the `return_to` for an authorization request whose raw query string is
316/// `query`.
317///
318/// The result carries [`LOGIN_HOP_MARKER`], which is what makes the hop
319/// terminate (module docs). It is validated before it is returned, so a caller
320/// cannot emit a `Location` this module would refuse to accept back — the two
321/// directions are the same predicate by construction rather than by review.
322///
323/// `None` when the query is empty or the result would not validate. A caller
324/// that gets `None` must not redirect: there is nothing safe to come back to.
325pub fn build_return_to(query: &str) -> Option<String> {
326    if query.is_empty() {
327        return None;
328    }
329    build_return_to_at(AUTHORIZE_PATH, query)
330}

332/// [`build_return_to`], for an authorization request that arrived at
333/// `authorize_path` (T21.6).
334///
335/// The caller passes the path of the request it is answering, so the browser
336/// comes back to the endpoint it left — which on a per-tenant path is what
337/// makes the `iss` of the resulting authorization response the tenant issuer
338/// the client discovered, rather than the deployment root.
339///
340/// `None` on the same two conditions [`build_return_to`] answers `None` on: an
341/// empty query, and a result this module would not accept back.
342#[must_use]
343pub fn build_return_to_at(authorize_path: &str, query: &str) -> Option<String> {
344    if query.is_empty() {
345        return None;
346    }
347    let candidate = format!("{authorize_path}?{query}&{LOGIN_HOP_MARKER}=1");
348    validate_return_to_at(&candidate, authorize_path).ok()?;
349    Some(candidate)
350}

352/// The marker a **consent** hop carries (W7).
353///
354/// A second marker rather than a reuse of [`LOGIN_HOP_MARKER`], and the reason
355/// is a defect the shared one would have caused. The login marker means "this
356/// request has been through a first-party page once", and W7's termination rule
357/// needs something narrower: "this end user has already been *asked about
358/// consent* and did not give it". Those differ exactly when both ceremonies are
359/// needed — a request carrying `prompt=consent` and `address` goes to the
360/// sign-in page first, and comes back carrying the login marker without anybody
361/// having been asked a thing about consent. Read as a consent leg, that is
362/// `access_denied` for a user who was never shown the question.
363///
364/// With two markers each ceremony terminates on its own: at most one login hop
365/// and at most one consent hop per authorization request, in that order,
366/// because authentication has to be settled before there is a person to ask.
367pub const CONSENT_HOP_MARKER: &str = "axiam_consent_hop";

369/// The sign-in page's **Cancel**, on its way back to the authorization request.
370///
371/// # Why the protocol needs a way to say no
372///
373/// RFC 6749 §4.1.2.1 and OIDC Core §3.1.2.6 both require `access_denied` to be
374/// returned to the relying party when the end user refuses the request, and
375/// until this marker existed AXIAM had no way for them to refuse one. The
376/// consent screen has a decline button, but it is shown only when a *sensitive*
377/// scope is asked for; a request for `openid profile` reached a sign-in page
378/// whose only two outcomes were "authenticate" and "close the tab". Closing the
379/// tab is not a protocol answer: the relying party is left waiting on a
380/// response that will never arrive, and cannot tell a refusal from a crash.
381///
382/// The OIDF suite states the same requirement as an instruction to a human —
383/// `fapi2-security-profile-final-user-rejects-authentication` says "the tester
384/// MUST press 'cancel' on the login screen or deny consent" — and there was no
385/// cancel to press.
386///
387/// # Why a third marker rather than a value on the login one
388///
389/// It answers a different question. [`LOGIN_HOP_MARKER`] means "this browser
390/// has been sent to sign in once already", which is a statement about
391/// termination; this one means "the person said no", which is a statement about
392/// the outcome, and a request can legitimately carry both. Folding them into
393/// one parameter would make `axiam_login_hop=declined` mean two things at once
394/// and put the loop guard at the mercy of how the decline was spelled.
395///
396/// # What it can and cannot cause
397///
398/// Exactly one thing: `access_denied`, delivered to a `redirect_uri` this
399/// client registered, with the request's own `state`. It is read only on the
400/// anonymous path — a request that resolved a principal from a token ignores it
401/// entirely — and it is not a credential, so forging it onto somebody else's
402/// authorization URL achieves what closing their tab already achieved, only
403/// politely.
404pub const USER_DECLINED_MARKER: &str = "axiam_user_declined";
405
406/// Did the person at the sign-in page decline this authorization request?
407///
408/// Any present value counts, for [`is_return_leg`]'s reason: the marker is a
409/// statement that the cancel control was used, and a browser that rewrote its
410/// value to `0` has still used it.
411pub fn user_declined(marker: Option<&str>) -> bool {
412    marker.is_some()
413}

438/// Build the `Location` that sends the browser to the SPA login page.
439///
440/// Relative on purpose. The SPA and the API are one origin in every shipped
441/// topology (`docker/nginx.conf`, and the `baseURL: "/"` the admin UI is built
442/// with), and they must be for this feature at all: `return_to` is a path on
443/// the **API's** origin, and the `axiam_op_session` cookie the login sets is
444/// scoped to `/oauth2/authorize` on that same origin. A deployment serving the
445/// SPA from another host cannot complete this hop, and emitting an absolute URL
446/// would hide that rather than fix it.
447///
448/// `reauth` asks the SPA to authenticate the user afresh rather than reuse
449/// whatever it already holds. W3 sets it in exactly one case — a browser
450/// arriving with an `axiam_op_session` cookie that resolves to no live session —
451/// because that browser believes it is signed in and is not, and sending it to
452/// a login page that might agree with it is how a hop becomes a loop the guard
453/// then has to catch.
454pub fn build_login_redirect(return_to: &str, reauth: bool) -> String {
455    build_login_redirect_for(return_to, reauth, None, &Cosmetic::NONE)
456}

458/// The presentation an authorization request asked the sign-in page for
459/// (W5, plan §4.5/§4.6).
460///
461/// A struct rather than three more positional arguments on
462/// [`build_login_redirect_for`], which would otherwise take six — two of them
463/// `Option`s a transposed call site would still compile with.
464///
465/// [`Cosmetic::NONE`] is what every request that asked for nothing produces,
466/// and it is the value the *ignore* lane always passes: a client registered
467/// today gets a `/login` URL byte-identical to the one W3 and W4 built, which
468/// is invariant 4 for this wave.
469#[derive(Debug, Clone, Copy, Default)]
470pub struct Cosmetic<'a> {
471    /// The relying party's guess at the identifier the end user will type, to
472    /// be pre-filled into the username field.
473    ///
474    /// **The server performs no lookup on this value, on any path.** It is
475    /// never compared to a user, never used to select a session or a tenant,
476    /// and it is not read at all when a session already exists — the only
477    /// place it is used is here, building a URL for a page that is being shown
478    /// anyway.
479    ///
480    /// That is the enumeration mitigation the plan asks for, and it is worth
481    /// being precise about *why* it is the strong form. The weak form of this
482    /// defence looks up the hint, finds the account or does not, and then
483    /// takes care to answer identically either way. It is one refactor away
484    /// from a timing difference, an audit row, a cache entry or an error
485    /// message that distinguishes the two — because the two branches exist and
486    /// something has to keep them equal. Here there is no branch: the value is
487    /// percent-encoded into a `Location` header and nothing else in this
488    /// server ever reads it. Test **T5.1** asserts the responses for an
489    /// existing and a non-existing hint are byte-identical apart from the
490    /// echoed parameter, and it is asserting a property of the shape of the
491    /// code rather than of anybody's diligence.
492    ///
493    /// Already bounded to [`crate::authn_params::MAX_HINT_LEN`] bytes and
494    /// known to be valid UTF-8 by the time it arrives here: it comes from
495    /// [`crate::authn_params::AuthnRequestParams`], which drops an over-long
496    /// value rather than truncating it.
497    pub login_hint: Option<&'a str>,
498    /// The layout the relying party asked for, already allow-listed.
499    pub display: Option<crate::locale::Display>,
500    /// The language the sign-in page should render in — **the selected one**,
501    /// not the `ui_locales` list that selected it.
502    ///
503    /// The matching happens in [`crate::locale::select_ui_locale`] precisely so
504    /// that this field can be a five-value enum. See that module for why the
505    /// raw value must never reach the SPA.
506    pub ui_locale: Option<crate::locale::Locale>,
507}

509impl Cosmetic<'_> {
510    /// A request that asked for no particular presentation — and the value the
511    /// ignore lane always uses.
512    pub const NONE: Self = Self {
513        login_hint: None,
514        display: None,
515        ui_locale: None,
516    };
517
518    /// Whether anything at all was asked for.
519    pub const fn is_empty(&self) -> bool {
520        self.login_hint.is_none() && self.display.is_none() && self.ui_locale.is_none()
521    }
522}

524impl<'a> Cosmetic<'a> {
525    /// Assemble the presentation from a parsed request, on the honour lane.
526    ///
527    /// This is the **only** function that turns
528    /// [`crate::authn_params::AuthnRequestParams`] into something a URL builder
529    /// accepts, and it exists so that three properties are readable in one
530    /// place instead of being spread across two call sites in the REST layer:
531    ///
532    /// 1. `display` and `ui_locales` are *matched here* and forwarded as
533    ///    types, so the raw values stop at this function (T6.2).
534    /// 2. `login_hint` is forwarded verbatim and nothing looks it up (T5.1;
535    ///    see [`Cosmetic::login_hint`]).
536    /// 3. **`claims_locales` is not read.** It has no field on [`Cosmetic`],
537    ///    it is not a parameter of this function, and `select_ui_locale` is
538    ///    called with `params.ui_locales` at exactly one call site — this one.
539    ///
540    /// That third property is the one worth a paragraph. `claims_locales` and
541    /// `ui_locales` are adjacent in OIDC Core §3.1.2.1, carry the same BCP 47
542    /// syntax, and differ by a prefix; one selects the language of the *page*
543    /// and the other the language of *claim values*, of which AXIAM has none.
544    /// A future edit reaching for "the locale the relying party asked for"
545    /// could reach for either and look right in review. Having exactly one
546    /// call site — pinned by a test that `claims_locales=it` alone leaves the
547    /// page in the deployment default — is what makes the wrong one visible.
548    ///
549    /// `tenant_default` is the tenant's configured language, already parsed;
550    /// it is consulted only when the relying party asked for nothing this
551    /// deployment ships.
552    pub fn from_params(
553        params: &'a crate::authn_params::AuthnRequestParams,
554        tenant_default: Option<crate::locale::Locale>,
555    ) -> Self {
556        Self {
557            login_hint: params.login_hint.as_deref(),
558            display: params
559                .display
560                .as_deref()
561                .and_then(crate::locale::Display::from_wire),
562            ui_locale: crate::locale::select_ui_locale(
563                params.ui_locales.as_deref(),
564                tenant_default,
565            ),
566        }
567    }
568}

570/// [`build_login_redirect`], plus the one factor the sign-in page must demand
571/// (W4, plan §4.4) and the presentation it was asked for (W5, plan §4.5/§4.6).
572///
573/// `required_acr` is a member of the closed two-value vocabulary
574/// ([`crate::acr::Acr`]) and nothing else can be passed, which is the whole
575/// design of the step-up: **the page never chooses an authentication context
576/// class.** It learns which factor to insist on, from an allow-list of two,
577/// and the class the resulting session earns is derived afterwards from what
578/// the session actually proves ([`crate::acr::acr_for`]). A `String` parameter
579/// here would be the first place an operator-chosen or relying-party-chosen
580/// ACR could reach a user-facing page, and from there the temptation to echo
581/// it into the claim is one refactor away.
582///
583/// A step-up is always a `reauth` in practice — the point is to authenticate
584/// afresh — but the two are separate parameters because they answer different
585/// questions: `reauth` says *do not trust what this browser already holds*,
586/// and `acr` says *what to ask it for*.
587///
588/// `cosmetic` follows the same rule for the same reason (see [`Cosmetic`]).
589/// Passing [`Cosmetic::NONE`] reproduces the W3/W4 URL byte for byte, which is
590/// what the ignore lane does and what its test asserts.
591///
592/// This is the **only** place a `/login` URL is built. Keeping it that way is
593/// what makes "the raw `ui_locales` appears in no redirect the server builds"
594/// (T6.2) a claim about one function rather than a claim about the tree.
595pub fn build_login_redirect_for(
596    return_to: &str,
597    reauth: bool,
598    required_acr: Option<crate::acr::Acr>,
599    cosmetic: &Cosmetic<'_>,
600) -> String {
601    let mut location = format!("{LOGIN_PATH}?return_to={}", encode(return_to));
602    if reauth {
603        location.push_str("&reauth=1");
604    }
605    if let Some(acr) = required_acr {
606        location.push_str("&acr=");
607        location.push_str(&encode(acr.as_str()));
608    }
609    // W5. `login_hint` is the only one of the three that is not a type, so it
610    // is the only one that is encoded rather than merely written; the other
611    // two can emit nothing but short lower-case ASCII identifiers and are
612    // encoded anyway, because a builder that treats its inputs differently
613    // depending on how much it trusts them is one whose next parameter gets
614    // the wrong treatment.
615    if let Some(hint) = cosmetic.login_hint {
616        location.push_str("&login_hint=");
617        location.push_str(&encode(hint));
618    }
619    if let Some(display) = cosmetic.display {
620        location.push_str("&display=");
621        location.push_str(&encode(display.as_str()));
622    }
623    if let Some(locale) = cosmetic.ui_locale {
624        location.push_str("&ui_locale=");
625        location.push_str(&encode(locale.as_tag()));
626    }
627    location
628}

630/// The SPA route that asks the end user to consent to a scope release (W7).
631///
632/// A sibling of [`LOGIN_PATH`] rather than a query flag on it, because the two
633/// pages ask different questions of a different person-state: `/login` asks an
634/// anonymous browser to prove who it is, `/consent` asks a signed-in person
635/// what they are willing to hand over. Conflating them is how a consent
636/// ceremony turns into "type your password again", which is a dark pattern
637/// whatever the specification says.
638pub const CONSENT_PATH: &str = "/consent";

640/// Build the redirect for an interaction the authorization endpoint asked for.
641///
642/// The one place either first-party page's URL is chosen, so that "which page,
643/// with which flags" is a single exhaustive decision rather than a condition
644/// the two call sites could answer differently.
645///
646/// # `/login` — every reason but one
647///
648/// Byte-identical to what [`build_login_redirect_for`] built for W4 and W5:
649/// `reauth=1`, the required `acr` when there is one, and the full cosmetic
650/// presentation. This is the path invariant 4's golden tests pin.
651///
652/// # `/consent` — [`crate::honour::Reason::ConsentRequired`]
653///
654/// No `reauth`, because the end user is authenticated and re-authenticating
655/// answers no question about consent. No `acr`, because the sign-in ceremony
656/// is not being repeated and naming a factor for a page that will not run one
657/// would be telling it something untrue.
658///
659/// And no `login_hint`: it is a guess at the identifier somebody is about to
660/// type, and on this page nobody is about to type one. Dropping it is not
661/// tidiness — it is the difference between a relying party's opaque string
662/// reaching a page that renders it into a form field and it reaching no page
663/// at all. `display` and `ui_locale` are kept, because how to render and in
664/// which language are questions the consent page really does have to answer,
665/// and both are closed vocabularies (`crate::authn_params::Display`,
666/// `crate::locale::Locale`) rather than relying-party strings.
667pub fn build_interaction_redirect(
668    return_to: &str,
669    reason: crate::honour::Reason,
670    required_acr: Option<crate::acr::Acr>,
671    cosmetic: &Cosmetic<'_>,
672) -> String {
673    if reason.requires_reauthentication() {
674        return build_login_redirect_for(return_to, true, required_acr, cosmetic);
675    }
676    let mut location = format!("{CONSENT_PATH}?return_to={}", encode(return_to));
677    if let Some(display) = cosmetic.display {
678        location.push_str("&display=");
679        location.push_str(&encode(display.as_str()));
680    }
681    if let Some(locale) = cosmetic.ui_locale {
682        location.push_str("&ui_locale=");
683        location.push_str(&encode(locale.as_tag()));
684    }
685    location
686}

688/// Percent-encode one query-parameter value.
689///
690/// `byte_serialize` rather than a hand-rolled escape: it is the encoder the
691/// SPA's `URLSearchParams` is the decoder for, and the two have to agree about
692/// `+`, `&`, `=` and every non-ASCII byte of a `login_hint` that is somebody's
693/// name.
694fn encode(value: &str) -> String {
695    url::form_urlencoded::byte_serialize(value.as_bytes()).collect()
696}
