1//! Mutual-TLS client authentication and certificate-bound tokens
2//! (RFC 8705) — X5.1.
3//!
4//! Two mechanisms live here, and RFC 8705 keeps them deliberately separate
5//! because they answer different questions:
6//!
7//! - **§2, client authentication.** *Who is this client?* The certificate
8//!   replaces the shared secret at the token endpoint. AXIAM implements both
9//!   variants: `tls_client_auth` (PKI — the certificate chains to a CA the
10//!   deployment's listener trusts, and AXIAM matches a registered subject DN
11//!   or SAN) and `self_signed_tls_client_auth` (the certificate *is* the
12//!   registered credential, matched by thumbprint).
13//! - **§3, sender-constrained tokens.** *May this bearer use this token?* The
14//!   access token carries a `cnf.x5t#S256` confirmation naming the
15//!   certificate it was issued to, so a stolen token is inert without the
16//!   corresponding private key.
17//!
18//! # Where the trust actually comes from
19//!
20//! Nothing in this module verifies a certificate chain, and it must not: by
21//! the time a [`PresentedCertificate`] exists, rustls has already verified the
22//! peer chain against the configured client-CA bundle during the TLS 1.3
23//! handshake (`axiam-server`'s `on_connect` hook → `VerifiedClientCert`). This
24//! module's job is the *matching* step — deciding whether the certificate the
25//! transport verified is the one this particular client registered.
26//!
27//! That division is why the `X-Client-Certificate` proxy header, which the
28//! device-auth extractor accepts as a fallback, is **not** accepted here. That
29//! header is an assertion by a reverse proxy; for device authentication, where
30//! the certificate is looked up against a per-tenant issued-certificate table,
31//! a deployment can reasonably choose to trust its own proxy. For OAuth2
32//! client authentication under a FAPI profile it cannot: FAPI 2.0 requires the
33//! authorization server to authenticate the client, and a header is forgeable
34//! by anything that can reach the server on a non-mTLS port. So the header path
35//! is absent by construction rather than gated by configuration — there is no
36//! setting that turns it on.
37//!
38//! # Self-signed certificates and the `x5t#S256` shortcut
39//!
40//! RFC 8705 §2.2 registers a self-signed client's certificates inside its
41//! `jwks`/`jwks_uri`. AXIAM registers the SHA-256 thumbprint instead. The
42//! comparison the spec performs against a self-signed certificate reduces to
43//! an equality check against a registered key, and a thumbprint is that check
44//! without a JWKS parser on the authentication path. What it costs is
45//! JWKS-driven rotation: a self-signed client's new certificate must be
46//! registered rather than merely published. The operator guide says so.
47

57/// The single `error_description` every mTLS client-authentication failure
58/// returns, whatever actually went wrong.
59///
60/// Same reasoning as `token::CLIENT_AUTH_FAILED`, which it deliberately
61/// matches word for word: an unauthenticated caller must not be able to tell
62/// "no certificate presented" from "certificate presented but the DN did not
63/// match" from "this client does not use mTLS at all", because each of those
64/// answers is a fact about a client id they have not authenticated as.
65///
66/// The distinctions are kept — they go to the tracing log, where an operator
67/// debugging a genuine onboarding problem can see them and an attacker cannot.
68pub(crate) const MTLS_AUTH_FAILED: &str = "invalid client credentials";

70/// A client certificate that the TLS layer verified on this connection.
71///
72/// Constructed only from a chain rustls accepted.
73///
74/// # Why the X.509 parse is lazy
75///
76/// The thumbprint is computed eagerly, because it is one SHA-256 over bytes
77/// already in memory and *every* certificate-bound token needs it. The subject
78/// DN and SANs are not: they are needed only by the `tls_client_auth` variant
79/// of client authentication, and parsing an X.509 structure to extract and
80/// allocate strings nobody reads is real work on a hot path.
81///
82/// The distinction matters because these two costs land on different
83/// populations. Certificate *binding* is what X5.1 advertises as cheap, and it
84/// pays only the SHA-256. A deployment running mTLS with ordinary
85/// `client_secret_post` clients — the IoT shape AXIAM targets — would
86/// otherwise have paid for a DN parse on every token request in exchange for
87/// nothing at all. Eager parsing was the first cut of this type; the
88/// benchmark's A/B is what made the asymmetry visible.
89#[derive(Debug, Clone)]
90pub struct PresentedCertificate {
91    /// DER encoding of the verified leaf certificate.
92    der: Vec<u8>,
93    /// Base64url (no padding) SHA-256 digest of [`Self::der`] — the
94    /// `x5t#S256` value of RFC 8705 §3.1.
95    pub thumbprint_s256: String,
96}

98/// The identity fields of a certificate, parsed on demand.
99///
100/// Separate from [`PresentedCertificate`] so the type system records which
101/// operations need an X.509 parse and which do not: you cannot read a subject
102/// DN without having called [`PresentedCertificate::identity`], and that call
103/// is the parse.
104#[derive(Debug, Clone)]
105pub struct CertificateIdentity {
106    /// Subject distinguished name in RFC 4514 string form.
107    pub subject_dn: String,
108    /// `dNSName` SAN entries, in certificate order.
109    pub san_dns: Vec<String>,
110    /// `uniformResourceIdentifier` SAN entries, in certificate order.
111    pub san_uri: Vec<String>,
112}
113
114impl PresentedCertificate {
115    /// Wrap a DER leaf certificate and compute its `x5t#S256` thumbprint.
116    ///
117    /// Infallible: a SHA-256 over arbitrary bytes always succeeds, and the
118    /// bytes are not interpreted here. Anything that needs them to be a
119    /// well-formed certificate goes through [`Self::identity`], which reports
120    /// the parse failure at the point where it actually matters.
121    pub fn from_der(der: &[u8]) -> Self {
122        Self {
123            der: der.to_vec(),
124            thumbprint_s256: thumbprint_s256(der),
125        }
126    }
127
128    /// Parse the subject DN and SANs (RFC 8705 §2.1.2 matching inputs).
129    ///
130    /// Returns `Err` only when the bytes are not a parseable X.509
131    /// certificate. In the native-mTLS path that cannot happen — rustls parsed
132    /// the same bytes to verify the chain — but the fallible signature is kept
133    /// so a future caller cannot introduce an unchecked `unwrap`.
134    pub fn identity(&self) -> Result<CertificateIdentity, String> {
135        let (_, cert) =
136            parse_x509_certificate(&self.der).map_err(|e| format!("parse client cert DER: {e}"))?;
137
138        let mut san_dns = Vec::new();
139        let mut san_uri = Vec::new();
140        if let Ok(Some(ext)) = cert.subject_alternative_name() {
141            for name in &ext.value.general_names {
142                match name {
143                    GeneralName::DNSName(s) => san_dns.push((*s).to_owned()),
144                    GeneralName::URI(s) => san_uri.push((*s).to_owned()),
145                    _ => {}
146                }
147            }
148        }
149
150        Ok(CertificateIdentity {
151            subject_dn: cert.subject().to_string(),
152            san_dns,
153            san_uri,
154        })
155    }
156}

158/// RFC 8705 §3.1 `x5t#S256`: base64url-encoded, unpadded SHA-256 of the DER
159/// certificate.
160///
161/// Base64url **without** padding is not a stylistic choice: the value travels
162/// inside a JWT claim and an introspection response, and RFC 7515 §2 defines
163/// base64url encoding in JOSE as omitting the `=` padding. A padded value
164/// would not compare equal at a conforming resource server.
165pub fn thumbprint_s256(der: &[u8]) -> String {
166    base64::engine::general_purpose::URL_SAFE_NO_PAD.encode(Sha256::digest(der))
167}
168
169/// Compare two thumbprints without leaking, through timing, how many leading
170/// characters matched.
171///
172/// A thumbprint is a public value in most threat models — it is derived from a
173/// certificate the client transmits in the clear during the handshake — so
174/// this is belt-and-braces rather than load-bearing. It is cheap, it is the
175/// same discipline `client_secret` verification already applies, and the one
176/// case where it *is* load-bearing is `self_signed_tls_client_auth`, where the
177/// registered thumbprint is the entire credential and an attacker who could
178/// grind it character by character would be forging a client identity rather
179/// than merely recognising one.
180fn thumbprints_match(a: &str, b: &str) -> bool {
181    // `ConstantTimeEq` on unequal-length inputs short-circuits, which leaks
182    // only the length — and both operands are fixed-length base64url SHA-256
183    // digests whenever either is well-formed.
184    a.as_bytes().ct_eq(b.as_bytes()).into()
185}

187/// Authenticate a client by the certificate it presented (RFC 8705 §2).
188///
189/// Called *instead of* secret verification when the client's registered
190/// [`ClientAuthMethod`] is an mTLS one. Returns `Ok(())` only when the
191/// presented certificate matches what this specific client registered.
192///
193/// # The three ways this fails, and why they all look identical
194///
195/// 1. **No certificate on the connection.** The client reached a listener that
196///    does not request client certificates, or presented none. This is the
197///    failure an operator hits most often during onboarding, and the tracing
198///    line says so explicitly.
199/// 2. **The client registered no expectation.** A client whose method is
200///    `tls_client_auth` but which has no `tls_client_auth_subject_dn`,
201///    `…_san_dns` or `…_san_uri` cannot be authenticated by anything, and this
202///    refuses rather than matching everything. Registration validation is meant
203///    to make the state unreachable; this is the second line, because a row
204///    edited directly in the database bypasses registration validation and the
205///    failure mode of guessing here is *authenticating every certificate*.
206/// 3. **The certificate does not match.** A real certificate, verified by
207///    rustls, belonging to somebody else.
208///
209/// All three answer `invalid_client` with [`MTLS_AUTH_FAILED`]. See that
210/// constant for why.
211pub fn authenticate_mtls_client(
212    client: &OAuth2Client,
213    presented: Option<&PresentedCertificate>,
214) -> Result<(), OAuth2Error> {
215    let method = client.token_endpoint_auth_method;
216    debug_assert!(
217        method.is_mtls(),
218        "authenticate_mtls_client called for a non-mTLS auth method"
219    );
220
221    let Some(cert) = presented else {
222        tracing::debug!(
223            client_id = %client.client_id,
224            method = method.as_str(),
225            "mTLS client authentication failed: no verified client certificate on this \
226             connection (is the client reaching the mTLS listener?)"
227        );
228        return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
229    };
230
231    let matched = match method {
232        ClientAuthMethod::SelfSignedTlsClientAuth => {
233            let registered = &client.self_signed_tls_client_auth_thumbprints;
234            if registered.is_empty() {
235                tracing::warn!(
236                    client_id = %client.client_id,
237                    "client is registered for self_signed_tls_client_auth but has no \
238                     registered certificate thumbprint; it cannot authenticate"
239                );
240                return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
241            }
242            // Every candidate is compared even after a match, so the number of
243            // comparisons does not reveal the matching thumbprint's position
244            // in the list.
245            registered.iter().fold(false, |found, t| {
246                thumbprints_match(t, &cert.thumbprint_s256) | found
247            })
248        }
249        ClientAuthMethod::TlsClientAuth => {
250            match client.mtls_binding_count() {
251                0 => {
252                    tracing::warn!(
253                        client_id = %client.client_id,
254                        "client is registered for tls_client_auth but registered no expected \
255                         subject DN or SAN; it cannot authenticate"
256                    );
257                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
258                }
259                // RFC 8705 §2.1.2 permits exactly one. Registration validation
260                // rejects more, but a row that acquired two some other way must
261                // not be authenticated by whichever happens to match — that is
262                // an OR over credentials nobody intended to grant.
263                n if n > 1 => {
264                    tracing::error!(
265                        client_id = %client.client_id,
266                        registered = n,
267                        "client has more than one tls_client_auth_* parameter registered, \
268                         which RFC 8705 §2.1.2 forbids; refusing to guess which one \
269                         authenticates"
270                    );
271                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
272                }
273                _ => {}
274            }
275
276            // The X.509 parse happens here and nowhere else — this is the one
277            // branch that needs a DN or a SAN. A parse failure is an
278            // authentication failure, never a pass: rustls verified these
279            // bytes, so unparseable-here means something is deeply wrong and
280            // the only safe reading is "this is not the registered client".
281            let identity = match cert.identity() {
282                Ok(identity) => identity,
283                Err(e) => {
284                    tracing::error!(
285                        client_id = %client.client_id,
286                        error = %e,
287                        "could not parse a client certificate rustls had already verified; \
288                         refusing the authentication"
289                    );
290                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
291                }
292            };
293
294            if let Some(expected) = non_empty(client.tls_client_auth_subject_dn.as_deref()) {
295                // The DN comparison is exact on the RFC 4514 string form. RFC
296                // 8705 §2.1.2 describes this as a comparison of the DN, and a
297                // structural comparison would be more faithful — but a
298                // normalising comparison is exactly where DN-matching CVEs
299                // live, and an exact match can only ever be *too strict*,
300                // which fails an onboarding rather than authenticating a
301                // stranger. The operator guide tells operators to copy the DN
302                // out of `openssl x509 -noout -subject -nameopt rfc2253`.
303                expected == identity.subject_dn
304            } else if let Some(expected) = non_empty(client.tls_client_auth_san_dns.as_deref()) {
305                // DNS names are case-insensitive (RFC 4343). No wildcard
306                // handling: a wildcard registered here would authenticate
307                // every certificate a CA issued under that suffix as this
308                // client, which is not an authentication decision anybody
309                // should be able to make by typing `*`.
310                identity
311                    .san_dns
312                    .iter()
313                    .any(|got| got.eq_ignore_ascii_case(expected))
314            } else if let Some(expected) = non_empty(client.tls_client_auth_san_uri.as_deref()) {
315                // URIs are compared exactly: unlike a DNS name, no component
316                // of a URI is case-insensitive in a way that is safe to assume
317                // here.
318                identity.san_uri.iter().any(|got| got == expected)
319            } else {
320                // Unreachable: `mtls_binding_count()` returned 1 above, and it
321                // counts exactly these three fields under the same
322                // non-emptiness rule.
323                false
324            }
325        }
326        // Neither of these authenticates by certificate. Reaching here at all
327        // means a caller routed a non-mTLS client into the mTLS path, which the
328        // `debug_assert` above catches in tests; in release the answer is
329        // "not authenticated", never "authenticated by default".
330        ClientAuthMethod::ClientSecretPost | ClientAuthMethod::PrivateKeyJwt => false,
331    };
332
333    if !matched {
334        tracing::debug!(
335            client_id = %client.client_id,
336            method = method.as_str(),
337            "mTLS client authentication failed: the verified client certificate does not \
338             match this client's registered expectation"
339        );
340        return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
341    }
342
343    Ok(())
344}

346/// A registered value counts only when it is present *and* non-blank.
347///
348/// Mirrors `OAuth2Client::mtls_binding_count`'s rule exactly. The two must
349/// agree: if the counter treated `Some("")` as registered and the matcher
350/// treated it as absent, a client could reach the `else` branch with a count
351/// of one and authenticate nothing — or, worse, the reverse.
352fn non_empty(value: Option<&str>) -> Option<&str> {
353    value.map(str::trim).filter(|v| !v.is_empty())
354}

622    /// Every refusal returns the identical description, so a caller cannot
623    /// distinguish "no certificate" from "wrong certificate" from "client
624    /// registered nothing" — each of which is a fact about a client id they
625    /// have not authenticated as.
626    #[test]
627    fn every_failure_reports_the_same_description() {
628        let (der_a, _) = cert_with_sans(&["a.example.com"]);
629        let (_, cert_b) = cert_with_sans(&["b.example.com"]);
630
631        let mut wrong_cert = client(ClientAuthMethod::SelfSignedTlsClientAuth);
632        wrong_cert.self_signed_tls_client_auth_thumbprints = vec![thumbprint_s256(&der_a)];
633
634        let unregistered = client(ClientAuthMethod::TlsClientAuth);
635
636        let mut no_cert = client(ClientAuthMethod::TlsClientAuth);
637        no_cert.tls_client_auth_san_dns = Some("a.example.com".into());
638
639        let descriptions: Vec<String> = vec![
640            authenticate_mtls_client(&wrong_cert, Some(&cert_b)).unwrap_err(),
641            authenticate_mtls_client(&unregistered, Some(&cert_b)).unwrap_err(),
642            authenticate_mtls_client(&no_cert, None).unwrap_err(),
643        ]
644        .into_iter()
645        .map(|e| match e {
646            OAuth2Error::InvalidClient(d) => d,
647            other => panic!("expected invalid_client, got {other:?}"),
648        })
649        .collect();
650
651        assert!(
652            descriptions.iter().all(|d| d == MTLS_AUTH_FAILED),
653            "all mTLS auth failures must share one description, got {descriptions:?}"
654        );
655    }
