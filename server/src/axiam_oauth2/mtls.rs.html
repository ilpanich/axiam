1//! Mutual-TLS client authentication and certificate-bound tokens
2//! (RFC 8705) — X5.1.
3//!
4//! Two mechanisms live here, and RFC 8705 keeps them deliberately separate
5//! because they answer different questions:
6//!
7//! - **§2, client authentication.** *Who is this client?* The certificate
8//!   replaces the shared secret at the token endpoint. AXIAM implements both
9//!   variants: `tls_client_auth` (PKI — the certificate chains to a CA the
10//!   deployment's listener trusts, and AXIAM matches a registered subject DN
11//!   or SAN) and `self_signed_tls_client_auth` (the certificate *is* the
12//!   registered credential, matched by thumbprint).
13//! - **§3, sender-constrained tokens.** *May this bearer use this token?* The
14//!   access token carries a `cnf.x5t#S256` confirmation naming the
15//!   certificate it was issued to, so a stolen token is inert without the
16//!   corresponding private key.
17//!
18//! # Where the trust actually comes from
19//!
20//! Nothing in this module verifies a certificate chain, and it must not: by
21//! the time a [`PresentedCertificate`] exists, rustls has already verified the
22//! peer chain against the configured client-CA bundle during the TLS 1.3
23//! handshake (`axiam-server`'s `on_connect` hook → `VerifiedClientCert`). This
24//! module's job is the *matching* step — deciding whether the certificate the
25//! transport verified is the one this particular client registered.
26//!
27//! That division is why the `X-Client-Certificate` proxy header, which the
28//! device-auth extractor accepts as a fallback, is **not** accepted here. That
29//! header is an assertion by a reverse proxy; for device authentication, where
30//! the certificate is looked up against a per-tenant issued-certificate table,
31//! a deployment can reasonably choose to trust its own proxy. For OAuth2
32//! client authentication under a FAPI profile it cannot: FAPI 2.0 requires the
33//! authorization server to authenticate the client, and a header is forgeable
34//! by anything that can reach the server on a non-mTLS port. So the header path
35//! is absent by construction rather than gated by configuration — there is no
36//! setting that turns it on.
37//!
38//! # Self-signed certificates and the `x5t#S256` shortcut
39//!
40//! RFC 8705 §2.2 registers a self-signed client's certificates inside its
41//! `jwks`/`jwks_uri`. AXIAM registers the SHA-256 thumbprint instead. The
42//! comparison the spec performs against a self-signed certificate reduces to
43//! an equality check against a registered key, and a thumbprint is that check
44//! without a JWKS parser on the authentication path. What it costs is
45//! JWKS-driven rotation: a self-signed client's new certificate must be
46//! registered rather than merely published. The operator guide says so.
47

58/// The single `error_description` every mTLS client-authentication failure
59/// returns, whatever actually went wrong.
60///
61/// Same reasoning as `token::CLIENT_AUTH_FAILED`, which it deliberately
62/// matches word for word: an unauthenticated caller must not be able to tell
63/// "no certificate presented" from "certificate presented but the DN did not
64/// match" from "this client does not use mTLS at all", because each of those
65/// answers is a fact about a client id they have not authenticated as.
66///
67/// The distinctions are kept — they go to the tracing log, where an operator
68/// debugging a genuine onboarding problem can see them and an attacker cannot.
69pub(crate) const MTLS_AUTH_FAILED: &str = "invalid client credentials";

71/// A client certificate that the TLS layer accepted on this connection.
72///
73/// Constructed only from a certificate rustls accepted — which, under
74/// `client_auth = optional_self_signed`, includes one that chains to no
75/// configured anchor. [`Self::trust`] records which, and
76/// [`authenticate_mtls_client`] is where that distinction is spent.
77///
78/// # Why the X.509 parse is lazy
79///
80/// The thumbprint is computed eagerly, because it is one SHA-256 over bytes
81/// already in memory and *every* certificate-bound token needs it. The subject
82/// DN and SANs are not: they are needed only by the `tls_client_auth` variant
83/// of client authentication, and parsing an X.509 structure to extract and
84/// allocate strings nobody reads is real work on a hot path.
85///
86/// The distinction matters because these two costs land on different
87/// populations. Certificate *binding* is what X5.1 advertises as cheap, and it
88/// pays only the SHA-256. A deployment running mTLS with ordinary
89/// `client_secret_post` clients — the IoT shape AXIAM targets — would
90/// otherwise have paid for a DN parse on every token request in exchange for
91/// nothing at all. Eager parsing was the first cut of this type; the
92/// benchmark's A/B is what made the asymmetry visible.
93#[derive(Debug, Clone)]
94pub struct PresentedCertificate {
95    /// DER encoding of the verified leaf certificate.
96    der: Vec<u8>,
97    /// Base64url (no padding) SHA-256 digest of [`Self::der`] — the
98    /// `x5t#S256` value of RFC 8705 §3.1.
99    pub thumbprint_s256: String,
100    /// Whether the TLS layer built a chain for this certificate, or accepted
101    /// it self-asserted (RFC 8705 §2.2).
102    ///
103    /// The distinction is what keeps §2.1 and §2.2 apart at the one point
104    /// where it matters. It is *not* a property of the certificate — the same
105    /// bytes would be [`CertTrust::ChainedToAnchor`] on a listener whose
106    /// anchor set includes their issuer — so it has to be carried from the
107    /// handshake rather than recomputed here.
108    pub trust: CertTrust,
109}

111/// The identity fields of a certificate, parsed on demand.
112///
113/// Separate from [`PresentedCertificate`] so the type system records which
114/// operations need an X.509 parse and which do not: you cannot read a subject
115/// DN without having called [`PresentedCertificate::identity`], and that call
116/// is the parse.
117#[derive(Debug, Clone)]
118pub struct CertificateIdentity {
119    /// Subject distinguished name as `x509_parser` renders it: attributes in
120    /// **certificate (DER) order**, separated by `", "`.
121    pub subject_dn: String,
122    /// The same name in **RFC 2253** form: attributes in reverse order,
123    /// separated by `","` with no space.
124    ///
125    /// Both are carried because both are correct renderings of one name, and a
126    /// registration may legitimately hold either. RFC 2253 §2.1 specifies the
127    /// reversed order, and it is what `openssl x509 -nameopt rfc2253` prints —
128    /// which is what the operator guide tells operators to copy. `x509_parser`
129    /// prints DER order with a space.
130    ///
131    /// Until this field existed, only the first was compared, so a DN copied by
132    /// following the documentation could never match:
133    ///
134    /// ```text
135    /// registered   O=axiam-conformance,CN=axiam-conformance-mtls
136    /// compared to  CN=axiam-conformance-mtls, O=axiam-conformance
137    /// ```
138    ///
139    /// Every `tls_client_auth` client onboarded that way authenticated nothing.
140    /// It cost the FAPI 2.0 conformance lane 89 module failures, all at PAR,
141    /// because every FAPI flow begins there.
142    pub subject_dn_rfc2253: String,
143    /// `dNSName` SAN entries, in certificate order.
144    pub san_dns: Vec<String>,
145    /// `uniformResourceIdentifier` SAN entries, in certificate order.
146    pub san_uri: Vec<String>,
147}
148
149impl PresentedCertificate {
150    /// Wrap a DER leaf certificate and compute its `x5t#S256` thumbprint.
151    ///
152    /// `trust` says what the TLS handshake established about these bytes and
153    /// has no default: the two levels authorise different things, so the caller
154    /// states which one it observed. See [`CertTrust`].
155    ///
156    /// Infallible: a SHA-256 over arbitrary bytes always succeeds, and the
157    /// bytes are not interpreted here. Anything that needs them to be a
158    /// well-formed certificate goes through [`Self::identity`], which reports
159    /// the parse failure at the point where it actually matters.
160    pub fn from_der(der: &[u8], trust: CertTrust) -> Self {
161        Self {
162            der: der.to_vec(),
163            thumbprint_s256: thumbprint_s256(der),
164            trust,
165        }
166    }
167
168    /// Parse the subject DN and SANs (RFC 8705 §2.1.2 matching inputs).
169    ///
170    /// Returns `Err` only when the bytes are not a parseable X.509
171    /// certificate. In the native-mTLS path that cannot happen — rustls parsed
172    /// the same bytes to verify the chain — but the fallible signature is kept
173    /// so a future caller cannot introduce an unchecked `unwrap`.
174    pub fn identity(&self) -> Result<CertificateIdentity, String> {
175        let (_, cert) =
176            parse_x509_certificate(&self.der).map_err(|e| format!("parse client cert DER: {e}"))?;
177
178        let mut san_dns = Vec::new();
179        let mut san_uri = Vec::new();
180        if let Ok(Some(ext)) = cert.subject_alternative_name() {
181            for name in &ext.value.general_names {
182                match name {
183                    GeneralName::DNSName(s) => san_dns.push((*s).to_owned()),
184                    GeneralName::URI(s) => san_uri.push((*s).to_owned()),
185                    _ => {}
186                }
187            }
188        }
189
190        // RFC 2253 §2.1: the RDNs are emitted in REVERSE of their encoded
191        // order, joined by `,` with no space. Built from the parsed RDN
192        // sequence rather than by rewriting the string above, because a DN
193        // component may legitimately contain an escaped comma and splitting a
194        // formatted DN on `,` would cut one in half.
195        //
196        // Each RDN is rendered by wrapping it in an `X509Name` of its own, so
197        // the LIBRARY does the RFC 4514 escaping and this code only decides the
198        // order and the separator. A single-RDN name renders with no separator
199        // in it at all, which is what makes joining on `,` exact: an escaped
200        // comma inside a value never reaches the join.
201        let subject_dn_rfc2253 = {
202            let mut parts: Vec<String> = cert
203                .subject()
204                .iter_rdn()
205                .map(|rdn| X509Name::new(vec![rdn.clone()], &[]).to_string())
206                .collect();
207            parts.reverse();
208            parts.join(",")
209        };
210
211        Ok(CertificateIdentity {
212            subject_dn: cert.subject().to_string(),
213            subject_dn_rfc2253,
214            san_dns,
215            san_uri,
216        })
217    }
218}

220/// RFC 8705 §3.1 `x5t#S256`: base64url-encoded, unpadded SHA-256 of the DER
221/// certificate.
222///
223/// Base64url **without** padding is not a stylistic choice: the value travels
224/// inside a JWT claim and an introspection response, and RFC 7515 §2 defines
225/// base64url encoding in JOSE as omitting the `=` padding. A padded value
226/// would not compare equal at a conforming resource server.
227pub fn thumbprint_s256(der: &[u8]) -> String {
228    base64::engine::general_purpose::URL_SAFE_NO_PAD.encode(Sha256::digest(der))
229}

231/// Compare two thumbprints without leaking, through timing, how many leading
232/// characters matched.
233///
234/// A thumbprint is a public value in most threat models — it is derived from a
235/// certificate the client transmits in the clear during the handshake — so
236/// this is belt-and-braces rather than load-bearing. It is cheap, it is the
237/// same discipline `client_secret` verification already applies, and the one
238/// case where it *is* load-bearing is `self_signed_tls_client_auth`, where the
239/// registered thumbprint is the entire credential and an attacker who could
240/// grind it character by character would be forging a client identity rather
241/// than merely recognising one.
242fn thumbprints_match(a: &str, b: &str) -> bool {
243    // `ConstantTimeEq` on unequal-length inputs short-circuits, which leaks
244    // only the length — and both operands are fixed-length base64url SHA-256
245    // digests whenever either is well-formed.
246    a.as_bytes().ct_eq(b.as_bytes()).into()
247}

249/// Authenticate a client by the certificate it presented (RFC 8705 §2).
250///
251/// Called *instead of* secret verification when the client's registered
252/// [`ClientAuthMethod`] is an mTLS one. Returns `Ok(())` only when the
253/// presented certificate matches what this specific client registered.
254///
255/// # The three ways this fails, and why they all look identical
256///
257/// 1. **No certificate on the connection.** The client reached a listener that
258///    does not request client certificates, or presented none. This is the
259///    failure an operator hits most often during onboarding, and the tracing
260///    line says so explicitly.
261/// 2. **The client registered no expectation.** A client whose method is
262///    `tls_client_auth` but which has no `tls_client_auth_subject_dn`,
263///    `…_san_dns` or `…_san_uri` cannot be authenticated by anything, and this
264///    refuses rather than matching everything. Registration validation is meant
265///    to make the state unreachable; this is the second line, because a row
266///    edited directly in the database bypasses registration validation and the
267///    failure mode of guessing here is *authenticating every certificate*.
268/// 3. **The certificate does not match.** A real certificate, accepted by
269///    rustls, belonging to somebody else.
270/// 4. **The certificate is not trusted the way the method requires.** A
271///    `tls_client_auth` (§2.1) client presenting a certificate that chains to
272///    no configured anchor, which `client_auth = optional_self_signed` makes
273///    reachable. §2.1 matches a name a CA vouched for; a self-signed
274///    certificate vouches for itself.
275///
276/// All four answer `invalid_client` with [`MTLS_AUTH_FAILED`]. See that
277/// constant for why.
278pub fn authenticate_mtls_client(
279    client: &OAuth2Client,
280    presented: Option<&PresentedCertificate>,
281) -> Result<(), OAuth2Error> {
282    let method = client.token_endpoint_auth_method;
283    debug_assert!(
284        method.is_mtls(),
285        "authenticate_mtls_client called for a non-mTLS auth method"
286    );
287
288    let Some(cert) = presented else {
289        tracing::debug!(
290            client_id = %client.client_id,
291            method = method.as_str(),
292            "mTLS client authentication failed: no verified client certificate on this \
293             connection (is the client reaching the mTLS listener?)"
294        );
295        return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
296    };
297
298    let matched = match method {
299        ClientAuthMethod::SelfSignedTlsClientAuth => {
300            // Deliberately indifferent to `cert.trust`. §2.2's credential is
301            // the certificate itself: the thumbprint comparison below *is* the
302            // authentication, and it is no weaker for the certificate having
303            // chained to a CA as well. This is the one branch a
304            // `CertTrust::SelfAsserted` certificate can reach, and reaching it
305            // still requires an administrator to have registered its exact
306            // SHA-256.
307            let registered = &client.self_signed_tls_client_auth_thumbprints;
308            if registered.is_empty() {
309                tracing::warn!(
310                    client_id = %client.client_id,
311                    "client is registered for self_signed_tls_client_auth but has no \
312                     registered certificate thumbprint; it cannot authenticate"
313                );
314                return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
315            }
316            // Every candidate is compared even after a match, so the number of
317            // comparisons does not reveal the matching thumbprint's position
318            // in the list.
319            registered.iter().fold(false, |found, t| {
320                thumbprints_match(t, &cert.thumbprint_s256) | found
321            })
322        }
323        ClientAuthMethod::TlsClientAuth => {
324            // §2.1 is the PKI method, and its registered subject DN or SAN is
325            // an assertion *by a certificate authority*. A certificate that
326            // chains to nothing asserts its own subject, so matching a DN
327            // against one would authenticate whoever typed that DN into
328            // `openssl req -subj`.
329            //
330            // A no-op until `client_auth = optional_self_signed` existed —
331            // rustls could not have produced an unchained certificate, so this
332            // condition was unreachable. It is written as a guard rather than
333            // left to that invariant precisely because the invariant has now
334            // been made configurable, and the next thing to make it
335            // configurable again would not come past this file.
336            if !cert.trust.is_chained_to_anchor() {
337                tracing::warn!(
338                    client_id = %client.client_id,
339                    "tls_client_auth (RFC 8705 §2.1) refused: the presented certificate \
340                     chains to no configured trust anchor. §2.1 authenticates by a subject \
341                     DN or SAN vouched for by a CA; a client whose certificate is \
342                     self-signed must be registered for self_signed_tls_client_auth (§2.2) \
343                     with its certificate thumbprint"
344                );
345                return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
346            }
347
348            match client.mtls_binding_count() {
349                0 => {
350                    tracing::warn!(
351                        client_id = %client.client_id,
352                        "client is registered for tls_client_auth but registered no expected \
353                         subject DN or SAN; it cannot authenticate"
354                    );
355                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
356                }
357                // RFC 8705 §2.1.2 permits exactly one. Registration validation
358                // rejects more, but a row that acquired two some other way must
359                // not be authenticated by whichever happens to match — that is
360                // an OR over credentials nobody intended to grant.
361                n if n > 1 => {
362                    tracing::error!(
363                        client_id = %client.client_id,
364                        registered = n,
365                        "client has more than one tls_client_auth_* parameter registered, \
366                         which RFC 8705 §2.1.2 forbids; refusing to guess which one \
367                         authenticates"
368                    );
369                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
370                }
371                _ => {}
372            }
373
374            // The X.509 parse happens here and nowhere else — this is the one
375            // branch that needs a DN or a SAN. A parse failure is an
376            // authentication failure, never a pass: rustls verified these
377            // bytes, so unparseable-here means something is deeply wrong and
378            // the only safe reading is "this is not the registered client".
379            let identity = match cert.identity() {
380                Ok(identity) => identity,
381                Err(e) => {
382                    tracing::error!(
383                        client_id = %client.client_id,
384                        error = %e,
385                        "could not parse a client certificate rustls had already verified; \
386                         refusing the authentication"
387                    );
388                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
389                }
390            };
391
392            if let Some(expected) = non_empty(client.tls_client_auth_subject_dn.as_deref()) {
393                // The DN comparison is exact on the RFC 4514 string form. RFC
394                // 8705 §2.1.2 describes this as a comparison of the DN, and a
395                // structural comparison would be more faithful — but a
396                // normalising comparison is exactly where DN-matching CVEs
397                // live, and an exact match can only ever be *too strict*,
398                // which fails an onboarding rather than authenticating a
399                // stranger. The operator guide tells operators to copy the DN
400                // out of `openssl x509 -noout -subject -nameopt rfc2253`.
401                // Compared against BOTH renderings, and this is still an
402                // exact string match — no case folding, no whitespace
403                // stripping, no structural normalisation. The comment above
404                // argues against a normalising comparison and that argument
405                // stands; what changed is that the server now derives every
406                // form it is willing to accept FROM THE CERTIFICATE, and the
407                // registered value must equal one of them exactly.
408                //
409                // Two forms because both are correct renderings of one name and
410                // the operator guide documents the RFC 2253 one. Accepting only
411                // the other meant a DN copied as documented could never match.
412                expected == identity.subject_dn || expected == identity.subject_dn_rfc2253
413            } else if let Some(expected) = non_empty(client.tls_client_auth_san_dns.as_deref()) {
414                // DNS names are case-insensitive (RFC 4343). No wildcard
415                // handling: a wildcard registered here would authenticate
416                // every certificate a CA issued under that suffix as this
417                // client, which is not an authentication decision anybody
418                // should be able to make by typing `*`.
419                identity
420                    .san_dns
421                    .iter()
422                    .any(|got| got.eq_ignore_ascii_case(expected))
423            } else if let Some(expected) = non_empty(client.tls_client_auth_san_uri.as_deref()) {
424                // URIs are compared exactly: unlike a DNS name, no component
425                // of a URI is case-insensitive in a way that is safe to assume
426                // here.
427                identity.san_uri.iter().any(|got| got == expected)
428            } else {
429                // Unreachable: `mtls_binding_count()` returned 1 above, and it
430                // counts exactly these three fields under the same
431                // non-emptiness rule.
432                false
433            }
434        }
435        // None of these authenticates by certificate. Reaching here at all
436        // means a caller routed a non-mTLS client into the mTLS path, which the
437        // `debug_assert` above catches in tests; in release the answer is
438        // "not authenticated", never "authenticated by default".
439        ClientAuthMethod::ClientSecretPost
440        | ClientAuthMethod::ClientSecretBasic
441        | ClientAuthMethod::PrivateKeyJwt => false,
442    };
443
444    if !matched {
445        tracing::debug!(
446            client_id = %client.client_id,
447            method = method.as_str(),
448            "mTLS client authentication failed: the verified client certificate does not \
449             match this client's registered expectation"
450        );
451        return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
452    }
453
454    Ok(())
455}

457/// A registered value counts only when it is present *and* non-blank.
458///
459/// Mirrors `OAuth2Client::mtls_binding_count`'s rule exactly. The two must
460/// agree: if the counter treated `Some("")` as registered and the matcher
461/// treated it as absent, a client could reach the `else` branch with a count
462/// of one and authenticate nothing — or, worse, the reverse.
463fn non_empty(value: Option<&str>) -> Option<&str> {
464    value.map(str::trim).filter(|v| !v.is_empty())
465}

631    /// The DN an operator is TOLD to register must authenticate.
632    ///
633    /// `subject_dn_match_is_exact` below builds its expectation from
634    /// `identity_of(&cert).subject_dn` — it compares the server against itself,
635    /// so it passes no matter which rendering the server happens to use, and it
636    /// passed throughout the period when no documented registration could work.
637    ///
638    /// This one hard-codes both strings. The first is what
639    /// `openssl x509 -noout -subject -nameopt rfc2253` prints, which is what the
640    /// operator guide says to copy; the second is what `x509_parser` renders.
641    /// They differ in RDN order (RFC 2253 §2.1 reverses it) and in the
642    /// separator, and both must authenticate.
643    #[test]
644    fn both_renderings_of_one_name_authenticate() {
645        // TWO RDNs, deliberately: a one-attribute name renders identically in
646        // both forms, so the single-RDN fixture the other tests use cannot
647        // observe an ordering difference at all. This mirrors the conformance
648        // client, whose subject is `/CN=axiam-conformance-mtls/O=axiam-conformance`.
649        let mut params =
650            rcgen::CertificateParams::new(vec!["client.example.com".to_string()]).unwrap();
651        let mut dn = rcgen::DistinguishedName::new();
652        dn.push(rcgen::DnType::CommonName, "axiam-conformance-mtls");
653        dn.push(rcgen::DnType::OrganizationName, "axiam-conformance");
654        params.distinguished_name = dn;
655        let key = rcgen::KeyPair::generate().unwrap();
656        let der = params.self_signed(&key).unwrap().der().to_vec();
657        let cert = PresentedCertificate::from_der(&der, CertTrust::ChainedToAnchor);
658        let identity = identity_of(&cert);
659
660        // Rendered by the library, DER order, ", " separated.
661        assert!(
662            identity.subject_dn.contains(", "),
663            "expected the x509_parser rendering, got {:?}",
664            identity.subject_dn
665        );
666        // RFC 2253: reversed, no space.
667        assert!(
668            !identity.subject_dn_rfc2253.contains(", "),
669            "RFC 2253 form must not contain a space separator, got {:?}",
670            identity.subject_dn_rfc2253
671        );
672
673        // The same attributes, in opposite orders.
674        let mut a: Vec<&str> = identity.subject_dn.split(", ").collect();
675        let mut b: Vec<&str> = identity.subject_dn_rfc2253.split(',').collect();
676        assert_eq!(a.len(), b.len(), "same number of RDNs");
677        b.reverse();
678        assert_eq!(a, b, "the two renderings must name the same RDNs");
679        a.reverse();
680
681        // And a client registered with EITHER string authenticates.
682        for dn in [&identity.subject_dn, &identity.subject_dn_rfc2253] {
683            let mut c = client(ClientAuthMethod::TlsClientAuth);
684            c.tls_client_auth_subject_dn = Some(dn.clone());
685            assert!(
686                authenticate_mtls_client(&c, Some(&cert)).is_ok(),
687                "a client registered with {dn:?} must authenticate"
688            );
689        }
690    }

692    // -- RFC 8705's two trust models (§2.1 vs §2.2) ----------------------
693    //
694    // These pin the OPERATOR-FACING contract — "a self-signed certificate
695    // authenticates a §2.2 client and nothing else" — rather than the server's
696    // own idea of what it did. `subject_dn_match_is_exact` below is the
697    // cautionary example: it builds its expectation from `identity_of(&cert)`,
698    // so it compares the server against itself and passed throughout a period
699    // in which no documented registration could work.
700
701    /// A `tls_client_auth` (§2.1) client is refused a self-asserted
702    /// certificate **even when the DN matches exactly**.
703    ///
704    /// This is the guard, and the DN match is the whole point of the test: §2.1
705    /// authenticates by a name a certificate authority vouched for, and the one
706    /// thing an attacker can trivially do with a self-signed certificate is put
707    /// any name they like in it. `openssl req -subj "/CN=..."` is the entire
708    /// attack. So the registered DN matching must NOT be sufficient here — if
709    /// this test ever passes by having chosen a non-matching DN, it is testing
710    /// nothing.
711    #[test]
712    fn tls_client_auth_refuses_a_self_asserted_certificate_whose_dn_matches() {
713        let (der, _) = cert_with_sans(&["client.example.com"]);
714
715        let chained = PresentedCertificate::from_der(&der, CertTrust::ChainedToAnchor);
716        let self_asserted = PresentedCertificate::from_der(&der, CertTrust::SelfAsserted);
717
718        // One registration, used for both attempts, so the ONLY difference
719        // between the two outcomes below is the trust level.
720        let dn = identity_of(&chained).subject_dn_rfc2253;
721        let mut c = client(ClientAuthMethod::TlsClientAuth);
722        c.tls_client_auth_subject_dn = Some(dn.clone());
723
724        assert!(
725            authenticate_mtls_client(&c, Some(&chained)).is_ok(),
726            "control: the same certificate and the same registered DN {dn:?} must \
727             authenticate when the certificate chained to an anchor — otherwise the \
728             refusal below proves nothing"
729        );
730        assert!(
731            matches!(
732                authenticate_mtls_client(&c, Some(&self_asserted)),
733                Err(OAuth2Error::InvalidClient(_))
734            ),
735            "tls_client_auth must refuse a certificate that chains to no anchor, however \
736             exactly its subject DN matches what was registered"
737        );
738    }

752    /// A `self_signed_tls_client_auth` (§2.2) client authenticates with a
753    /// self-asserted certificate whose thumbprint is registered.
754    ///
755    /// The defect this whole change exists for: AXIAM accepts a §2.2 client
756    /// registration, and before `client_auth = optional_self_signed` no such
757    /// client could complete a TLS handshake — every conformance module
758    /// INTERRUPTED with no HTTP status at all, because the connection died
759    /// before AXIAM saw a request.
760    ///
761    /// The registered thumbprint is computed the way an ADMINISTRATOR computes
762    /// it — `openssl x509 -outform der | sha256sum`, then base64url without
763    /// padding — rather than by asking the certificate for its own
764    /// `thumbprint_s256`. Reading it back off the value under test is exactly
765    /// the self-comparison that let two defects survive on this branch.
766    #[test]
767    fn self_signed_tls_client_auth_accepts_a_self_asserted_certificate() {
768        use base64::Engine as _;
769
770        let (der, cert) =
771            cert_with_sans_trusted_as(&["client.example.com"], CertTrust::SelfAsserted);
772
773        let registered = base64::engine::general_purpose::URL_SAFE_NO_PAD
774            .encode(<Sha256 as Digest>::digest(&der));
775
776        let mut c = client(ClientAuthMethod::SelfSignedTlsClientAuth);
777        c.self_signed_tls_client_auth_thumbprints = vec![registered];
778
779        assert!(
780            authenticate_mtls_client(&c, Some(&cert)).is_ok(),
781            "a §2.2 client whose registered x5t#S256 matches must authenticate with a \
782             certificate that chains to nothing — that is the entire method"
783        );
784    }
