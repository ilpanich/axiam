1//! Mutual-TLS client authentication and certificate-bound tokens
2//! (RFC 8705) — X5.1.
3//!
4//! Two mechanisms live here, and RFC 8705 keeps them deliberately separate
5//! because they answer different questions:
6//!
7//! - **§2, client authentication.** *Who is this client?* The certificate
8//!   replaces the shared secret at the token endpoint. AXIAM implements both
9//!   variants: `tls_client_auth` (PKI — the certificate chains to a CA the
10//!   deployment's listener trusts, and AXIAM matches a registered subject DN
11//!   or SAN) and `self_signed_tls_client_auth` (the certificate *is* the
12//!   registered credential, matched by thumbprint).
13//! - **§3, sender-constrained tokens.** *May this bearer use this token?* The
14//!   access token carries a `cnf.x5t#S256` confirmation naming the
15//!   certificate it was issued to, so a stolen token is inert without the
16//!   corresponding private key.
17//!
18//! # Where the trust actually comes from
19//!
20//! Nothing in this module verifies a certificate chain, and it must not: by
21//! the time a [`PresentedCertificate`] exists, rustls has already verified the
22//! peer chain against the configured client-CA bundle during the TLS 1.3
23//! handshake (`axiam-server`'s `on_connect` hook → `VerifiedClientCert`). This
24//! module's job is the *matching* step — deciding whether the certificate the
25//! transport verified is the one this particular client registered.
26//!
27//! That division is why the `X-Client-Certificate` proxy header, which the
28//! device-auth extractor accepts as a fallback, is **not** accepted here. That
29//! header is an assertion by a reverse proxy; for device authentication, where
30//! the certificate is looked up against a per-tenant issued-certificate table,
31//! a deployment can reasonably choose to trust its own proxy. For OAuth2
32//! client authentication under a FAPI profile it cannot: FAPI 2.0 requires the
33//! authorization server to authenticate the client, and a header is forgeable
34//! by anything that can reach the server on a non-mTLS port. So the header path
35//! is absent by construction rather than gated by configuration — there is no
36//! setting that turns it on.
37//!
38//! # Self-signed certificates and the `x5t#S256` shortcut
39//!
40//! RFC 8705 §2.2 registers a self-signed client's certificates inside its
41//! `jwks`/`jwks_uri`. AXIAM registers the SHA-256 thumbprint instead. The
42//! comparison the spec performs against a self-signed certificate reduces to
43//! an equality check against a registered key, and a thumbprint is that check
44//! without a JWKS parser on the authentication path. What it costs is
45//! JWKS-driven rotation: a self-signed client's new certificate must be
46//! registered rather than merely published. The operator guide says so.
47//!
48//! # A certificate AXIAM revoked authenticates nothing (#565, T-102)
49//!
50//! A chain that verifies says the certificate was issued; it does not say the
51//! certificate is still good, and neither listener's handshake consults a
52//! revocation list. So after the match succeeds, the presented certificate is
53//! looked up by fingerprint in AXIAM's own certificate inventory — the lookup
54//! device sign-in by certificate makes (`DeviceAuthService::authenticate_der`)
55//! — and refused when AXIAM issued it and it is no longer `Active`, or its
56//! issuing CA is no longer `Active`. See [`IssuedCertificateLookup`]. A
57//! certificate AXIAM did not issue is not in the inventory, and is decided as
58//! before.
59//!
60//! # A `tls_client_auth` certificate belongs to the client's organization (R1W1-02)
61//!
62//! The listener is one per deployment and trusts every organization's flagged
63//! anchors at once, and any organization administrator can flag one of their
64//! CAs — an imported one whose key they hold included. A DN or SAN match under
65//! *some* anchor therefore said nothing about *whose*: an administrator of one
66//! organization could mint a certificate carrying another organization's client
67//! DN and take that client's tokens. So under `tls_client_auth`, after the
68//! status check, [`refuse_a_certificate_from_outside_the_clients_organization`]
69//! requires a certificate AXIAM issued to have been issued in the client's
70//! tenant, and any other certificate to have been verified through a chain
71//! whose trust anchor is a CA of the client's organization, with every AXIAM CA
72//! on that chain one the client's organization — and, for a tenant signing CA,
73//! the client's tenant — holds. The chain is the one the TLS handshake built,
74//! carried from the listener as fingerprints ([`PresentedCertificate::with_issuer_path`]).
75//! `self_signed_tls_client_auth` is untouched: its credential is the pinned
76//! thumbprint, not a CA's word.

94/// The single `error_description` every mTLS client-authentication failure
95/// returns, whatever actually went wrong.
96///
97/// Same reasoning as `token::CLIENT_AUTH_FAILED`, which it deliberately
98/// matches word for word: an unauthenticated caller must not be able to tell
99/// "no certificate presented" from "certificate presented but the DN did not
100/// match" from "this client does not use mTLS at all", because each of those
101/// answers is a fact about a client id they have not authenticated as.
102///
103/// The distinctions are kept — they go to the tracing log, where an operator
104/// debugging a genuine onboarding problem can see them and an attacker cannot.
105pub(crate) const MTLS_AUTH_FAILED: &str = "invalid client credentials";

107/// A client certificate that the TLS layer accepted on this connection.
108///
109/// Constructed only from a certificate rustls accepted — which, under
110/// `client_auth = optional_self_signed`, includes one that chains to no
111/// configured anchor. [`Self::trust`] records which, and
112/// [`authenticate_mtls_client`] is where that distinction is spent.
113///
114/// # Why the X.509 parse is lazy
115///
116/// The thumbprint is computed eagerly, because it is one SHA-256 over bytes
117/// already in memory and *every* certificate-bound token needs it. The subject
118/// DN and SANs are not: they are needed only by the `tls_client_auth` variant
119/// of client authentication, and parsing an X.509 structure to extract and
120/// allocate strings nobody reads is real work on a hot path.
121///
122/// The distinction matters because these two costs land on different
123/// populations. Certificate *binding* is what X5.1 advertises as cheap, and it
124/// pays only the SHA-256. A deployment running mTLS with ordinary
125/// `client_secret_post` clients — the IoT shape AXIAM targets — would
126/// otherwise have paid for a DN parse on every token request in exchange for
127/// nothing at all. Eager parsing was the first cut of this type; the
128/// benchmark's A/B is what made the asymmetry visible.
129#[derive(Debug, Clone)]
130pub struct PresentedCertificate {
131    /// DER encoding of the verified leaf certificate.
132    der: Vec<u8>,
133    /// Base64url (no padding) SHA-256 digest of [`Self::der`] — the
134    /// `x5t#S256` value of RFC 8705 §3.1.
135    pub thumbprint_s256: String,
136    /// Whether the TLS layer built a chain for this certificate, or accepted
137    /// it self-asserted (RFC 8705 §2.2).
138    ///
139    /// The distinction is what keeps §2.1 and §2.2 apart at the one point
140    /// where it matters. It is *not* a property of the certificate — the same
141    /// bytes would be [`CertTrust::ChainedToAnchor`] on a listener whose
142    /// anchor set includes their issuer — so it has to be carried from the
143    /// handshake rather than recomputed here.
144    pub trust: CertTrust,
145    /// SHA-256 fingerprints (lowercase hex of the DER) of the certificates the
146    /// TLS handshake verified this one through, nearest issuer first and the
147    /// trust anchor last (R1W1-02). Empty when the listener could not say —
148    /// a self-asserted certificate, or a path it could not re-derive — which
149    /// `tls_client_auth` refuses for a certificate AXIAM did not issue.
150    issuer_path: Vec<String>,
151}

153/// The identity fields of a certificate, parsed on demand.
154///
155/// Separate from [`PresentedCertificate`] so the type system records which
156/// operations need an X.509 parse and which do not: you cannot read a subject
157/// DN without having called [`PresentedCertificate::identity`], and that call
158/// is the parse.
159#[derive(Debug, Clone)]
160pub struct CertificateIdentity {
161    /// Subject distinguished name as `x509_parser` renders it: attributes in
162    /// **certificate (DER) order**, separated by `", "`.
163    pub subject_dn: String,
164    /// The same name in **RFC 2253** form: attributes in reverse order,
165    /// separated by `","` with no space.
166    ///
167    /// Both are carried because both are correct renderings of one name, and a
168    /// registration may legitimately hold either. RFC 2253 §2.1 specifies the
169    /// reversed order, and it is what `openssl x509 -nameopt rfc2253` prints —
170    /// which is what the operator guide tells operators to copy. `x509_parser`
171    /// prints DER order with a space.
172    ///
173    /// Until this field existed, only the first was compared, so a DN copied by
174    /// following the documentation could never match:
175    ///
176    /// ```text
177    /// registered   O=axiam-conformance,CN=axiam-conformance-mtls
178    /// compared to  CN=axiam-conformance-mtls, O=axiam-conformance
179    /// ```
180    ///
181    /// Every `tls_client_auth` client onboarded that way authenticated nothing.
182    /// It cost the FAPI 2.0 conformance lane 89 module failures, all at PAR,
183    /// because every FAPI flow begins there.
184    pub subject_dn_rfc2253: String,
185    /// `dNSName` SAN entries, in certificate order.
186    pub san_dns: Vec<String>,
187    /// `uniformResourceIdentifier` SAN entries, in certificate order.
188    pub san_uri: Vec<String>,
189}

191impl PresentedCertificate {
192    /// Wrap a DER leaf certificate and compute its `x5t#S256` thumbprint.
193    ///
194    /// `trust` says what the TLS handshake established about these bytes and
195    /// has no default: the two levels authorise different things, so the caller
196    /// states which one it observed. See [`CertTrust`].
197    ///
198    /// Infallible: a SHA-256 over arbitrary bytes always succeeds, and the
199    /// bytes are not interpreted here. Anything that needs them to be a
200    /// well-formed certificate goes through [`Self::identity`], which reports
201    /// the parse failure at the point where it actually matters.
202    pub fn from_der(der: &[u8], trust: CertTrust) -> Self {
203        Self {
204            der: der.to_vec(),
205            thumbprint_s256: thumbprint_s256(der),
206            trust,
207            issuer_path: Vec::new(),
208        }
209    }
210
211    /// Record the chain the TLS handshake verified this certificate through:
212    /// the SHA-256 fingerprints (lowercase hex) of each issuer above it,
213    /// nearest first, ending with the trust anchor (R1W1-02).
214    ///
215    /// Only the listener knows it, so only the code that lifts the certificate
216    /// off the connection sets it; with none, `tls_client_auth` accepts only a
217    /// certificate AXIAM issued in the client's own tenant.
218    #[must_use]
219    pub fn with_issuer_path(mut self, issuer_path: Vec<String>) -> Self {
220        self.issuer_path = issuer_path;
221        self
222    }
223
224    /// The chain set by [`Self::with_issuer_path`], nearest issuer first.
225    pub fn issuer_path(&self) -> &[String] {
226        &self.issuer_path
227    }
228
229    /// Parse the subject DN and SANs (RFC 8705 §2.1.2 matching inputs).
230    ///
231    /// Returns `Err` only when the bytes are not a parseable X.509
232    /// certificate. In the native-mTLS path that cannot happen — rustls parsed
233    /// the same bytes to verify the chain — but the fallible signature is kept
234    /// so a future caller cannot introduce an unchecked `unwrap`.
235    pub fn identity(&self) -> Result<CertificateIdentity, String> {
236        let (_, cert) =
237            parse_x509_certificate(&self.der).map_err(|e| format!("parse client cert DER: {e}"))?;
238
239        let mut san_dns = Vec::new();
240        let mut san_uri = Vec::new();
241        if let Ok(Some(ext)) = cert.subject_alternative_name() {
242            for name in &ext.value.general_names {
243                match name {
244                    GeneralName::DNSName(s) => san_dns.push((*s).to_owned()),
245                    GeneralName::URI(s) => san_uri.push((*s).to_owned()),
246                    _ => {}
247                }
248            }
249        }
250
251        // RFC 2253 §2.1: the RDNs are emitted in REVERSE of their encoded
252        // order, joined by `,` with no space. Built from the parsed RDN
253        // sequence rather than by rewriting the string above, because a DN
254        // component may legitimately contain an escaped comma and splitting a
255        // formatted DN on `,` would cut one in half.
256        //
257        // Each RDN is rendered by wrapping it in an `X509Name` of its own, so
258        // the LIBRARY does the RFC 4514 escaping and this code only decides the
259        // order and the separator. A single-RDN name renders with no separator
260        // in it at all, which is what makes joining on `,` exact: an escaped
261        // comma inside a value never reaches the join.
262        let subject_dn_rfc2253 = {
263            let mut parts: Vec<String> = cert
264                .subject()
265                .iter_rdn()
266                .map(|rdn| X509Name::new(vec![rdn.clone()], &[]).to_string())
267                .collect();
268            parts.reverse();
269            parts.join(",")
270        };
271
272        Ok(CertificateIdentity {
273            subject_dn: cert.subject().to_string(),
274            subject_dn_rfc2253,
275            san_dns,
276            san_uri,
277        })
278    }
279}

281/// RFC 8705 §3.1 `x5t#S256`: base64url-encoded, unpadded SHA-256 of the DER
282/// certificate.
283///
284/// Base64url **without** padding is not a stylistic choice: the value travels
285/// inside a JWT claim and an introspection response, and RFC 7515 §2 defines
286/// base64url encoding in JOSE as omitting the `=` padding. A padded value
287/// would not compare equal at a conforming resource server.
288pub fn thumbprint_s256(der: &[u8]) -> String {
289    base64::engine::general_purpose::URL_SAFE_NO_PAD.encode(Sha256::digest(der))
290}

292/// Compare two thumbprints without leaking, through timing, how many leading
293/// characters matched.
294///
295/// A thumbprint is a public value in most threat models — it is derived from a
296/// certificate the client transmits in the clear during the handshake — so
297/// this is belt-and-braces rather than load-bearing. It is cheap, it is the
298/// same discipline `client_secret` verification already applies, and the one
299/// case where it *is* load-bearing is `self_signed_tls_client_auth`, where the
300/// registered thumbprint is the entire credential and an attacker who could
301/// grind it character by character would be forging a client identity rather
302/// than merely recognising one.
303fn thumbprints_match(a: &str, b: &str) -> bool {
304    // `ConstantTimeEq` on unequal-length inputs short-circuits, which leaks
305    // only the length — and both operands are fixed-length base64url SHA-256
306    // digests whenever either is well-formed.
307    a.as_bytes().ct_eq(b.as_bytes()).into()
308}

310/// Authenticate a client by the certificate it presented (RFC 8705 §2).
311///
312/// Called *instead of* secret verification when the client's registered
313/// [`ClientAuthMethod`] is an mTLS one. Returns `Ok(())` only when the
314/// presented certificate matches what this specific client registered.
315///
316/// # The three ways this fails, and why they all look identical
317///
318/// 1. **No certificate on the connection.** The client reached a listener that
319///    does not request client certificates, or presented none. This is the
320///    failure an operator hits most often during onboarding, and the tracing
321///    line says so explicitly.
322/// 2. **The client registered no expectation.** A client whose method is
323///    `tls_client_auth` but which has no `tls_client_auth_subject_dn`,
324///    `…_san_dns` or `…_san_uri` cannot be authenticated by anything, and this
325///    refuses rather than matching everything. Registration validation is meant
326///    to make the state unreachable; this is the second line, because a row
327///    edited directly in the database bypasses registration validation and the
328///    failure mode of guessing here is *authenticating every certificate*.
329/// 3. **The certificate does not match.** A real certificate, accepted by
330///    rustls, belonging to somebody else.
331/// 4. **The certificate is not trusted the way the method requires.** A
332///    `tls_client_auth` (§2.1) client presenting a certificate that chains to
333///    no configured anchor, which `client_auth = optional_self_signed` makes
334///    reachable. §2.1 matches a name a CA vouched for; a self-signed
335///    certificate vouches for itself.
336///
337/// All four answer `invalid_client` with [`MTLS_AUTH_FAILED`]. See that
338/// constant for why.
339pub fn authenticate_mtls_client(
340    client: &OAuth2Client,
341    presented: Option<&PresentedCertificate>,
342) -> Result<(), OAuth2Error> {
343    let method = client.token_endpoint_auth_method;
344    debug_assert!(
345        method.is_mtls(),
346        "authenticate_mtls_client called for a non-mTLS auth method"
347    );
348
349    let Some(cert) = presented else {
350        tracing::debug!(
351            client_id = %client.client_id,
352            method = method.as_str(),
353            "mTLS client authentication failed: no verified client certificate on this \
354             connection (is the client reaching the mTLS listener?)"
355        );
356        return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
357    };
358
359    let matched = match method {
360        ClientAuthMethod::SelfSignedTlsClientAuth => {
361            // Deliberately indifferent to `cert.trust`. §2.2's credential is
362            // the certificate itself: the thumbprint comparison below *is* the
363            // authentication, and it is no weaker for the certificate having
364            // chained to a CA as well. This is the one branch a
365            // `CertTrust::SelfAsserted` certificate can reach, and reaching it
366            // still requires an administrator to have registered its exact
367            // SHA-256.
368            let registered = &client.self_signed_tls_client_auth_thumbprints;
369            if registered.is_empty() {
370                tracing::warn!(
371                    client_id = %client.client_id,
372                    "client is registered for self_signed_tls_client_auth but has no \
373                     registered certificate thumbprint; it cannot authenticate"
374                );
375                return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
376            }
377            // Every candidate is compared even after a match, so the number of
378            // comparisons does not reveal the matching thumbprint's position
379            // in the list.
380            registered.iter().fold(false, |found, t| {
381                thumbprints_match(t, &cert.thumbprint_s256) | found
382            })
383        }
384        ClientAuthMethod::TlsClientAuth => {
385            // §2.1 is the PKI method, and its registered subject DN or SAN is
386            // an assertion *by a certificate authority*. A certificate that
387            // chains to nothing asserts its own subject, so matching a DN
388            // against one would authenticate whoever typed that DN into
389            // `openssl req -subj`.
390            //
391            // A no-op until `client_auth = optional_self_signed` existed —
392            // rustls could not have produced an unchained certificate, so this
393            // condition was unreachable. It is written as a guard rather than
394            // left to that invariant precisely because the invariant has now
395            // been made configurable, and the next thing to make it
396            // configurable again would not come past this file.
397            if !cert.trust.is_chained_to_anchor() {
398                tracing::warn!(
399                    client_id = %client.client_id,
400                    "tls_client_auth (RFC 8705 §2.1) refused: the presented certificate \
401                     chains to no configured trust anchor. §2.1 authenticates by a subject \
402                     DN or SAN vouched for by a CA; a client whose certificate is \
403                     self-signed must be registered for self_signed_tls_client_auth (§2.2) \
404                     with its certificate thumbprint"
405                );
406                return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
407            }
408
409            match client.mtls_binding_count() {
410                0 => {
411                    tracing::warn!(
412                        client_id = %client.client_id,
413                        "client is registered for tls_client_auth but registered no expected \
414                         subject DN or SAN; it cannot authenticate"
415                    );
416                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
417                }
418                // RFC 8705 §2.1.2 permits exactly one. Registration validation
419                // rejects more, but a row that acquired two some other way must
420                // not be authenticated by whichever happens to match — that is
421                // an OR over credentials nobody intended to grant.
422                n if n > 1 => {
423                    tracing::error!(
424                        client_id = %client.client_id,
425                        registered = n,
426                        "client has more than one tls_client_auth_* parameter registered, \
427                         which RFC 8705 §2.1.2 forbids; refusing to guess which one \
428                         authenticates"
429                    );
430                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
431                }
432                _ => {}
433            }
434
435            // The X.509 parse happens here and nowhere else — this is the one
436            // branch that needs a DN or a SAN. A parse failure is an
437            // authentication failure, never a pass: rustls verified these
438            // bytes, so unparseable-here means something is deeply wrong and
439            // the only safe reading is "this is not the registered client".
440            let identity = match cert.identity() {
441                Ok(identity) => identity,
442                Err(e) => {
443                    tracing::error!(
444                        client_id = %client.client_id,
445                        error = %e,
446                        "could not parse a client certificate rustls had already verified; \
447                         refusing the authentication"
448                    );
449                    return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
450                }
451            };
452
453            if let Some(expected) = non_empty(client.tls_client_auth_subject_dn.as_deref()) {
454                // The DN comparison is exact on the RFC 4514 string form. RFC
455                // 8705 §2.1.2 describes this as a comparison of the DN, and a
456                // structural comparison would be more faithful — but a
457                // normalising comparison is exactly where DN-matching CVEs
458                // live, and an exact match can only ever be *too strict*,
459                // which fails an onboarding rather than authenticating a
460                // stranger. The operator guide tells operators to copy the DN
461                // out of `openssl x509 -noout -subject -nameopt rfc2253`.
462                // Compared against BOTH renderings, and this is still an
463                // exact string match — no case folding, no whitespace
464                // stripping, no structural normalisation. The comment above
465                // argues against a normalising comparison and that argument
466                // stands; what changed is that the server now derives every
467                // form it is willing to accept FROM THE CERTIFICATE, and the
468                // registered value must equal one of them exactly.
469                //
470                // Two forms because both are correct renderings of one name and
471                // the operator guide documents the RFC 2253 one. Accepting only
472                // the other meant a DN copied as documented could never match.
473                expected == identity.subject_dn || expected == identity.subject_dn_rfc2253
474            } else if let Some(expected) = non_empty(client.tls_client_auth_san_dns.as_deref()) {
475                // DNS names are case-insensitive (RFC 4343). No wildcard
476                // handling: a wildcard registered here would authenticate
477                // every certificate a CA issued under that suffix as this
478                // client, which is not an authentication decision anybody
479                // should be able to make by typing `*`.
480                identity
481                    .san_dns
482                    .iter()
483                    .any(|got| got.eq_ignore_ascii_case(expected))
484            } else if let Some(expected) = non_empty(client.tls_client_auth_san_uri.as_deref()) {
485                // URIs are compared exactly: unlike a DNS name, no component
486                // of a URI is case-insensitive in a way that is safe to assume
487                // here.
488                identity.san_uri.iter().any(|got| got == expected)
489            } else {
490                // Unreachable: `mtls_binding_count()` returned 1 above, and it
491                // counts exactly these three fields under the same
492                // non-emptiness rule.
493                false
494            }
495        }
496        // None of these authenticates by certificate. Reaching here at all
497        // means a caller routed a non-mTLS client into the mTLS path, which the
498        // `debug_assert` above catches in tests; in release the answer is
499        // "not authenticated", never "authenticated by default".
500        ClientAuthMethod::ClientSecretPost
501        | ClientAuthMethod::ClientSecretBasic
502        | ClientAuthMethod::PrivateKeyJwt
503        | ClientAuthMethod::None => false,
504    };
505
506    if !matched {
507        tracing::debug!(
508            client_id = %client.client_id,
509            method = method.as_str(),
510            "mTLS client authentication failed: the verified client certificate does not \
511             match this client's registered expectation"
512        );
513        return Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()));
514    }
515
516    Ok(())
517}

544///
545/// A port rather than a repository type parameter on `TokenService` so the
546/// token service keeps its eight, and object-safe for the reason
547/// `axiam_core::ca_keys::CaKeyStore` is: the composition root builds one and
548/// every grant shares it. [`InventoryCertificateLookup`] is the implementation.
549pub trait IssuedCertificateLookup: Send + Sync {
550    /// The standing of the certificate whose DER encoding is `der`.
551    ///
552    /// An `Err` is a failed read, never a verdict: the caller answers it as a
553    /// server error, not as "not issued here".
554    fn standing<'a>(
555        &'a self,
556        der: &'a [u8],
557    ) -> Pin<Box<dyn Future<Output = AxiamResult<IssuedCertificateStanding>> + Send + 'a>>;
558
559    /// Every CA record — any organization, any status — whose certificate has
560    /// one of `fingerprints` (R1W1-02): whose CA each certificate of a verified
561    /// chain is.
562    ///
563    /// Required, with no default, for the reason [`TokenService::new`] takes
564    /// the lookup at all: a default answering "no records" would refuse every
565    /// externally issued `tls_client_auth` certificate silently, and one
566    /// answering anything else would admit them.
567    ///
568    /// [`TokenService::new`]: crate::token::TokenService::new
569    fn ca_records<'a>(
570        &'a self,
571        fingerprints: &'a [String],
572    ) -> Pin<Box<dyn Future<Output = AxiamResult<Vec<CaCertificate>>> + Send + 'a>>;
573}

575/// [`IssuedCertificateLookup`] over the certificate and CA repositories — the
576/// same two reads, in the same order, as device sign-in by certificate.
577#[derive(Clone)]
578pub struct InventoryCertificateLookup<CR, CCR> {
579    cert_repo: CR,
580    ca_repo: CCR,
581}

583impl<CR, CCR> InventoryCertificateLookup<CR, CCR> {
584    /// Look certificates up in `cert_repo`, and their issuers in `ca_repo`.
585    pub fn new(cert_repo: CR, ca_repo: CCR) -> Self {
586        Self { cert_repo, ca_repo }
587    }

589
590impl<CR, CCR> IssuedCertificateLookup for InventoryCertificateLookup<CR, CCR>
591where
592    CR: CertificateRepository,
593    CCR: CaCertificateRepository,
594{
595    fn standing<'a>(
596        &'a self,
597        der: &'a [u8],
598    ) -> Pin<Box<dyn Future<Output = AxiamResult<IssuedCertificateStanding>> + Send + 'a>> {
599        Box::pin(async move {
600            // The inventory's key: lowercase hex SHA-256 of the DER, as
601            // `axiam_pki` computes it at issuance.
602            let fingerprint = hex::encode(Sha256::digest(der));
603            let cert = match self.cert_repo.get_by_fingerprint_global(&fingerprint).await {
604                Ok(cert) => cert,
605                Err(AxiamError::NotFound { .. }) => {
606                    return Ok(IssuedCertificateStanding::NotIssuedHere);
607                }
608                Err(e) => return Err(e),
609            };
610            let now = chrono::Utc::now();
611            let tenant_id = cert.tenant_id;
612            if cert.status != CertificateStatus::Active
613                || now < cert.not_before
614                || now > cert.not_after
615            {
616                return Ok(IssuedCertificateStanding::NotActive);
617            }
618            // The issuing CA, as `authenticate_der` reads it (SECHRD-05): a
619            // revoked tenant signing CA leaves its leaves `Active` in the
620            // inventory, and they still chain to the organization anchor above
621            // it. A CA row that is gone is not an issuer anybody vouches for.
622            match self.ca_repo.get_by_issuer_id(cert.issuer_ca_id).await {
623                Ok(ca)
624                    if ca.status == CertificateStatus::Active
625                        && now >= ca.not_before
626                        && now <= ca.not_after =>
627                {
628                    Ok(IssuedCertificateStanding::Active { tenant_id })
629                }
630                Ok(_) | Err(AxiamError::NotFound { .. }) => {
631                    Ok(IssuedCertificateStanding::NotActive)
632                }
633                Err(e) => Err(e),
634            }
635        })
636    }
637
638    fn ca_records<'a>(
639        &'a self,
640        fingerprints: &'a [String],
641    ) -> Pin<Box<dyn Future<Output = AxiamResult<Vec<CaCertificate>>> + Send + 'a>> {
642        Box::pin(self.ca_repo.list_by_fingerprints(fingerprints))
643    }
644}

646/// Refuse a certificate AXIAM issued and no longer stands behind (#565,
647/// T-102).
648///
649/// Called by the token service after [`authenticate_mtls_client`] has matched
650/// `presented` to `client`, under either mTLS method: a certificate AXIAM
651/// revoked authenticates no client, whether the client registered its subject
652/// (§2.1) or its thumbprint (§2.2). A certificate AXIAM did not issue —
653/// [`IssuedCertificateStanding::NotIssuedHere`] — passes unchanged; see that
654/// variant.
655///
656/// The refusal is `invalid_client` with [`MTLS_AUTH_FAILED`], like every other
657/// mTLS failure; the reason goes to the log. A failed read is a server error,
658/// never an authentication.
659///
660/// Returns the standing it read, for
661/// [`refuse_a_certificate_from_outside_the_clients_organization`].
662pub async fn refuse_a_certificate_axiam_revoked(
663    client: &OAuth2Client,
664    presented: &PresentedCertificate,
665    lookup: &dyn IssuedCertificateLookup,
666) -> Result<IssuedCertificateStanding, OAuth2Error> {
667    match lookup.standing(&presented.der).await {
668        Ok(
669            standing @ (IssuedCertificateStanding::NotIssuedHere
670            | IssuedCertificateStanding::Active { .. }),
671        ) => Ok(standing),
672        Ok(IssuedCertificateStanding::NotActive) => {
673            tracing::warn!(
674                client_id = %client.client_id,
675                method = client.token_endpoint_auth_method.as_str(),
676                "mTLS client authentication refused: the presented certificate was issued by \
677                 AXIAM and is revoked or expired, or its issuing CA is"
678            );
679            Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()))
680        }
681        Err(e) => Err(OAuth2Error::ServerError(format!(
682            "could not read the presented client certificate's status: {e}"
683        ))),
684    }
685}

687/// Refuse, under `tls_client_auth`, a certificate that does not belong to the
688/// client's organization (R1W1-02).
689///
690/// Called by the token service after [`refuse_a_certificate_axiam_revoked`],
691/// with the standing it returned and the organization of the client's tenant:
692///
693/// - **A certificate AXIAM issued** must have been issued in the client's
694///   tenant. Its subject is a CN an administrator typed, and any tenant can be
695///   issued any CN; that it is AXIAM's says nothing about whose.
696/// - **Any other certificate** must have been verified through a chain
697///   ([`PresentedCertificate::issuer_path`]) whose **trust anchor is a CA the
698///   client's organization holds**, active and in date, and on which **every
699///   certificate AXIAM records as a CA** has such a record in the client's
700///   organization — for a tenant signing CA, in the client's tenant. A chain
701///   the listener could not report, an anchor AXIAM records for no
702///   organization (one an operator placed in a bundle by hand) and an anchor
703///   only another organization holds are all refused: the listener trusts every
704///   organization's anchors at once, so "it chained" alone says nothing about
705///   whose CA vouched for the DN.
706///
707/// `self_signed_tls_client_auth` is not checked here: its credential is the
708/// thumbprint the client registered. The refusal is `invalid_client` with
709/// [`MTLS_AUTH_FAILED`]; a failed read is a server error.
710pub async fn refuse_a_certificate_from_outside_the_clients_organization(
711    client: &OAuth2Client,
712    client_organization: Uuid,
713    presented: &PresentedCertificate,
714    standing: IssuedCertificateStanding,
715    lookup: &dyn IssuedCertificateLookup,
716) -> Result<(), OAuth2Error> {
717    let refuse = |reason: &str| {
718        tracing::warn!(
719            client_id = %client.client_id,
720            tenant_id = %client.tenant_id,
721            reason,
722            "tls_client_auth refused: the presented certificate does not belong to the \
723             client's organization (R1W1-02)"
724        );
725        Err(OAuth2Error::InvalidClient(MTLS_AUTH_FAILED.into()))
726    };
727    if client.token_endpoint_auth_method != ClientAuthMethod::TlsClientAuth {
728        return Ok(());
729    }
730    match standing {
731        IssuedCertificateStanding::Active { tenant_id } if tenant_id == client.tenant_id => {
732            return Ok(());
733        }
734        IssuedCertificateStanding::Active { .. } => {
735            return refuse("AXIAM issued it in another tenant");
736        }
737        // Refused already by `refuse_a_certificate_axiam_revoked`; never a pass.
738        IssuedCertificateStanding::NotActive => {
739            return refuse("AXIAM issued it and no longer stands behind it");
740        }
741        IssuedCertificateStanding::NotIssuedHere => {}
742    }
743
744    let path = presented.issuer_path();
745    let Some(anchor) = path.last() else {
746        return refuse(
747            "the listener reported no verified chain for a certificate AXIAM did not issue",
748        );
749    };
750    let records = lookup
751        .ca_records(path)
752        .await
753        .map_err(|e| OAuth2Error::ServerError(format!("could not read the chain's CAs: {e}")))?;
754    let now = chrono::Utc::now();
755    let in_scope = |ca: &CaCertificate| {
756        ca.organization_id == client_organization
757            && ca.tenant_id.is_none_or(|t| t == client.tenant_id)
758            && ca.status == CertificateStatus::Active
759            && now >= ca.not_before
760            && now <= ca.not_after
761    };
762    for fingerprint in path {
763        let mut held = records
764            .iter()
765            .filter(|ca| &ca.fingerprint == fingerprint)
766            .peekable();
767        if held.peek().is_none() {
768            if fingerprint == anchor {
769                return refuse("its trust anchor is no CA of the client's organization");
770            }
771            // An intermediate AXIAM does not record (an external sub-CA) adds
772            // no claim; the anchor above it decides.
773            continue;
774        }
775        if !held.any(&in_scope) {
776            return refuse(if fingerprint == anchor {
777                "its trust anchor is another organization's CA, or one the client's \
778                 organization no longer stands behind"
779            } else {
780                "its chain runs through another organization's or another tenant's CA"
781            });
782        }
783    }
784    Ok(())
785}

787/// A registered value counts only when it is present *and* non-blank.
788///
789/// Mirrors `OAuth2Client::mtls_binding_count`'s rule exactly. The two must
790/// agree: if the counter treated `Some("")` as registered and the matcher
791/// treated it as absent, a client could reach the `else` branch with a count
792/// of one and authenticate nothing — or, worse, the reverse.
793fn non_empty(value: Option<&str>) -> Option<&str> {
794    value.map(str::trim).filter(|v| !v.is_empty())
795}

1316    /// A lookup that answers one verdict for every certificate, and holds the
1317    /// CA records it is given.
1318    struct Answers(Result<IssuedCertificateStanding, ()>, Vec<CaCertificate>);
1319
1320    impl Answers {
1321        fn verdict(verdict: Result<IssuedCertificateStanding, ()>) -> Self {
1322            Self(verdict, Vec::new())
1323        }
1324    }
1325
1326    impl IssuedCertificateLookup for Answers {
1327        fn standing<'a>(
1328            &'a self,
1329            _der: &'a [u8],
1330        ) -> Pin<Box<dyn Future<Output = AxiamResult<IssuedCertificateStanding>> + Send + 'a>>
1331        {
1332            let verdict = self
1333                .0
1334                .map_err(|()| AxiamError::Database("the store is down".into()));
1335            Box::pin(async move { verdict })
1336        }
1337
1338        fn ca_records<'a>(
1339            &'a self,
1340            fingerprints: &'a [String],
1341        ) -> Pin<Box<dyn Future<Output = AxiamResult<Vec<CaCertificate>>> + Send + 'a>> {
1342            let records = self
1343                .1
1344                .iter()
1345                .filter(|ca| fingerprints.contains(&ca.fingerprint))
1346                .cloned()
1347                .collect();
1348            Box::pin(async move { Ok(records) })
1349        }
1350    }
