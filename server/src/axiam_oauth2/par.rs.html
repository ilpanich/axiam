1//! Pushed Authorization Requests (RFC 9126) — B5.
2//!
3//! The client POSTs its authorization parameters to `/oauth2/par`, where it
4//! **authenticates**, and gets back an opaque `request_uri` to put in the
5//! browser redirect instead of the parameters themselves.
6//!
7//! # What this actually buys
8//!
9//! In a plain authorization-code redirect, every parameter travels through the
10//! user agent: it lands in browser history, in `Referer` headers, in any proxy
11//! access log along the way, and — the part that matters — it is trivially
12//! modifiable by whoever controls the browser. PKCE closes the code-injection
13//! half of that, but nothing stops a tampered `scope` or `redirect_uri` from
14//! reaching the authorization endpoint attributable to nobody.
15//!
16//! With PAR the parameters arrive over a direct, client-authenticated,
17//! server-to-server POST. What travels through the browser is a random string
18//! that means nothing to anyone who intercepts it and cannot be edited into
19//! meaning something else. This is why FAPI 2.0 requires it, and why X5 needs
20//! it before a conformance run is possible.
21//!
22//! # The two rules that carry the security
23//!
24//! 1. **Single-use.** Enforced in the repository's `consume`, in one
25//!    statement. A replayable `request_uri` is a replayable authorization
26//!    request.
27//! 2. **Parameters do not mix.** An authorize request carrying both a
28//!    `request_uri` and inline parameters is refused rather than merged.
29//!    Merging is exactly where parameter confusion lives: the attacker
30//!    supplies the inline value they want and lets the pushed one satisfy
31//!    whatever check reads the other copy.
32

45/// The `request_uri` scheme RFC 9126 §2.2 mandates.
46pub const REQUEST_URI_PREFIX: &str = "urn:ietf:params:oauth:request_uri:";
47
48/// How long a pushed request stays usable.
49///
50/// RFC 9126 §2.2 suggests "in the order of seconds to a few minutes", and the
51/// window only has to cover one browser redirect. There is deliberately no
52/// configuration knob in v1: every value an operator might pick is either this
53/// or worse, and a tunable that only trends longer is a tunable that only
54/// widens a replay window.
55pub const REQUEST_URI_LIFETIME_SECS: i64 = 60;
56
57/// The longest `state` or `nonce` a **fapi2** client may push.
58///
59/// 256 characters, which is six times what a 32-byte random value needs once
60/// base64url-encoded (43) and comfortably above anything that carries entropy
61/// rather than payload. It is not a guess at what clients send: the OpenID
62/// Foundation's FAPI 2.0 suite probes this boundary directly with a
63/// 1000-character `state` and a 384-character `nonce`, and requires both to be
64/// refused, so any cap that admits either is not conformant.
65///
66/// Characters, not bytes — [`str::len`] would make the limit depend on how
67/// many non-ASCII code points the value happens to contain, and the value is
68/// opaque, so the count the client can reason about is the one to bound.
69pub const MAX_FAPI_OPAQUE_PARAM_CHARS: usize = 256;

71/// Generate a `request_uri`: 256 bits of CSPRNG behind the RFC's URN prefix.
72pub fn generate_request_uri() -> String {
73    let mut rng = rand::rng();
74    let bytes: [u8; 32] = rng.random();
75    format!("{REQUEST_URI_PREFIX}{}", URL_SAFE_NO_PAD.encode(bytes))
76}
77
78/// SHA-256 of a `request_uri`'s random component, hex-encoded — what is stored.
79///
80/// Hashed at rest for the same reason device codes are: for the 60 s it lives,
81/// the `request_uri` is a bearer credential, and a database read should not
82/// hand an attacker a usable one. SHA-256 rather than a KDF because the value
83/// is a 256-bit CSPRNG string with no offline-guessing threat to defend
84/// against.
85pub fn hash_request_uri(raw: &str) -> String {
86    let component = raw.strip_prefix(REQUEST_URI_PREFIX).unwrap_or(raw);
87    let mut hasher = Sha256::new();
88    hasher.update(component.as_bytes());
89    hex::encode(hasher.finalize())
90}

92/// What a client pushes.
93///
94/// X7.1 — the nine OIDC authentication-request parameters are pushed
95/// alongside the original seven. PAR and the inline query string are two
96/// carriers of one request, and for a `require_par` client PAR is the only
97/// carrier there is: a parameter added to only one of them is silently lost by
98/// exactly the clients the FAPI profile insists on.
99#[derive(Debug, Clone, Default)]
100pub struct PushedRequest {
101    pub tenant_id: Uuid,
102    pub client_id: String,
103    pub response_type: String,
104    pub redirect_uri: String,
105    pub scope: Option<String>,
106    pub state: Option<String>,
107    pub code_challenge: Option<String>,
108    pub code_challenge_method: Option<String>,
109    pub nonce: Option<String>,
110    pub prompt: Option<String>,
111    pub max_age: Option<String>,
112    pub acr_values: Option<String>,
113    pub claims: Option<String>,
114    pub id_token_hint: Option<String>,
115    pub login_hint: Option<String>,
116    pub display: Option<String>,
117    pub ui_locales: Option<String>,
118    pub claims_locales: Option<String>,
119    /// RFC 9449 §10 — the DPoP key this request binds its authorization to.
120    ///
121    /// Already *resolved* by the caller: the handler is where both inputs
122    /// exist (the `dpop_jkt` form parameter and the `DPoP` header's verified
123    /// thumbprint), and §10.1's rule that the two must agree is a refusal the
124    /// endpoint owes the client before anything is stored. What arrives here
125    /// is the single key the authorization is bound to, or `None`.
126    pub dpop_jkt: Option<String>,
127    /// T21.3 / RFC 8707 §2 — the target service this request is for.
128    ///
129    /// Validated here rather than deferred to `/oauth2/authorize`, for the
130    /// same reason the `redirect_uri` is: the client is authenticated *now*,
131    /// so an `invalid_target` is attributable and reaches the client as a
132    /// protocol error — instead of surfacing in a browser after a sign-in the
133    /// user should never have been asked for.
134    pub resource: Option<String>,
135}

163    /// Store a pushed authorization request and mint its `request_uri`.
164    ///
165    /// The caller must already have authenticated the client — that is the
166    /// point of the endpoint, and doing it here as well would duplicate the
167    /// one secret-verification path the token endpoint shares.
168    pub async fn push(&self, req: PushedRequest) -> Result<PushedAuthResponse, OAuth2Error> {
169        let client = self
170            .client_repo
171            .get_by_client_id(req.tenant_id, &req.client_id)
172            .await
173            .map_err(|e| match e {
174                // Same QUAL-03/D-11 discipline as the authorize endpoint: only
175                // a genuinely-unknown client is `invalid_client`. A DB outage
176                // must not masquerade as bad client credentials.
177                AxiamError::NotFound { .. } => {
178                    OAuth2Error::InvalidClient("client not found".into())
179                }
180                other => OAuth2Error::ServerError(other.to_string()),
181            })?;
182
183        // The redirect_uri is validated here, not deferred to the authorize
184        // step. Validating at push time is the whole benefit: the client is
185        // authenticated *now*, so a rejection is attributable, and the browser
186        // never gets a request_uri standing for a request that was going to
187        // fail anyway.
188        // T21.2: the same matcher the authorization endpoint uses, so the two
189        // cannot come to disagree about what this client registered — a PAR
190        // request accepted here and refused at `/oauth2/authorize` would hand
191        // the user agent a `request_uri` standing for a request that cannot
192        // complete, which is the failure this check exists to prevent.
193        if !crate::redirect_uri::any_redirect_uri_matches(&client.redirect_uris, &req.redirect_uri)
194        {
195            return Err(OAuth2Error::InvalidRedirectUri(
196                "redirect_uri is not registered for this client".into(),
197            ));
198        }
199
200        if req.response_type != "code" {
201            return Err(OAuth2Error::UnsupportedResponseType);
202        }
203
204        // `state` and `nonce` are bounded, on the FAPI 2.0 profile only.
205        //
206        // Both are opaque values the client chooses and the server only ever
207        // echoes, so a client has no legitimate need for a long one: 32 bytes
208        // of entropy is 43 characters base64url, and the cap below is six
209        // times that. What an unbounded value buys instead is a way to push
210        // kilobytes of attacker-chosen text through the authorization request
211        // and back out of the `redirect_uri` — stored in the datastore in the
212        // meantime, and reflected into whatever the client does with `state`.
213        //
214        // Gated on [`ClientProfile::Fapi2`] deliberately, and not applied to
215        // `Standard`. A cap is a breaking change for any client that packs
216        // data into `state` — a bad practice, but a widespread one, and one a
217        // deployment upgrading AXIAM has not agreed to. The FAPI profile is
218        // the place where a client HAS agreed to the stricter bundle, and the
219        // OpenID Foundation's own conformance suite requires the refusal
220        // (`ensure-authorization-request-with-long-state` pushes 1000
221        // characters, `-with-long-nonce` pushes 384, and both expect
222        // `invalid_request`).
223        //
224        // Checked here rather than at `/oauth2/authorize` for the same reason
225        // the `redirect_uri` above is: the client is authenticated *now*, so
226        // the refusal is attributable and reaches the client as a protocol
227        // error — instead of surfacing in a browser after a sign-in the user
228        // should never have been asked for.
229        if client.profile == ClientProfile::Fapi2 {
230            for (name, value) in [
231                ("state", req.state.as_deref()),
232                ("nonce", req.nonce.as_deref()),
233            ] {
234                if let Some(v) = value
235                    && v.chars().count() > MAX_FAPI_OPAQUE_PARAM_CHARS
236                {
237                    return Err(OAuth2Error::InvalidRequest(format!(
238                        "{name} exceeds the {MAX_FAPI_OPAQUE_PARAM_CHARS}-character limit this \
239                         client's fapi2 profile imposes"
240                    )));
241                }
242            }
243        }
244
245        // T21.3 / RFC 8707 §2 — the resource indicator, validated against the
246        // client's allow-list and stored in its normalised form so the
247        // authorization endpoint compares the same string this endpoint
248        // accepted. Absent is `Ok(None)` and changes nothing (I2).
249        let resource =
250            crate::resource::resolve_requested(&client.allowed_resources, req.resource.as_deref())?;
251
252        // RFC 9126 §2.1: `request_uri` is not a parameter a client may push.
253        // Accepting one would let a client chain pushed requests, and the
254        // second would inherit the first's authentication.
255        let request_uri = generate_request_uri();
256        let expires_at = Utc::now() + Duration::seconds(REQUEST_URI_LIFETIME_SECS);
257
258        self.par_repo
259            .create(CreatePushedAuthRequest {
260                tenant_id: req.tenant_id,
261                client_id: req.client_id,
262                request_uri_hash: hash_request_uri(&request_uri),
263                params: PushedAuthParams {
264                    response_type: req.response_type,
265                    redirect_uri: req.redirect_uri,
266                    scope: req.scope,
267                    state: req.state,
268                    code_challenge: req.code_challenge,
269                    code_challenge_method: req.code_challenge_method,
270                    nonce: req.nonce,
271                    prompt: req.prompt,
272                    max_age: req.max_age,
273                    acr_values: req.acr_values,
274                    claims: req.claims,
275                    id_token_hint: req.id_token_hint,
276                    login_hint: req.login_hint,
277                    display: req.display,
278                    ui_locales: req.ui_locales,
279                    claims_locales: req.claims_locales,
280                    dpop_jkt: req.dpop_jkt,
281                    resource,
282                },
283                expires_at,
284            })
285            .await
286            .map_err(|e| OAuth2Error::ServerError(e.to_string()))?;
287
288        Ok(PushedAuthResponse {
289            request_uri,
290            expires_in: REQUEST_URI_LIFETIME_SECS,
291        })
292    }

294    /// Resolve and consume a `request_uri` on the authorize path.
295    ///
296    /// The returned parameters are the ones the client pushed; the caller must
297    /// use them *instead of* anything on the authorize query string, never
298    /// merged with it.
299    pub async fn consume(
300        &self,
301        tenant_id: Uuid,
302        client_id: &str,
303        request_uri: &str,
304    ) -> Result<PushedAuthParams, OAuth2Error> {
305        if !request_uri.starts_with(REQUEST_URI_PREFIX) {
306            return Err(OAuth2Error::InvalidRequest(
307                "request_uri is not a pushed authorization request URI".into(),
308            ));
309        }
310
311        let stored = self
312            .par_repo
313            .consume(tenant_id, &hash_request_uri(request_uri))
314            .await
315            .map_err(|e| OAuth2Error::ServerError(e.to_string()))?
316            .ok_or_else(|| {
317                // Unknown, expired and already-consumed all answer identically,
318                // deliberately: distinguishing them tells an attacker holding a
319                // stolen request_uri whether it is worth racing for, and none of
320                // the three is recoverable by the client anyway.
321                OAuth2Error::InvalidRequest(REQUEST_URI_GONE.into())
322            })?;
323
324        // The pushed request belongs to the client that pushed it. Without
325        // this, a second client could spend another client's request_uri and
326        // receive a code minted against the first client's registration.
327        if stored.client_id != client_id {
328            return Err(OAuth2Error::InvalidRequest(
329                "request_uri was not issued to this client".into(),
330            ));
331        }
332
333        Ok(stored.params)
334    }

336    /// Ask whether a `request_uri` is still spendable, **without** spending it.
337    ///
338    /// Answers the three questions [`consume`](Self::consume) answers — is this
339    /// a pushed-request handle at all, does an unexpired and unconsumed row
340    /// exist for it, and does that row belong to this client — with the same
341    /// refusals, in the same order, and nothing else.
342    ///
343    /// # Why this exists, and why it returns nothing
344    ///
345    /// `/oauth2/authorize` sends an anonymous browser to a sign-in page before
346    /// it can consume anything: the handle is single-use and is spent in the
347    /// handler, after a principal exists. So a request presenting a
348    /// `request_uri` that was already used, expired, or issued to a different
349    /// client took a person through a full sign-in for a request that was dead
350    /// before they started, and refused it afterwards. This lets the endpoint
351    /// refuse first.
352    ///
353    /// It returns `()` rather than the pushed parameters **deliberately**. A
354    /// caller holding them could authorize from a handle it never consumed, and
355    /// the single-use guarantee is exactly the property that would lose. The
356    /// authoritative decision stays in `consume`, inside the handler: a
357    /// `request_uri` that passes here has not been authorized, has not been
358    /// spent, and may still lose the race to a concurrent authorize request —
359    /// which is the correct outcome, and the reason nothing here is cached,
360    /// marked or carried forward.
361    ///
362    /// **This is an early refusal, never an authorization.**
363    pub async fn peek(
364        &self,
365        tenant_id: Uuid,
366        client_id: &str,
367        request_uri: &str,
368    ) -> Result<(), OAuth2Error> {
369        if !request_uri.starts_with(REQUEST_URI_PREFIX) {
370            return Err(OAuth2Error::InvalidRequest(
371                "request_uri is not a pushed authorization request URI".into(),
372            ));
373        }
374
375        let stored = self
376            .par_repo
377            .find_unconsumed(tenant_id, &hash_request_uri(request_uri))
378            .await
379            .map_err(|e| OAuth2Error::ServerError(e.to_string()))?
380            // Unknown, expired and already-consumed answer identically here for
381            // the same reason they do in `consume`, and the wording is the same
382            // constant so the two cannot come to describe the same state
383            // differently depending on how far the request got.
384            .ok_or_else(|| OAuth2Error::InvalidRequest(REQUEST_URI_GONE.into()))?;
385
386        if stored.client_id != client_id {
387            return Err(OAuth2Error::InvalidRequest(
388                "request_uri was not issued to this client".into(),
389            ));
390        }
391
392        Ok(())
393    }
394}

396/// The single answer given for a `request_uri` that is unknown, expired or
397/// already consumed.
398///
399/// A constant because two places need to agree on it: [`ParService::consume`]
400/// produces it, and the authorization endpoint recognises it to tell a
401/// **login-hop return leg** whose 60-second window closed (W3, plan §4.0 and
402/// F10) apart from a client that sent nonsense. See [`is_request_uri_gone`].
403pub const REQUEST_URI_GONE: &str = "request_uri is unknown, expired, or used";
404
405/// Is this the "the pushed request is gone" refusal?
406///
407/// The recogniser lives here, next to the producer, so the two cannot drift:
408/// a caller matching on the message itself would keep compiling after the
409/// wording changed and would silently stop recognising the case.
410///
411/// Deliberately narrow. `request_uri was not issued to this client` is a
412/// different failure — a client spending someone else's handle — and must keep
413/// its own answer even on a return leg.
414pub fn is_request_uri_gone(e: &OAuth2Error) -> bool {
415    matches!(e, OAuth2Error::InvalidRequest(msg) if msg == REQUEST_URI_GONE)
416}

418// `has_inline_params` used to live here: it reported whether an authorize
419// request carried `response_type`/`redirect_uri`/`scope`/`code_challenge`
420// alongside a `request_uri`, and the authorization endpoint refused such a
421// request as "the two forms do not mix".
422//
423// It is gone rather than merely unused, because the rule it encoded is not the
424// one the specifications state. RFC 9126 §4 delegates the shape of the
425// authorization request to RFC 9101, whose §5 says a client MAY duplicate the
426// pushed parameters in the query string and whose §6.3 says the authorization
427// server MUST only *use* the ones from the pushed request. Ignore, not refuse
428// — and the endpoint reads every field from the pushed copy already, so
429// ignoring is what it now does. See the comment at the `request_uri` branch in

594                unreachable!("peek does not clean up")
595            }

607    /// A live handle is spendable, and **stays** spendable.
608    ///
609    /// The second assertion is the one that matters. `peek` exists so that a
610    /// dead `request_uri` can be refused before a person is asked to sign in
611    /// for it; if it spent the handle on the way past, it would break the
612    /// opposite case — the OIDF module
613    /// `par-ensure-reused-request-uri-prior-to-auth-completion-succeeds`
614    /// presents one `request_uri` twice before any authorization completes and
615    /// requires the login page both times.
616    #[tokio::test]
617    async fn a_live_handle_passes_and_is_not_spent() {
618        let tenant = Uuid::now_v7();
619        let svc = service(OneRow::live(tenant, "client-a"));
620        let uri = generate_request_uri();
621
622        assert!(svc.peek(tenant, "client-a", &uri).await.is_ok());
623        assert_eq!(
624            svc.par_repo.consumes.load(Ordering::SeqCst),
625            0,
626            "peek must never call consume — the single-use decision belongs in \
627             the handler, after a principal exists"
628        );
629        assert_eq!(svc.par_repo.reads.load(Ordering::SeqCst), 1);
630    }
