1//! SCIM authorization: the dedicated `scim:provision` permission (B4).
2//!
3//! # Tenant scoping — the code path
4//!
5//! SCIM reuses `axiam-api-rest`'s [`AuthenticatedUser`] extractor unchanged:
6//! every `/scim/v2/*` handler takes `user: AuthenticatedUser` exactly like a
7//! native `/api/v1/users` handler does, and the middleware chain in front of
8//! it (`AuthzMiddleware`, wired in `crate::routes`) is the same one every
9//! other authenticated scope uses. `AuthenticatedUser::tenant_id` comes
10//! **only** from the validated JWT's `tenant_id` claim — never from anything
11//! in the SCIM request path or body. Every repository call this crate makes
12//! (`UserRepository`/`GroupRepository`) takes that same `tenant_id` as an
13//! explicit, mandatory parameter and every generated SurrealDB query filters
14//! on it (see `axiam-db`'s `user.rs`/`group.rs`). A caller cannot name
15//! another tenant's resources into existence in the query, and a token
16//! minted for tenant A therefore cannot read or mutate tenant B's data
17//! through this crate — not because SCIM adds a check, but because it never
18//! introduces a second source of tenant identity for the check to miss.
19//!
20//! This is call-time enforcement (checked on every request), not a
21//! provisioning-time assumption: even a handler bug that forgot to call
22//! [`require_scim_provision`] would still be unable to cross tenants, because
23//! the cross-tenant channel does not exist in the repository calls it would
24//! make. `tests/contract_test.rs`'s tenant-isolation tests exercise exactly
25//! this property adversarially (cross-tenant GET/PUT/PATCH/DELETE/list by
26//! UUID, not merely "no token").
27//!
28//! # What `scim:provision` actually confers (SEC-098) — read before granting
29//!
30//! **A holder of `scim:provision` can set any user's password in this tenant,
31//! including a tenant administrator's, and then log in as them.**
32//!
33//! RFC 7643 §4.1.1 defines `password` as a writable User attribute and
34//! `PATCH /scim/v2/Users/{id}` honours it ([`crate::users::patch`]). The
35//! native admin API has no equivalent — `handlers::users::update` never
36//! writes `password_hash`, and the only native password writes are
37//! self-service change and reset inside `AuthService`. So this single
38//! permission is strictly more powerful than `users:create` +
39//! `users:update` combined, and the provisioning guide's own advice ("grant
40//! it to your Okta/Entra integration identity") is therefore advice to grant
41//! tenant-wide account takeover to an external system.
42//!
43//! That is the correct reading of the RFC and it is not being changed here;
44//! what was wrong was that nothing said it. If a deployment federates and
45//! never pushes a password — which is most Okta/Entra deployments — the
46//! integration identity does not need this capability and splitting it behind
47//! a second permission is a reasonable follow-on.
48//!
49//! Two consequences that ARE fixed rather than documented, in
50//! [`crate::users`]: a SCIM password write, an `active: false`, and a
51//! `DELETE /Users/{id}` each revoke every live session and OAuth2 refresh
52//! token for the target. Before SEC-098 they flushed only the authorization
53//! *decision* cache, so a password rotated to lock out a compromised account
54//! left the attacker's session and refresh token spendable.
55//!
56//! # Principal — a note for operators (see `docs/api/scim-provisioning.md`)
57//!
58//! The bearer principal is deliberately whichever tenant-scoped AXIAM
59//! identity holds `scim:provision` — in practice a dedicated tenant user
60//! (e.g. `scim-provisioner`) created and role-granted through the existing
61//! `/api/v1/users` + `/api/v1/roles` APIs, **not** a `service_account` row:
62//! AXIAM's RBAC role-assignment edge (`has_role`) is hard-scoped to the
63//! `user` table today (`axiam-db`'s `RoleRepository::assign_to_user`/
64//! `get_user_role_assignments` both query `type::record('user', $id)`), so a
65//! `service_account` subject cannot currently hold ANY RBAC permission,
66//! `scim:provision` included. That gap predates this crate and is out of
67//! R3.1's file scope (`axiam-db`, `axiam-authz`) to close; it is flagged
68//! here, in the provisioning guide, and in this task's final report so a
69//! follow-on (the planned SCIM token-management UI, or a dedicated fix) has
70//! a precise pointer.
71use axiam_api_rest::authz::{AuthzChecker, RequirePermission};
72use axiam_api_rest::extractors::auth::AuthenticatedUser;
73use uuid::Uuid;
74
75use crate::error::ScimError;

77/// The permission every `/scim/v2/*` route requires (B4: "a DEDICATED
78/// `scim:provision` permission"). Declared here, and separately registered
79/// in `axiam_api_rest::permissions::PERMISSION_REGISTRY` (the same array
80/// every other AXIAM permission is declared in) so it is seeded per-tenant
81/// exactly like `users:create`, `groups:list`, etc.
82pub const SCIM_PROVISION_PERMISSION: &str = "scim:provision";
83
84/// Enforce `scim:provision` for the calling principal, using the SAME
85/// [`RequirePermission`] guard every native `/api/v1/*` handler uses. Not
86/// resource-scoped (SCIM has no notion of an AXIAM `resource` hierarchy), so
87/// the check runs against the global sentinel (`Uuid::nil()`), exactly like
88/// `users:create`/`groups:create` do today.
89pub async fn require_scim_provision(
90    user: &AuthenticatedUser,
91    authz: &dyn AuthzChecker,
92) -> Result<(), ScimError> {
93    RequirePermission::new(SCIM_PROVISION_PERMISSION, Uuid::nil())
94        .check(user, authz)
95        .await
96        .map_err(ScimError::from)
97}
